# 2) Service Loadbalancing — 경로로 나눠 보내기

원문 : https://cafe.naver.com/kubeops/529 (2. Service Loadbalancing)

- 선행 조건 : [1번](1.nginx-controller.md)의 Nginx Controller

Service는 **하나의 앱**에 트래픽을 보낸다. 앱이 셋이면 Service도 셋이고,
외부에서는 포트를 셋 알아야 한다.

Ingress는 **입구 하나**를 두고 URL 경로로 갈라 보낸다.

```
                    ┌─ /          ──▶ svc-shopping ──▶ pod-shopping
30431 ──▶ nginx ────┼─ /customer  ──▶ svc-customer ──▶ pod-customer
                    └─ /order     ──▶ svc-order    ──▶ pod-order
```

## 왜 필요한가

### 없으면 이렇게 된다

[1번](1.nginx-controller.md)으로 컨트롤러는 떴다. 이제 **규칙**을 줄 차례다.

규칙이 없으면 앱마다 Service를 따로 열어야 한다.
Service는 **하나의 앱**에만 트래픽을 보내기 때문이다.
앱이 셋이면 외부 노출도 셋이고, 사용자는 **포트를 세 개 외워야 한다.**

```
30001 → shopping
30002 → customer      ← 사용자가 전부 알아야 한다
30003 → order
```

### 경로로 가르기

Ingress 규칙을 주면 **주소 하나로 통합**된다. 뒤에서 어떻게 나뉘는지는 사용자가 몰라도 된다.

```
                    ┌─ /          ──▶ svc-shopping ──▶ pod-shopping
30431 ──▶ nginx ────┼─ /customer  ──▶ svc-customer ──▶ pod-customer
                    └─ /order     ──▶ svc-order    ──▶ pod-order
```

이 구조에는 부수 효과가 하나 있다. **뒤의 Service를 전부 ClusterIP로 둘 수 있다.**
외부에 노출되는 것은 nginx 하나뿐이므로, 앱들은 클러스터 안에만 있으면 된다.
노출면이 줄어 보안에도 낫다.

경로 매칭 방식을 정하는 `pathType`은 **생략할 수 없다.**
`v1`에서 필수가 됐는데, 이전 버전 예제를 복사하면 여기서 막힌다.

### 이 문서에서 확인할 것

- 경로에 따라 다른 Pod이 응답하는가 (3절)
- 뒤의 Service가 ClusterIP여도 외부에서 닿는가 (2절)
- `ADDRESS` 칸에 뜨는 IP는 무엇인가 (3절)
- `pathType`을 빼면 어떻게 되는가 (YAML 절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

# Ingress도 비운다 (ingress-nginx 네임스페이스의 컨트롤러는 건드리지 않는다)
kubectl delete ingress --all -n default --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> 선행 조건인 `ingress-nginx` 컨트롤러는 다른 네임스페이스라 지워지지 않는다.

## YAML

Pod과 Service는 평범하다. 세 벌을 만든다 (shopping / customer / order).

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-shopping
  labels:
    category: shopping
spec:
  containers:
  - name: container
    image: kubetm/shopping                     # 자기 이름을 응답하는 실습 이미지
---
apiVersion: v1
kind: Service
metadata:
  name: svc-shopping
spec:
  selector:
    category: shopping
  ports:
  - port: 8080                                 # ClusterIP 로 충분하다. 입구는 nginx 다
```

핵심은 Ingress다.

```yaml
apiVersion: networking.k8s.io/v1               # v1beta1 은 폐기됐다
kind: Ingress
metadata:
  name: service-loadbalancing
spec:
  ingressClassName: nginx                      # 어느 컨트롤러가 처리할지
  rules:
  - http:                                      # host 를 안 적으면 모든 호스트에 적용
      paths:
      - path: /                                # 이 경로로 오면
        pathType: Prefix
        backend:
          service:
            name: svc-shopping                 # 이 Service 로 보낸다
            port:
              number: 8080
      - path: /customer
        pathType: Prefix
        backend:
          service:
            name: svc-customer
            port:
              number: 8080
      - path: /order
        pathType: Prefix
        backend:
          service:
            name: svc-order
            port:
              number: 8080
```

### `pathType` 세 가지

| 값 | 의미 |
|---|---|
| `Prefix` | 경로가 이것으로 **시작**하면 매치 (`/order` → `/order/123` 도 포함) |
| `Exact` | 정확히 일치해야 함 |
| `ImplementationSpecific` | 컨트롤러가 알아서 (nginx는 정규식 지원) |

> **`pathType`은 필수 필드다.** v1beta1에서는 없어도 됐지만 v1에서는 안 적으면 거부된다.
> 원문이 *"버전(v1beta1 -> v1)이 변경되면서 Yaml 스펙이 바꼈어요"* 라고 한 부분이다.

## 실습 과정

```bash
clear                                                                                              # 화면 정리 후 시작
kubectl apply -f - <<'END'                                                                         # Pod 3개 + Service 3개 생성
# ... pod-shopping, pod-customer, pod-order 와 각 Service ...
END

kubectl wait --for=condition=Ready pod/pod-shopping pod/pod-customer pod/pod-order --timeout=240s  # 대기

kubectl apply -f - <<'END'                                                                         # Ingress 생성
# ... service-loadbalancing YAML ...
END

kubectl get ingress                                                                                # 등록 확인
```

```
NAME                    CLASS   HOSTS   ADDRESS         PORTS   AGE
service-loadbalancing   nginx   *       192.168.56.32   80      15s
```

`ADDRESS`에 nginx 컨트롤러 Pod이 떠 있는 노드 IP가 찍힌다.
`HOSTS`가 `*` 인 것은 `host` 를 안 적었기 때문이다.

```bash
clear                              # 화면 정리 후 시작
curl 192.168.56.30:30431/          # 기본 경로
curl 192.168.56.30:30431/customer  # 고객센터
curl 192.168.56.30:30431/order     # 주문
```

```
Shopping Service.
Customer Service.
Order Service.
```

**포트 하나(30431)로 세 앱에 도달했다.**

> master(`.30`)로 호출했는데 nginx Pod은 worker2(`.32`)에 있다.
> NodePort라 어느 노드로 들어가도 nginx까지 전달된다 (게시글 498).

### 정리

```bash
clear                                                            # 화면 정리 후 시작
kubectl delete ingress service-loadbalancing --ignore-not-found  # Ingress 삭제

kubectl delete pod \
  pod-shopping \
  pod-customer \
  pod-order \
  --grace-period=1 --ignore-not-found

kubectl delete svc \
  svc-shopping \
  svc-customer \
  svc-order \
  --ignore-not-found
```

## 배운 것

- Ingress는 **입구 하나로 여러 Service를 나눠 보낸다.** 포트를 여러 개 열 필요가 없다.
- `apiVersion: networking.k8s.io/v1` 을 쓴다. `v1beta1` 은 폐기됐다.
- `pathType` 은 **필수**다. 보통 `Prefix` 를 쓴다.
- 뒤에 붙는 Service는 `ClusterIP` 로 충분하다. 외부 입구는 nginx가 담당한다.
- `kubectl get ingress` 의 `ADDRESS` 는 컨트롤러 Pod이 있는 노드 IP다.
