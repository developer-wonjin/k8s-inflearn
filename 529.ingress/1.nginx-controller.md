# 1) Nginx Ingress Controller 설치

원문 : https://cafe.naver.com/kubeops/529 (1. Nginx Controller)

**Ingress는 규칙일 뿐이다. 그 규칙을 실행하는 것은 Ingress Controller다.**

컨트롤러가 없으면 Ingress를 아무리 만들어도 아무 일도 일어나지 않는다.
Deployment를 만들었는데 kube-controller-manager가 없는 것과 같은 상황이다.

```
[사용자] ──▶ NodePort 30431 ──▶ Nginx Controller ──▶ Ingress 규칙을 읽고 ──▶ Service ──▶ Pod
                                (실제로 트래픽을 나눠주는 주체)
```

## 왜 필요한가

### 없으면 이렇게 된다

[498](../498.service-clusterip-nodeport-loadbalancer/README.md)에서 외부 노출 방법을 봤다.
그런데 **앱이 여러 개**가 되면 둘 다 불편해진다.

| 방식 | 앱이 3개면 |
|---|---|
| NodePort | 포트가 3개 (`30001`, `30002`, `30003`). 사용자가 전부 알아야 한다 |
| LoadBalancer | **LB가 3개.** 클라우드에서는 곧 요금 3배다 |

게다가 둘 다 **L4**라 경로를 구분하지 못한다.
`/order`와 `/customer`를 다른 앱으로 보내고 싶어도 방법이 없다.
HTTPS 인증서도 앱마다 따로 넣어야 한다.

### Ingress가 세우는 입구

Ingress는 **입구 하나**를 두고 **URL로 갈라 보낸다.** L7이라 경로와 호스트를 볼 수 있다.

```
                    ┌─ /          ──▶ svc-shopping
30431 ──▶ nginx ────┼─ /customer  ──▶ svc-customer
                    └─ /order     ──▶ svc-order
```

여기서 이 게시글 전체를 관통하는 핵심이 나온다.

> **Ingress는 규칙일 뿐이다. 그 규칙을 실행하는 것은 Ingress Controller다.**

Ingress 오브젝트는 "이렇게 나눠 보내라"고 적어둔 **명세서**에 지나지 않는다.
그 명세서를 읽고 **실제로 트래픽을 처리하는 프로그램**이 따로 떠 있어야 한다.

컨트롤러가 없으면 Ingress를 아무리 만들어도 **아무 일도 일어나지 않는다.**
그래서 이 게시글의 첫 문서가 규칙이 아니라 **설치**인 것이다.

### 이 문서에서 확인할 것

- 컨트롤러가 무엇으로 떠 있는가 — 어떤 포트로 입구를 여는가 (3절)
- `IngressClass`는 무슨 역할인가 (4절)
- `Completed`로 남는 Job들은 정상인가 (3절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## 설치

```bash
clear  # 화면 정리 후 시작
kubectl apply -f https://raw.githubusercontent.com/k8s-1pro/install/refs/heads/main/ground/k8s-1.27/nginx-1.8.2/nginx-controller.yaml

```

### 설치 확인

```bash
clear                             # 화면 정리 후 시작
kubectl get all -n ingress-nginx  # 컨트롤러가 떴는지
```

```
NAME                                            READY   STATUS      RESTARTS   AGE
pod/ingress-nginx-admission-create-s6rp7        0/1     Completed   0          40s
pod/ingress-nginx-admission-patch-v7nv8         0/1     Completed   0          40s
pod/ingress-nginx-controller-5c778bffff-xbtmz   1/1     Running     0          40s

NAME                              TYPE       CLUSTER-IP     PORT(S)                      AGE
service/ingress-nginx-controller  NodePort   10.101.10.24   80:30431/TCP,443:30798/TCP   41s
```

세 가지를 확인한다.

- **`ingress-nginx-controller` Pod이 `Running`** — 이것이 실제 nginx다
- **`admission-create`/`admission-patch` Job이 `Completed`** — 웹훅 인증서를 만드는 일회성 작업이다.
  `Completed`가 정상이고, 지우지 않아도 된다 (게시글 507의 Job과 같다)
- **NodePort `30431`(http), `30798`(https)** — 외부에서 들어오는 입구

> **트래픽은 반드시 이 포트로 보내야 한다.** Ingress에 규칙을 적어도
> Service로 직접 접속하면 규칙이 적용되지 않는다. nginx를 거쳐야 한다.

### IngressClass

```bash
clear                     # 화면 정리 후 시작
kubectl get ingressclass  # 어떤 컨트롤러가 등록돼 있나
```

```
NAME    CONTROLLER             AGE
nginx   k8s.io/ingress-nginx   1m
```

Ingress를 만들 때 `ingressClassName: nginx` 라고 적는 것이 이 이름이다.
컨트롤러가 여러 개일 수 있어서(nginx, traefik, HAProxy...) **누가 처리할지 지정**하는 것이다.

## 배운 것

- **Ingress는 규칙, Controller는 실행 주체.** 컨트롤러가 없으면 Ingress는 무의미하다.
- 이 설치본은 NodePort **30431(http) / 30798(https)** 로 입구를 연다.
- `IngressClass`(여기서는 `nginx`)로 **어느 컨트롤러가 처리할지** 지정한다.
- `admission-create`/`patch` Job이 `Completed`로 남는 것은 정상이다.
