# 3) Canary Upgrade — 일부 트래픽만 새 버전으로

원문 : https://cafe.naver.com/kubeops/529 (3. Canary Upgrade)

- 선행 조건 : [1번](1.nginx-controller.md)의 Nginx Controller

게시글 504에서 배포 전략 세 가지를 봤다. RollingUpdate는 **비율을 정할 수 없었다.**
교체가 시작되면 알아서 끝까지 간다.

Canary는 **"10%만 새 버전으로 보내고 지켜보자"** 를 가능하게 한다.
Ingress에 **annotation** 을 붙이면 nginx가 그 비율대로 나눠준다.

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

# Ingress도 비운다 (ingress-nginx 네임스페이스의 컨트롤러는 건드리지 않는다)
kubectl delete ingress --all -n default --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> 선행 조건인 `ingress-nginx` 컨트롤러는 다른 네임스페이스라 지워지지 않는다.

## 준비 — v1이 기본, v2는 대기

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-v1
  labels:
    app: v1
spec:
  containers:
  - name: container
    image: kubetm/app:v1                       # /version 으로 버전을 응답한다
---
apiVersion: v1
kind: Service
metadata:
  name: svc-v1
spec:
  selector:
    app: v1
  ports:
  - port: 8080
```

`pod-v2` / `svc-v2` 도 같은 형태로 만든다 (`app: v2`, `kubetm/app:v2`).

기본 Ingress는 **v1만** 가리킨다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app
spec:
  ingressClassName: nginx
  rules:
  - host: www.app.com                          # 이번엔 host 를 지정한다
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: svc-v1
            port:
              number: 8080
```

```bash
clear                                                                    # 화면 정리 후 시작
kubectl apply -f - <<'END'                                               # v1, v2, 기본 Ingress 생성
# ... pod-v1, svc-v1, pod-v2, svc-v2, app Ingress ...
END

kubectl wait --for=condition=Ready pod/pod-v1 pod/pod-v2 --timeout=240s  # 대기

# host 를 지정했으므로 이름으로 접속해야 한다
grep -q 'www.app.com' /etc/hosts || echo '192.168.56.30 www.app.com' >> /etc/hosts

curl www.app.com:30431/version                                           # 현재 버전
```

```
Version : v1
```

`pod-v2`도 떠 있지만 트래픽은 v1으로만 간다. **가리키는 Ingress가 없기 때문**이다.

## 3-4) 가중치로 나누기

기존 Ingress는 그대로 두고 **canary 표시가 붙은 Ingress를 하나 더** 만든다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: canary-v2
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"        # 이건 canary 규칙이다
    nginx.ingress.kubernetes.io/canary-weight: "10"   # 10% 를 여기로
spec:
  ingressClassName: nginx
  rules:
  - host: www.app.com                          # 같은 host, 같은 path 여야 한다
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: svc-v2                       # 나머지만 다르다
            port:
              number: 8080
```

**같은 `host` + `path`에 Ingress가 두 개** 있는 상태가 된다.
평소라면 충돌이지만, `canary: "true"` 가 붙으면 **덮어쓰는 게 아니라 비율로 나눈다.**

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # canary Ingress 추가
# ... canary-v2 YAML ...
END

# 100번 호출해서 분포를 센다
for i in $(seq 1 100); do curl -s www.app.com:30431/version; echo; done | sort | uniq -c
```

```
     92 Version : v1
      8 Version : v2
```

**약 10%가 v2로 갔다.** 정확히 10은 아니다. 확률적 분배라 호출 수가 적으면 편차가 있다.

`canary-weight` 값을 올리면 그만큼 넘어간다. `100`으로 두면 전부 v2로 간다.
**서서히 올리면서 지켜보는 것**이 canary 배포다.

## 3-5) 헤더로 나누기

비율이 아니라 **특정 조건**으로 보낼 수도 있다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: canary-kr
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-by-header: "Accept-Language"   # 이 헤더가
    nginx.ingress.kubernetes.io/canary-by-header-value: "kr"          # 이 값이면
spec:
  ingressClassName: nginx
  rules:
  - host: www.app.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: svc-v2
            port:
              number: 8080
```

```bash
clear                                                    # 화면 정리 후 시작
kubectl delete ingress canary-v2 --ignore-not-found      # 가중치 규칙은 먼저 지운다
kubectl apply -f - <<'END'                               # 헤더 규칙 생성
# ... canary-kr YAML ...
END

curl www.app.com:30431/version                           # 헤더 없이
curl -H "Accept-Language: kr" www.app.com:30431/version  # kr 헤더
curl -H "Accept-Language: en" www.app.com:30431/version  # en 헤더
```

```
헤더 없이            → Version : v1     (5회 모두)
Accept-Language: kr  → Version : v2     (5회 모두)
Accept-Language: en  → Version : v1     (3회 모두)
```

**값까지 정확히 일치해야** 넘어간다. `en` 은 v1으로 갔다.

확률이 아니라 **결정적**이다. 특정 사용자·팀만 새 버전을 쓰게 할 때 유용하다.

| 방식 | annotation | 성격 |
|---|---|---|
| 가중치 | `canary-weight` | 확률적. 전체 사용자의 N% |
| 헤더 | `canary-by-header` + `-value` | 결정적. 조건에 맞는 요청만 |
| 쿠키 | `canary-by-cookie` | 결정적. 같은 사용자는 계속 같은 버전 |

### 정리

```bash
clear                               # 화면 정리 후 시작
kubectl delete ingress \
  app \
  canary-v2 \
  canary-kr \
  --ignore-not-found

kubectl delete pod \
  pod-v1 \
  pod-v2 \
  --grace-period=1 --ignore-not-found

kubectl delete svc \
  svc-v1 \
  svc-v2 \
  --ignore-not-found

sed -i '/www.app.com/d' /etc/hosts  # hosts 에 추가한 줄 제거
```

## 배운 것

- Canary는 **Ingress annotation** 으로 동작한다. nginx가 그 설정을 읽어 트래픽을 나눈다.
- 같은 `host` + `path` 에 Ingress를 하나 더 만들되 `canary: "true"` 를 붙인다.
- `canary-weight` 는 **확률적**, `canary-by-header` 는 **결정적**이다.
- 헤더 방식은 **값까지 일치**해야 한다.
- 504의 RollingUpdate는 비율을 조절할 수 없었다. Canary는 **속도를 사람이 정한다.**
