# 3) Headless Service — 각 Pod을 이름으로 부르기

원문 : https://cafe.naver.com/kubeops/528 (3. Headless Service)

- 선행 조건 : [2번](2.persistentvolume.md)의 `stateful-pvc` StatefulSet

이름이 고정되고(1번) 볼륨이 각자 있어도(2번), **밖에서 특정 Pod을 지목할 수 없으면** 소용이 없다.
일반 Service는 요청을 아무 Pod에나 보내기 때문이다.

Headless Service가 그 마지막 조각이다.

## 왜 필요한가

### 없으면 이렇게 된다

이름이 고정되고([1번](1.pod-naming-order.md)) 볼륨도 각자 갖게 됐다([2번](2.persistentvolume.md)).
그런데 **밖에서 특정 Pod을 지목할 수 없으면** 그 모든 게 소용없다.

일반 Service는 요청을 **아무 Pod에나** 보낸다. 그것이 Service의 존재 이유다.
하지만 "primary에만 쓰기를 보내야 한다"는 요구 앞에서는 정확히 반대로 동작한다.

`stateful-pvc-0`이 primary인 것을 알아도, **거기로 보낼 주소가 없다.**
Pod IP는 재생성마다 바뀌므로 적어둘 수도 없다.

### Headless가 채우는 마지막 조각

[516 2](../516.service-headless-endpoint-externalname/2.headless.md)에서 봤듯
`clusterIP: None`이면 DNS가 **Pod을 개별적으로** 알려준다.

StatefulSet과 만나면 여기에 **이름이 고정된다**는 성질이 더해진다.

```
stateful-pvc-0.svc-headless.default.svc.cluster.local  ──▶ 0번 Pod
stateful-pvc-1.svc-headless.default.svc.cluster.local  ──▶ 1번 Pod
```

Pod이 죽었다 살아나도 **번호가 같으므로 주소도 같다.**
이제 "0번에만 쓰기를 보낸다"를 설정 파일에 적을 수 있다.

| 조각 | 보장하는 것 |
|---|---|
| 순번 이름 (1번) | 재생성돼도 **같은 신원** |
| `volumeClaimTemplates` (2번) | 재생성돼도 **같은 데이터** |
| **Headless (이 문서)** | 재생성돼도 **같은 주소** |

세 가지가 다 있어야 StatefulSet이 완성된다.

### 이 문서에서 확인할 것

- Pod마다 개별 도메인이 정말 생기는가 (2절)
- Pod을 지웠다 살려도 같은 주소로 닿는가 (3절)
- `serviceName`을 지정하지 않으면 어떻게 되는가 (YAML 절)

## 시작 전 확인

> **여기서는 정리하지 않는다.** 이 문서는 2에서 만든 **StatefulSet `stateful-pvc`** 가 남아 있어야 성립한다.
> 표준 정리 블록을 돌리면 전제가 사라져 실습 자체가 되지 않는다.

| 상황 | 할 일 |
|---|---|
| 앞 문서를 막 끝내고 이어서 온 경우 | 그대로 진행한다 |
| 처음부터 다시 하는 경우 | [2.persistentvolume.md](2.persistentvolume.md) 를 먼저 실습하고 돌아온다 |

```bash
clear                                 # 화면 정리 후 시작
kubectl get statefulset stateful-pvc  # 전제가 남아 있는지 확인 — 없으면 앞 문서부터
```

## YAML

```yaml
apiVersion: v1
kind: Service
metadata:
  name: stateful-headless                      # StatefulSet 의 serviceName 과 같아야 한다
spec:
  selector:
    type: db2
  ports:
    - port: 80
      targetPort: 8080
  clusterIP: None                              # 이 줄이 Headless 로 만든다
```

StatefulSet 쪽에는 이 이름을 적어둔다.

```yaml
kind: StatefulSet
spec:
  serviceName: "stateful-headless"             # 이 Service 를 통해 Pod 도메인이 만들어진다
```

> **`serviceName`은 StatefulSet의 필수 필드다.** 없으면 생성이 거부된다.
> Headless Service 자체가 나중에 만들어져도 상관없지만, 이름은 미리 정해둬야 한다.

## 실습 과정

### 1. Service 이름으로 조회하면 Pod IP들이 나온다

```bash
clear                                                              # 화면 정리 후 시작
kubectl apply -f - <<'END'                                         # 호출용 Pod 생성
apiVersion: v1
kind: Pod
metadata:
  name: request-pod
spec:
  containers:
  - name: container
    image: kubetm/init
END

kubectl wait --for=condition=Ready pod/request-pod --timeout=180s  # 뜰 때까지
kubectl exec request-pod -- nslookup stateful-headless             # Service 이름으로 질의
```

```
Name:    stateful-headless.default.svc.cluster.local
Address: 20.110.126.10
Name:    stateful-headless.default.svc.cluster.local
Address: 20.100.194.120
```

**Pod IP 두 개가 나온다.** Service IP가 없으니 Pod IP를 직접 준다 (게시글 516과 동일).

### 2. Pod마다 고유한 도메인

```bash
clear                                                                               # 화면 정리 후 시작
kubectl exec request-pod -- curl -s stateful-pvc-0.stateful-headless:8080/hostname  # 0번 지목
kubectl exec request-pod -- curl -s stateful-pvc-1.stateful-headless:8080/hostname  # 1번 지목
```

```
Hostname : stateful-pvc-0
Hostname : stateful-pvc-1
```

**부른 Pod이 정확히 응답한다.** 도메인 형식은 이렇다.

```
<Pod이름>.<Service이름>.<네임스페이스>.svc.cluster.local
stateful-pvc-0 . stateful-headless . default . svc.cluster.local
```

516에서는 Pod에 `hostname`·`subdomain`을 직접 적어야 했다.
**StatefulSet은 그것을 자동으로 해준다.** Pod 이름이 곧 도메인 앞부분이 된다.

## 세 조각이 모여야 완성된다

StatefulSet이 상태 있는 앱을 감당할 수 있는 이유는 세 가지가 함께 동작하기 때문이다.

| 조각 | 보장하는 것 | 없으면 |
|---|---|---|
| **순번 이름** (1번) | Pod을 구분할 수 있다 | 누가 primary인지 모른다 |
| **개별 볼륨** (2번) | 각자 자기 데이터를 갖는다 | 데이터가 섞인다 |
| **Headless Service** (3번) | 밖에서 특정 Pod을 부를 수 있다 | 지목할 방법이 없다 |

실제 DB 클러스터라면 이렇게 쓴다.

```
mysql-0.mysql-headless   →  primary  (쓰기)
mysql-1.mysql-headless   →  replica  (읽기)
mysql-2.mysql-headless   →  replica  (읽기)
```

애플리케이션 설정에 이 주소를 **그대로 박아둘 수 있다.**
Pod이 죽었다 살아나도 이름과 데이터가 그대로이기 때문이다.

### 정리 — 528 실습 전체

```bash
clear                                                                # 화면 정리 후 시작
kubectl delete pod request-pod --grace-period=1 --ignore-not-found   # 호출용 Pod

kubectl delete sts stateful-pvc --grace-period=1 --ignore-not-found  # StatefulSet
kubectl delete rs replica-pvc --grace-period=1 --ignore-not-found    # ReplicaSet
kubectl delete svc stateful-headless --ignore-not-found              # Headless Service

# PVC 는 컨트롤러를 지워도 남으므로 직접 지운다
kubectl delete pvc \
  replica-pvc1 \
  volume-stateful-pvc-0 \
  volume-stateful-pvc-1 \
  --ignore-not-found

# 이 실습에서 수동으로 만든 PV 와 StorageClass 도 정리한다
kubectl delete pv \
  manual-pv-1 \
  manual-pv-2 \
  manual-pv-3 \
  manual-pv-4 \
  --ignore-not-found

kubectl delete sc fast --ignore-not-found                            # StorageClass
kubectl get all,pvc,pv -n default                                    # service/kubernetes 만 남으면 정상
```

## 배운 것

- Headless Service가 있어야 **Pod을 이름으로 지목**할 수 있다.
- 도메인은 `<Pod이름>.<Service이름>.<네임스페이스>.svc.cluster.local` 이다.
- StatefulSet은 `hostname`/`subdomain` 을 **자동으로** 설정해준다 (516과 다른 점).
- `serviceName`은 StatefulSet의 **필수 필드**다.
- 순번 이름 + 개별 볼륨 + Headless Service, **셋이 모여야** 상태 있는 앱이 성립한다.
