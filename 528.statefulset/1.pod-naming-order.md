# 1) Pod 이름과 생성·삭제 순서

원문 : https://cafe.naver.com/kubeops/528 (1. StatefulSet Controller)

ReplicaSet의 Pod들은 **서로 구분되지 않는다.** 아무거나 죽여도 되고 아무거나 요청을 받아도 된다.
StatefulSet의 Pod들은 **각자 역할이 있다.** DB의 primary와 replica처럼.

그 차이가 **이름**과 **순서**에서 먼저 드러난다.

## 왜 필요한가

### 없으면 이렇게 된다

[ReplicaSet](../503.replicaset/1.template-replicas.md)의 Pod들은 **서로 구분되지 않는다.**
이름이 `web-79c7f75bc-4lfm8`처럼 랜덤이고, 아무거나 죽여도 되고 아무거나 요청을 받아도 된다.
웹 서버라면 그게 맞다. 어느 Pod이 응답하든 결과가 같기 때문이다.

그런데 **각자 역할이 다른** 경우가 있다.

- DB 복제 구성에서 **primary는 하나**여야 하고, 쓰기는 거기로만 가야 한다
- 카프카 브로커는 **자기 번호**를 알아야 하고, 그 번호의 데이터를 갖고 있어야 한다
- 클러스터 멤버들이 **서로를 순서대로** 찾아 합류해야 한다

이때 랜덤 이름은 치명적이다. Pod이 재생성되면 이름이 바뀌어
**"방금 죽은 그 Pod"이 누구였는지 알 수 없다.**
동시에 우르르 뜨면 누가 primary인지 정할 수도 없다.

### StatefulSet이 고정하는 것

StatefulSet은 Pod에 **번호를 붙여 신원을 고정한다.** 이 문서는 그 첫 번째 조각을 다룬다.

| | ReplicaSet | StatefulSet |
|---|---|---|
| 이름 | `<이름>-<랜덤5자>` | **`<이름>-<순번>`** |
| 생성 | 동시에 | **0부터 하나씩** |
| 삭제 | 동시에 | **큰 번호부터 하나씩** |
| Pod 구분 | 안 됨 | **번호로 구분됨** |

순서대로 하나씩 처리하는 이유는 **앞 Pod이 준비돼야 뒤 Pod이 의미를 갖기 때문**이다.
`-0`이 primary로 뜬 뒤에 `-1`이 복제본으로 붙어야 순서가 맞는다.

> StatefulSet이 완성되려면 세 조각이 다 필요하다.
> **이름(이 문서) + 각자의 볼륨([2번](2.persistentvolume.md)) + 개별 주소([3번](3.headless-service.md))**

### 이 문서에서 확인할 것

- Pod 이름이 실제로 어떻게 지어지는가 (2절)
- 정말 하나씩 순서대로 뜨는가 (2절)
- `replicas`를 줄이면 어느 번호부터 사라지는가 (3절)
- 중간 번호 Pod을 지우면 **같은 이름**으로 돌아오는가 (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## YAML

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # replica-web — ReplicaSet (replicas 1)
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: replica-web
spec:
  replicas: 1
  selector:
    matchLabels:
      type: web
  template:
    metadata:
      labels:
        type: web
    spec:
      containers:
      - name: container
        image: kubetm/app
      terminationGracePeriodSeconds: 10
END
```

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # stateful-db — StatefulSet (replicas 1)
apiVersion: apps/v1
kind: StatefulSet                              # 형태는 ReplicaSet 과 거의 같다
metadata:
  name: stateful-db
spec:
  replicas: 1
  selector:
    matchLabels:
      type: db
  template:
    metadata:
      labels:
        type: db
    spec:
      containers:
      - name: container
        image: kubetm/app
      terminationGracePeriodSeconds: 10
END
```

## 실습 과정

### 1. 이름이 다르다

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # ReplicaSet 과 StatefulSet 을 하나씩 생성
# ... 위 YAML 전체 ...
END

kubectl get pod             # 이름 비교
```

```
replica-web-5dh55        ← <컨트롤러명>-<랜덤 5자>
stateful-db-0            ← <컨트롤러명>-<순번>
```

**StatefulSet은 0부터 순번을 붙인다.** 예측 가능한 이름이다.
`stateful-db-0` 이 primary, `-1`, `-2` 가 replica 같은 식으로 역할을 고정할 수 있다.

### 2. 생성 순서가 다르다

```bash
clear                                       # 화면 정리 후 시작
kubectl scale rs replica-web --replicas=3   # ReplicaSet 을 3개로
kubectl scale sts stateful-db --replicas=3  # StatefulSet 도 3개로

# 4초 간격으로 상태를 본다
for i in $(seq 1 6); do
  printf "  [%2ds] rs=%s  sts=%s\n" $((i*4)) \
    "$(kubectl get pod -l type=web --no-headers | awk '{printf "%s(%s) ", $1, $3}')" \
    "$(kubectl get pod -l type=db  --no-headers | awk '{printf "%s(%s) ", $1, $3}')"
  timeout 4 tail -f /dev/null
done
```

```
[ 4s] rs=...5dh55(Running) ...gf8m6(Pending) ...hrgcj(ContainerCreating)
      sts=stateful-db-0(Running) stateful-db-1(ContainerCreating)

[ 8s] rs=(3개 모두 Running)
      sts=stateful-db-0(Running) stateful-db-1(Running) stateful-db-2(ContainerCreating)

[12s] sts=(3개 모두 Running)
```

- **ReplicaSet** — 3개를 **동시에** 만든다. 4초 만에 다 뜬다.
- **StatefulSet** — `0` 이 Running이 된 다음 `1`, 그다음 `2`. **하나씩 순서대로.**

앞 번호가 준비돼야 다음이 시작한다. DB 클러스터에서 primary가 떠야 replica가
붙을 수 있는 상황을 그대로 반영한 것이다.

### 3. 삭제 순서는 반대다

```bash
clear                                      # 화면 정리 후 시작
kubectl scale rs replica-web --replicas=0  # 둘 다 0으로 줄인다
kubectl scale sts stateful-db --replicas=0

for i in $(seq 1 7); do
  printf "  [%2ds] rs=%s개  sts=%s\n" $((i*5)) \
    "$(kubectl get pod -l type=web --no-headers | wc -l)" \
    "$(kubectl get pod -l type=db  --no-headers | awk '{printf "%s ", $1}')"
  timeout 5 tail -f /dev/null
done
```

```
[ 5s] rs=3개  sts=stateful-db-0 stateful-db-1 stateful-db-2
[20s] rs=0개  sts=stateful-db-0 stateful-db-1        ← 2번이 먼저 사라짐
[30s] rs=0개  sts=stateful-db-0                       ← 그다음 1번
[35s] rs=0개  sts=stateful-db-0
```

- **ReplicaSet** — 3개가 **한꺼번에** 사라진다.
- **StatefulSet** — `2` → `1` → `0`. **큰 번호부터 하나씩.**

생성의 역순이다. `0`번(주로 primary)이 **가장 마지막까지 살아 있다.**

### 정리

```bash
clear                                                               # 화면 정리 후 시작
kubectl delete rs replica-web --grace-period=1 --ignore-not-found   # ReplicaSet 삭제
kubectl delete sts stateful-db --grace-period=1 --ignore-not-found  # StatefulSet 삭제
```

## 배운 것

| | ReplicaSet | StatefulSet |
|---|---|---|
| 이름 | `<이름>-<랜덤5자>` | **`<이름>-<순번>`** |
| 생성 | 동시에 | **0부터 하나씩** |
| 삭제 | 동시에 | **큰 번호부터 하나씩** |
| Pod 구분 | 안 됨 | **번호로 구분됨** |

- StatefulSet의 Pod은 **예측 가능한 이름**을 갖는다.
- 순서를 지키는 이유는 **앞 Pod이 준비돼야 뒤 Pod이 의미가 있는** 워크로드를 위해서다.
- 삭제가 역순인 것도 같은 이유다. 0번을 마지막까지 남긴다.
