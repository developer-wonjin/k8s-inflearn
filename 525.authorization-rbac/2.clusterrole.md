# 2) ClusterRole, ClusterRoleBinding — 클러스터 전체 권한

원문 : https://cafe.naver.com/kubeops/525 (2. ClusterRole, ClusterRoleBinding)

`Role`은 자기 네임스페이스 안에서만 통한다.
`ClusterRole`은 **모든 네임스페이스**에 통하고, **네임스페이스에 속하지 않는 자원**도 다룰 수 있다.

| | Role | ClusterRole |
|---|---|---|
| 유효 범위 | 한 네임스페이스 | **클러스터 전체** |
| `nodes`, `persistentvolumes` 같은 자원 | **불가** (네임스페이스 자원이 아니다) | 가능 |
| 짝이 되는 Binding | RoleBinding | ClusterRoleBinding |

## 왜 필요한가

### 없으면 이렇게 된다

[1. Role, RoleBinding](1.role-rolebinding.md)으로 네임스페이스 안의 권한은 해결됐다.
그런데 `Role`로는 아예 표현할 수 없는 것이 있다.

| 하고 싶은 것 | Role로는 |
|---|---|
| **모든** 네임스페이스의 Pod을 조회 | 네임스페이스마다 Role을 하나씩 만들어야 한다 |
| **노드** 목록 조회 | **불가능.** 노드는 네임스페이스에 속하지 않는다 |
| **PersistentVolume** 관리 | **불가능.** 같은 이유 |

노드와 PV처럼 **클러스터 전체에 하나뿐인 자원**은 어느 네임스페이스에도 속하지 않는다.
네임스페이스 안에서만 유효한 Role로는 손댈 방법이 없다.

### ClusterRole이 넓히는 범위

| | Role | ClusterRole |
|---|---|---|
| 유효 범위 | 한 네임스페이스 | **클러스터 전체** |
| `nodes`, `persistentvolumes` | **불가** | 가능 |
| 짝이 되는 Binding | RoleBinding | ClusterRoleBinding |

여기서 알아둘 조합이 하나 있다. **ClusterRole을 RoleBinding으로 묶을 수 있다.**
그러면 역할 정의는 한 번만 해두고 **적용 범위만 네임스페이스로 좁혀** 쓸 수 있다.
"Pod 읽기" 같은 공통 역할을 팀마다 재사용하는 방식이다.

실제로 쿠버네티스에는 `view`, `edit`, `admin`, `cluster-admin` 같은
**내장 ClusterRole**이 이미 들어 있다. 대부분의 경우 직접 만들 필요가 없다.

> `apiGroups`·`verbs`·`resources`를 전부 `*`로 두면 사실상 관리자다.
> 편하다고 그렇게 두면 RBAC을 쓰는 의미가 없어진다.

### 이 문서에서 확인할 것

- 노드 조회 권한을 Role로 만들 수 있는가 (2절)
- ClusterRole을 RoleBinding으로 묶으면 범위가 어떻게 되는가 (3절)
- 이미 들어 있는 내장 ClusterRole에는 무엇이 있는가 (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> `nm-02`와 ClusterRole은 default 밖이거나 클러스터 범위라 지워지지 않는다.

## YAML

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: sa-02
  namespace: nm-02
---
apiVersion: v1
kind: Secret
metadata:
  namespace: nm-02
  name: sa-02-token
  annotations:
    kubernetes.io/service-account.name: sa-02  # 이 SA 의 토큰
type: kubernetes.io/service-account-token
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole                              # namespace 필드가 없다
metadata:
  name: cr-02
rules:
- apiGroups: ["*"]                             # 모든 API 그룹
  verbs: ["*"]                                 # 모든 동작
  resources: ["*"]                             # 모든 리소스
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding                       # 이것도 namespace 가 없다
metadata:
  name: rb-02
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cr-02
subjects:
- kind: ServiceAccount
  name: sa-02
  namespace: nm-02                             # Subject 는 네임스페이스를 갖는다
```

> `*` 세 개는 **사실상 클러스터 관리자 권한**이다. 실습이라 이렇게 했을 뿐,
> 실무에서는 필요한 것만 나열해야 한다.

## 실습 과정

### 1. 두 토큰을 나란히 비교한다

```bash
clear                                                                                  # 화면 정리 후 시작
kubectl apply -f - <<'END'                                                             # nm-02, sa-02, ClusterRole, ClusterRoleBinding 생성
# ... 위 YAML 전체 ...
END

T2=$(kubectl get secret sa-02-token -n nm-02 -o jsonpath='{.data.token}' | base64 -d)  # sa-02 토큰
TOKEN=$(kubectl get secret nm-01 -n nm-01 -o jsonpath='{.data.token}' | base64 -d)     # nm-01 default 토큰
```

같은 엔드포인트들을 두 토큰으로 각각 호출한다.

```bash
clear  # 화면 정리 후 시작
# sa-02 (ClusterRole *) 로 호출
for p in "namespaces/nm-01/pods" "namespaces/nm-01/services" "namespaces/nm-02/pods" "nodes"; do
  echo -n "  /api/v1/$p → "
  curl -sk -o /dev/null -w 'HTTP %{http_code}\n' \
    "https://192.168.56.30:6443/api/v1/$p" -H "Authorization: Bearer $T2"
done
```

```
  /api/v1/namespaces/nm-01/pods     → HTTP 200
  /api/v1/namespaces/nm-01/services → HTTP 200
  /api/v1/namespaces/nm-02/pods     → HTTP 200
  /api/v1/nodes                     → HTTP 200
```

**전부 통과한다.** 자기 네임스페이스(`nm-02`)가 아닌 `nm-01`도, 클러스터 자원인 `nodes`도.

```bash
clear  # 화면 정리 후 시작
# nm-01 의 default (Role 만 있음) 로 같은 호출
for p in "namespaces/nm-01/pods" "namespaces/nm-02/pods" "nodes"; do
  echo -n "  /api/v1/$p → "
  curl -sk -o /dev/null -w 'HTTP %{http_code}\n' \
    "https://192.168.56.30:6443/api/v1/$p" -H "Authorization: Bearer $TOKEN"
done
```

```
  /api/v1/namespaces/nm-01/pods → HTTP 200      ← 자기 ns 의 pods 만
  /api/v1/namespaces/nm-02/pods → HTTP 403      ← 다른 ns 는 막힘
  /api/v1/nodes                 → HTTP 403      ← 클러스터 자원도 막힘
```

**대비가 뚜렷하다.**

| 대상 | Role (nm-01) | ClusterRole |
|---|---|---|
| `nm-01/pods` | 200 | 200 |
| `nm-01/services` | 403 | 200 |
| `nm-02/pods` | **403** | 200 |
| `nodes` | **403** | 200 |

### 2. `auth can-i` 로 확인

```bash
clear                                                                                        # 화면 정리 후 시작
kubectl auth can-i delete pods -n nm-01 --as=system:serviceaccount:nm-02:sa-02               # 다른 ns 삭제
kubectl auth can-i create deployments -n kube-system --as=system:serviceaccount:nm-02:sa-02  # 시스템 ns 에 생성
```

```
yes
yes
```

**`kube-system`에 Deployment를 만들 수도 있다.** `*` 권한의 위력이자 위험이다.

### ClusterRole을 RoleBinding에 붙일 수도 있다

자주 쓰이는 조합이다.

```yaml
kind: RoleBinding                              # 네임스페이스 단위 Binding
metadata:
  namespace: nm-01
roleRef:
  kind: ClusterRole                            # 그런데 참조는 ClusterRole
  name: view                                   # 쿠버네티스 내장 ClusterRole
```

이렇게 하면 **ClusterRole에 정의된 권한을 그 네임스페이스에서만** 갖게 된다.
`view`, `edit`, `admin` 같은 내장 ClusterRole을 재사용할 때 이 방식을 쓴다.

```bash
clear                                                  # 화면 정리 후 시작
kubectl get clusterrole view edit admin cluster-admin  # 쿠버네티스가 미리 만들어둔 것들
```

| 내장 ClusterRole | 권한 |
|---|---|
| `view` | 읽기 전용 (Secret 제외) |
| `edit` | 읽기·쓰기 (RBAC 변경은 불가) |
| `admin` | 네임스페이스 안의 모든 것 (쿼터 제외) |
| `cluster-admin` | 전부 |

직접 Role을 쓰기 전에 **이것들로 충분한지 먼저 보는 편이 낫다.**

## 배운 것

- `ClusterRole`은 **모든 네임스페이스 + 클러스터 자원**에 통한다.
- `nodes`, `persistentvolumes` 처럼 네임스페이스에 속하지 않는 자원은 **ClusterRole로만** 다룰 수 있다.
- `ClusterRoleBinding`으로 묶으면 전역, `RoleBinding`으로 묶으면 **그 네임스페이스에서만** 유효하다.
- `view`, `edit`, `admin`, `cluster-admin` 같은 **내장 ClusterRole**이 이미 있다.
- `apiGroups/verbs/resources` 를 전부 `*` 로 두면 사실상 관리자다. 실무에서는 좁혀야 한다.
