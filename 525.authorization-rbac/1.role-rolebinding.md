# 1) Role, RoleBinding — 네임스페이스 안에서의 권한

원문 : https://cafe.naver.com/kubeops/525 (1. Role, RoleBinding)

- 선행 조건 : [게시글 522](../522.authentication/3.serviceaccount.md)에서 만든
  `nm-01` 네임스페이스, `default` ServiceAccount, `nm-01` Secret, `pod-1`

522에서 토큰은 통했지만 **403**이 났다. 인증은 됐는데 권한이 없어서였다.
그 권한을 붙이는 것이 RBAC이다.

## 왜 필요한가

### 없으면 이렇게 된다

[522 3](../522.authentication/3.serviceaccount.md)에서 토큰으로 인증은 통과했다.
그런데 Pod 목록을 조회하니 **403**이 돌아왔다.

```
"pods is forbidden: User \"system:serviceaccount:nm-01:default\" cannot list resource \"pods\""
```

**"너가 누구인지는 알겠는데, 그걸 할 수 있다고는 안 했다"** 는 뜻이다.
인증(누구인가)과 인가(무엇을 할 수 있는가)는 별개의 단계다.

여기서 권한을 주는 방법이 없다면 선택지는 둘뿐이다.
아무것도 못 하게 두거나, `cluster-admin`을 줘서 **전부 할 수 있게** 하거나.
후자를 택하면 모니터링 에이전트가 노드를 지울 수 있는 상태가 된다.

### RBAC의 세 조각

RBAC은 권한을 **역할**로 정의하고 **대상**에 붙이는 방식이다.

| 조각 | 무엇을 정하나 |
|---|---|
| **Role** | **무엇을 할 수 있는가** (어떤 리소스에 어떤 동작) |
| **Subject** | **누가** (User, Group, ServiceAccount) |
| **RoleBinding** | 둘을 **연결** |

역할과 대상을 분리한 덕분에 같은 역할을 여러 사람에게 재사용할 수 있고,
사람이 바뀌어도 Binding만 고치면 된다.

권한은 **리소스 단위 + 동작 단위**로 쪼개진다.
"Pod을 볼 수는 있지만 지울 수는 없다"가 표현된다.

> `Role`은 **자기 네임스페이스 안에서만** 유효하다.
> 클러스터 전체나 노드 같은 자원은 [2. ClusterRole](2.clusterrole.md)이 필요하다.

### 이 문서에서 확인할 것

- Role만 만들고 Binding을 안 하면 어떻게 되는가 (2절)
- Binding을 붙이면 403이 사라지는가 (3절)
- 조회는 되는데 삭제는 안 되게 만들 수 있는가 (4절)
- 권한을 미리 확인해 볼 방법이 있는가 — `auth can-i` (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> 선행 조건인 522의 `nm-01`과 그 안의 RBAC 리소스는 default 밖이라 지워지지 않는다.

## 세 조각으로 나뉜다

```
Subject ──── RoleBinding ────▶ Role
(누가)        (연결)            (무엇을 할 수 있나)

ServiceAccount   rb-01          r-01
default                         pods 에 get, list
```

**권한(Role)과 대상(Subject)을 따로 정의하고 Binding으로 잇는다.**
같은 Role을 여러 Subject에 붙일 수 있어 재사용이 된다.

## YAML

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role                                     # 네임스페이스 안에서만 유효
metadata:
  name: r-01
  namespace: nm-01
rules:
- apiGroups: [""]                              # "" 는 core 그룹 (pod, service, configmap 등)
  verbs: ["get", "list"]                       # 할 수 있는 동작
  resources: ["pods"]                          # 대상 리소스
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: rb-01
  namespace: nm-01
roleRef:                                       # 어떤 Role 을
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: r-01
subjects:                                      # 누구에게
- kind: ServiceAccount
  name: default
  namespace: nm-01
```

### verbs 종류

| verb | 동작 |
|---|---|
| `get` | 하나 조회 |
| `list` | 목록 조회 |
| `watch` | 변경 감시 |
| `create` | 생성 |
| `update` / `patch` | 수정 |
| `delete` / `deletecollection` | 삭제 |
| `*` | 전부 |

`get`과 `list`는 **다르다.** `kubectl get pods`(목록)에는 `list`가,
`kubectl get pod pod-1`(하나)에는 `get`이 필요하다.

## 실습 과정

### 1. 적용 전 상태

```bash
clear                                                                               # 화면 정리 후 시작
TOKEN=$(kubectl get secret nm-01 -n nm-01 -o jsonpath='{.data.token}' | base64 -d)  # 522에서 만든 토큰

curl -sk -o /dev/null -w 'pods     HTTP %{http_code}\n' \
  https://192.168.56.30:6443/api/v1/namespaces/nm-01/pods -H "Authorization: Bearer $TOKEN"
curl -sk -o /dev/null -w 'services HTTP %{http_code}\n' \
  https://192.168.56.30:6443/api/v1/namespaces/nm-01/services -H "Authorization: Bearer $TOKEN"
```

```
pods     HTTP 403
services HTTP 403
```

둘 다 막혀 있다.

### 2. Role과 RoleBinding을 붙인다

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # Role, RoleBinding, 비교용 Service 생성
# ... r-01, rb-01, svc-1 YAML ...
END

curl -sk -o /dev/null -w 'pods     HTTP %{http_code}\n' \
  https://192.168.56.30:6443/api/v1/namespaces/nm-01/pods -H "Authorization: Bearer $TOKEN"
curl -sk -o /dev/null -w 'services HTTP %{http_code}\n' \
  https://192.168.56.30:6443/api/v1/namespaces/nm-01/services -H "Authorization: Bearer $TOKEN"
```

```
pods     HTTP 200        ← 열렸다
services HTTP 403        ← 여전히 막혀 있다
```

**Role에 적은 것만 통한다.** `resources: ["pods"]` 라고 했으니 services는 그대로 막힌다.

### 3. verb 단위로도 갈린다

`get`, `list`만 줬으므로 삭제는 안 된다.

```bash
clear  # 화면 정리 후 시작
curl -sk -X DELETE -o /dev/null -w 'DELETE pod HTTP %{http_code}\n' \
  https://192.168.56.30:6443/api/v1/namespaces/nm-01/pods/pod-1 \
  -H "Authorization: Bearer $TOKEN"
```

```
DELETE pod HTTP 403
```

**조회는 되는데 삭제는 안 된다.** 리소스 단위가 아니라 **동작 단위**로 제어된다.

### `kubectl auth can-i` — 미리 확인하기

curl로 하나씩 찔러보지 않아도 된다.

```bash
clear                                                                               # 화면 정리 후 시작
kubectl auth can-i get pods -n nm-01 --as=system:serviceaccount:nm-01:default       # 조회 가능?
kubectl auth can-i delete pods -n nm-01 --as=system:serviceaccount:nm-01:default    # 삭제 가능?
kubectl auth can-i list services -n nm-01 --as=system:serviceaccount:nm-01:default  # 서비스 조회?
```

```
yes
no
no
```

`--as` 로 **다른 사용자인 척** 물어볼 수 있다 (impersonation).
권한 설계를 검증할 때 가장 빠른 방법이다.

## 배운 것

- RBAC은 **Role(무엇을) + Subject(누가) + Binding(연결)** 세 조각이다.
- `Role`은 **자기 네임스페이스 안에서만** 유효하다.
- `apiGroups: [""]` 는 core 그룹이다. Deployment는 `["apps"]` 다.
- 권한은 **리소스 단위 + 동작(verb) 단위**로 나뉜다. 조회는 되고 삭제는 안 될 수 있다.
- `kubectl auth can-i ... --as=...` 로 미리 확인할 수 있다.
