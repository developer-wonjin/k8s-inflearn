# 2) ResourceQuota

원문 : https://cafe.naver.com/kubeops/501 (2. ResourceQuota)

**네임스페이스 전체가 쓸 수 있는 총량**을 제한한다.
한 팀이 클러스터 자원을 독차지하지 못하게 막는 용도다.

> 원문도 적었듯 *"실무에서는 관리가 힘들어서 잘 사용되진 않는다."*
> 총량을 정해두면 Pod을 늘릴 때마다 쿼터를 조정해야 해서 운영 부담이 크다.

## 왜 필요한가

### 없으면 이렇게 된다

[1. Namespace](1.namespace.md)에서 확인했듯 네임스페이스는 **노드 자원을 나누지 않는다.**
이름만 갈렸을 뿐 메모리와 CPU는 여전히 한 통에서 꺼내 쓴다.

그래서 A팀이 실수로 Pod을 100개 띄우면 **B팀 Pod이 뜨지 못한다.**
클러스터 전체가 한 팀 때문에 멈출 수 있다.

### ResourceQuota가 거는 상한

ResourceQuota는 **네임스페이스 전체가 쓸 수 있는 총량**에 뚜껑을 씌운다.

```
네임스페이스 A  ──  메모리 총 1Gi 까지, Pod 5개 까지
네임스페이스 B  ──  메모리 총 2Gi 까지
```

넘으면 **Pod이 생성 시점에 거부된다.** 떴다가 죽는 게 아니라 아예 만들어지지 않는다.

여기에 부작용이 하나 따라온다. 총량을 세려면 각 Pod이 얼마를 쓰는지 알아야 하므로,
쿼터를 거는 순간 그 네임스페이스의 **모든 Pod은 `resources`를 반드시 적어야 한다.**
안 적으면 거부된다. 이 불편함이 다음 문서([LimitRange](3.limitrange.md))의 출발점이다.

> 원문도 적었듯 **실무에서는 관리 부담 때문에 잘 쓰이지 않는다.**
> Pod을 늘릴 때마다 쿼터를 조정해야 하기 때문이다.

### 이 문서에서 확인할 것

- 쿼터를 넘기면 Pod이 **언제** 거부되는가 — 생성 시점인가 실행 중인가 (2절)
- 쿼터가 걸린 네임스페이스에서 `resources`를 안 적으면 어떻게 되는가 (3절)
- 메모리·CPU 말고 **개수**도 제한할 수 있는가 (4절)
- 이미 떠 있는 Pod에도 소급 적용되는가 (검증 절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

# 이 문서가 만드는 네임스페이스를 지운다 (안에 든 리소스도 함께 사라진다)
kubectl delete namespace \
  nm-3 \
  --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## YAML

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # rq-1 — ResourceQuota
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-1
  namespace: nm-3                              # 네임스페이스 단위로 건다
spec:
  hard:                                        # 넘을 수 없는 상한
    requests.memory: 1Gi                       # 이 ns 안 모든 Pod의 requests 합
    limits.memory: 1Gi                         # 이 ns 안 모든 Pod의 limits 합
END
```

## 실습 과정

### 1. 쿼터를 걸면 resources가 필수가 된다

```bash
clear                                    # 화면 정리 후 시작
kubectl create ns nm-3                   # 네임스페이스 생성
kubectl apply -f - <<'END'               # ResourceQuota 생성
# ... rq-1 YAML ...
END

kubectl describe resourcequotas -n nm-3  # 현재 사용량 확인
```

```
Resource         Used  Hard
--------         ----  ----
limits.memory    0     1Gi
requests.memory  0     1Gi
```

이 상태에서 **resources를 안 적은 Pod**을 만들어 본다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # resources 없는 Pod
apiVersion: v1
kind: Pod
metadata:
  name: pod-2
  namespace: nm-3
spec:
  containers:
  - name: container
    image: kubetm/app
END
```

```
Error from server (Forbidden): pods "pod-2" is forbidden: failed quota: rq-1:
  must specify limits.memory for: container; requests.memory for: container
```

**거부된다.** 총량을 계산하려면 각 Pod이 얼마를 쓰는지 알아야 하는데,
resources가 없으면 계산이 안 되기 때문이다.

> 쿼터를 거는 순간 그 네임스페이스에서는 **resources 명시가 강제**된다.
> 이게 부담이면 [LimitRange](3.limitrange.md)의 `default`로 자동으로 채워줄 수 있다.

### 2. 총량을 넘으면 거부된다

`0.5Gi` Pod을 먼저 만든다.

```bash
clear                                    # 화면 정리 후 시작
kubectl apply -f - <<'END'               # 0.5Gi Pod (성공)
# ... pod-3 (requests/limits 0.5Gi) ...
END

kubectl describe resourcequotas -n nm-3  # 사용량이 얼마로 잡혔나
```

```
pod/pod-3 created

Resource         Used   Hard
limits.memory    512Mi  1Gi
requests.memory  512Mi  1Gi
```

이제 `0.8Gi` Pod을 추가하면 합계가 `1.3Gi`가 되어 `1Gi`를 넘는다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # 0.8Gi Pod (실패해야 정상)
# ... pod-4 (requests/limits 0.8Gi) ...
END
```

```
Error from server (Forbidden): pods "pod-4" is forbidden: exceeded quota: rq-1,
  requested: limits.memory=858993459200m, requests.memory=858993459200m,
  used:      limits.memory=512Mi,         requests.memory=512Mi,
  limited:   limits.memory=1Gi,           requests.memory=1Gi
```

메시지가 **요청량 / 이미 쓴 양 / 상한**을 모두 보여준다. 쿼터 관련 실패는 이 세 값을 보면 된다.

> `858993459200m` 은 `0.8Gi` 를 밀리 단위로 표현한 값이다.
> `0.8Gi` 처럼 소수점으로 쓰면 `fractional byte value ... is invalid` 경고가 함께 뜬다.
> `819Mi` 처럼 정수로 쓰는 편이 낫다 (게시글 497에서 확인한 것과 같은 현상).

### 3. 개수도 제한할 수 있다

메모리 총량만이 아니라 **오브젝트 개수**도 제한 대상이다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # Pod 개수를 2개로 제한
apiVersion: v1
kind: ResourceQuota
metadata:
  name: rq-2
  namespace: nm-3
spec:
  hard:
    pods: 2
END
```

이미 `pod-3` 하나가 있으므로 하나 더는 되고, 그다음은 막힌다.

```bash
clear                                         # 화면 정리 후 시작
kubectl apply -f - <<'END'                    # 2개째 (성공)
# ... pod-4 (100Mi) ...
END
kubectl apply -f - <<'END'                    # 3개째 (실패해야 정상)
# ... pod-5 (100Mi) ...
END
kubectl describe resourcequotas rq-2 -n nm-3  # 개수 확인
```

```
pod/pod-4 created

Error from server (Forbidden): pods "pod-5" is forbidden: exceeded quota: rq-2,
  requested: pods=1, used: pods=2, limited: pods=2

Resource  Used  Hard
pods      2     2
```

`pods` 외에도 `services`, `configmaps`, `persistentvolumeclaims`,
`services.nodeports`, `count/deployments.apps` 등을 제한할 수 있다.

### 정리

```bash
clear                   # 화면 정리 후 시작
kubectl delete ns nm-3  # 네임스페이스째 삭제하면 쿼터와 Pod이 함께 사라진다
```

## 배운 것

- ResourceQuota는 **네임스페이스 전체의 총량**을 제한한다.
- 쿼터를 거는 순간 그 네임스페이스의 Pod은 **resources 명시가 필수**가 된다.
- 위반하면 Pod이 **생성 시점에 거부**된다. 뜬 다음 죽는 게 아니다.
- 실패 메시지에 `requested / used / limited` 세 값이 다 나온다.
- 메모리·CPU만이 아니라 **오브젝트 개수**도 제한할 수 있다.
- **이미 떠 있는 Pod에는 소급 적용되지 않는다.** 쿼터를 나중에 걸면
  resources 없는 기존 Pod은 그대로 남고, 그때부터 총량 계산이 어긋난다.
