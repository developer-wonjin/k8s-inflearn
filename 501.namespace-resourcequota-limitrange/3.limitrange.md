# 3) LimitRange

원문 : https://cafe.naver.com/kubeops/501 (3. LimitRange)

ResourceQuota가 **네임스페이스 총량**을 본다면,
LimitRange는 **Pod(컨테이너) 하나하나**가 지켜야 할 범위를 정한다.

두 가지 일을 한다.

1. **검사** — 범위를 벗어난 Pod은 생성을 거부한다
2. **기본값 주입** — resources를 안 적은 Pod에 자동으로 채워준다

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

# 이 문서가 만드는 네임스페이스를 지운다 (안에 든 리소스도 함께 사라진다)
kubectl delete namespace \
  nm-5 \
  --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## YAML

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: lr-1
  namespace: nm-5
spec:
  limits:
  - type: Container                            # 컨테이너 단위로 적용 (Pod, PVC 도 가능)
    min:
      memory: 0.1Gi                            # 이보다 적게 요청할 수 없다
    max:
      memory: 0.4Gi                            # 이보다 많이 쓸 수 없다
    maxLimitRequestRatio:
      memory: 3                                # limits / requests 가 3배를 넘을 수 없다
    defaultRequest:
      memory: 0.1Gi                            # requests 를 안 적으면 이 값
    default:
      memory: 0.2Gi                            # limits 를 안 적으면 이 값
```

`maxLimitRequestRatio`가 있는 이유는 이렇다. `requests`는 예약이고 `limits`는 상한이라,
둘의 차이가 크면 **노드가 실제로는 감당 못 할 만큼 오버커밋**된다.
이 비율을 묶어두면 그 격차를 제한할 수 있다.

## 실습 과정

### 1. 설정 확인

```bash
clear                                 # 화면 정리 후 시작
kubectl create ns nm-5                # 네임스페이스 생성
kubectl apply -f - <<'END'            # LimitRange 생성
# ... lr-1 YAML ...
END

kubectl describe limitranges -n nm-5  # 적용된 값 확인
```

```
Type        Resource  Min            Max            Default Request  Default Limit  Max Limit/Request Ratio
Container   memory    107374182400m  429496729600m  107374182400m    214748364800m  3
```

`0.1Gi`가 `107374182400m`으로 표시된다. 소수점 표기가 밀리 단위로 바뀐 것이라 읽기 나쁘다.
**`100Mi`, `400Mi`처럼 정수로 쓰면** 그대로 보인다.

### 2. 범위를 벗어나면 거부된다

`requests: 0.1Gi` / `limits: 0.5Gi` 로 만들어 본다. 두 가지를 동시에 위반한다.

- `limits 0.5Gi` > `max 0.4Gi`
- 비율이 `0.5 / 0.1 = 5` > `maxLimitRequestRatio 3`

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # 범위를 벗어난 Pod (실패해야 정상)
# ... pod-1 (requests 0.1Gi / limits 0.5Gi) ...
END
```

```
Error from server (Forbidden): pods "pod-1" is forbidden:
  [maximum memory usage per Container is 429496729600m, but limit is 512Mi,
   memory max limit to request ratio per Container is 3, but provided ratio is 5.000000]
```

**위반한 항목을 전부 나열해준다.** 하나씩 고치며 재시도할 필요가 없다.

범위 안으로 바꾸면 통과한다 (`requests 0.2Gi` / `limits 0.4Gi` → 비율 2).

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # 범위 안의 Pod (성공)
# ... pod-1 (requests 0.2Gi / limits 0.4Gi) ...
END
```

```
pod/pod-1 created
```

### 3. resources를 안 쓰면 기본값이 채워진다

```bash
clear                                                                # 화면 정리 후 시작
kubectl apply -f - <<'END'                                           # resources 를 아예 안 쓴 Pod
apiVersion: v1
kind: Pod
metadata:
  name: pod-2
  namespace: nm-5
spec:
  containers:
  - name: container
    image: kubetm/app
END

kubectl wait --for=condition=Ready pod/pod-2 -n nm-5 --timeout=120s  # 뜰 때까지 대기
# 실제로 들어간 값을 확인한다 — yaml 에는 안 적었다
kubectl get pod pod-2 -n nm-5 -o jsonpath='requests={.spec.containers[0].resources.requests.memory} limits={.spec.containers[0].resources.limits.memory}'
```

```
requests=107374182400m  limits=214748364800m
```

`defaultRequest: 0.1Gi`와 `default: 0.2Gi`가 **자동으로 들어갔다.**
사용자는 아무것도 안 적었는데 Pod에는 값이 채워져 있다.

이것이 ResourceQuota와 잘 맞는 지점이다.

> ResourceQuota를 걸면 resources 명시가 강제되어 번거로워진다.
> 같은 네임스페이스에 LimitRange를 함께 걸어두면 **기본값이 자동으로 채워져서**
> 사용자는 resources를 안 적어도 되고, 쿼터 계산도 정상 동작한다.
> **둘은 짝으로 쓰는 것이 자연스럽다.**

### 정리

```bash
clear                   # 화면 정리 후 시작
kubectl delete ns nm-5  # 네임스페이스째 삭제
```

## 배운 것

- LimitRange는 **컨테이너 하나하나**의 범위를 정한다 (총량은 ResourceQuota).
- `min`/`max`를 벗어나면 생성이 거부되고, **위반 항목이 전부 나열**된다.
- `maxLimitRequestRatio`는 requests와 limits의 격차를 제한해 과도한 오버커밋을 막는다.
- `default`/`defaultRequest`는 **resources를 안 적은 Pod에 자동으로 채워준다.**
- ResourceQuota와 함께 쓰면 "총량은 제한하되 사용자는 편하게"가 된다.
- `0.1Gi` 같은 소수점 표기는 `107374182400m`으로 보여 읽기 나쁘다. `100Mi`를 쓴다.
