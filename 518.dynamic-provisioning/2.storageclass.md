# 2) StorageClass — PVC가 PV를 찾는 세 가지 방식

원문 : https://cafe.naver.com/kubeops/518 (2. Dynamic Provisioning)

PVC의 `storageClassName` 을 어떻게 쓰느냐에 따라 동작이 완전히 달라진다.

| 값 | 뜻 |
|---|---|
| `storageClassName: ""` | StorageClass를 **쓰지 않는다.** 미리 만들어둔 PV를 찾는다 (정적) |
| `storageClassName: "fast"` | 그 StorageClass의 프로비저너가 **PV를 새로 만든다** (동적) |
| **생략** | **default StorageClass**가 자동 적용된다 |

## 왜 필요한가

### 없으면 이렇게 된다

[1. Longhorn 구축](1.longhorn.md)으로 프로비저너는 준비됐다.
그런데 PVC를 쓰는 쪽에서 보면 **헷갈리는 지점**이 생긴다.

`storageClassName`을 어떻게 쓰느냐에 따라 **동작이 완전히 달라지는데**,
겉보기엔 차이가 작다. 특히 **빈 문자열과 생략은 전혀 다르다.**

```yaml
storageClassName: ""     # 정적 — 미리 만든 PV 를 찾는다
# storageClassName 없음  # 동적 — default StorageClass 가 끼어든다
```

이걸 모르면 "왜 PV를 만들어뒀는데 안 붙지" 또는
"왜 만든 적 없는 PV가 생겼지" 같은 데서 막힌다.

### 세 가지 방식

| 값 | 뜻 | 결과 |
|---|---|---|
| `storageClassName: ""` | 클래스를 **쓰지 않겠다** | 미리 만든 PV를 찾는다 (정적) |
| `storageClassName: "fast"` | 그 클래스를 쓰겠다 | 프로비저너가 **PV를 새로 만든다** (동적) |
| **생략** | 아무 말 안 함 | **default StorageClass가 자동 적용** |

세 번째가 함정이다. 아무 말도 안 했을 뿐인데 클러스터 설정에 따라
동작이 달라진다. **default가 있는 클러스터와 없는 클러스터에서 같은 YAML이
다르게 동작한다.**

그래서 `kubectl get sc`로 **`(default)` 표시를 먼저 확인하는 습관**이 필요하다.

### 이 문서에서 확인할 것

- `""`와 생략이 실제로 어떻게 다른가 (2절, 3절)
- 동적으로 만들어진 PV의 이름과 속성은 어떻게 정해지는가 (3절)
- default가 없는 클러스터에서 생략하면 어떻게 되는가 (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

# 이 문서는 PVC도 만든다 — 함께 비운다 (PV는 클러스터 범위라 문서 안에서 따로 다룬다)
kubectl delete pvc --all -n default --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> `longhorn-system` 네임스페이스와 `fast` StorageClass는 건드리지 않는다.

## 실습 범위

> `"fast"` 를 쓰는 2-3절은 **Longhorn이 필요해 실습하지 못했다** ([1번 문서](1.longhorn.md) 참고).
> `""` 와 생략은 Longhorn 없이 확인할 수 있어 실습했고, **원문과 다른 결과**가 나왔다.

## 2-1) 비교용 PV 두 개

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pv-hostpath1 — 1G / ReadWriteOnce
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-hostpath1
spec:
  capacity:
    storage: 1G
  accessModes:
  - ReadWriteOnce
  hostPath:                                    # storageClassName 이 없다 = 클래스 없음
    path: /mnt/hostpath
    type: DirectoryOrCreate
END
```

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pv-hostpath2 — 2G / ReadWriteOnce
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-hostpath2
spec:
  capacity:
    storage: 2G                                # 용량만 다르다
  accessModes:
  - ReadWriteOnce
  hostPath:
    path: /mnt/hostpath
    type: DirectoryOrCreate
END
```

```bash
clear                       # 화면 정리 후 시작
kubectl get sc              # 이 클러스터에 StorageClass 가 있는가
kubectl apply -f - <<'END'  # PV 2개 생성
# ... pv-hostpath1, pv-hostpath2 YAML ...
END
kubectl get pv              # 상태 확인
```

```
No resources found                             ← StorageClass 가 하나도 없다

NAME           CAPACITY   RECLAIM POLICY   STATUS    STORAGECLASS
pv-hostpath1   1G         Retain           Pending
pv-hostpath2   2G         Retain           Pending
```

`STORAGECLASS` 칸이 비어 있다. **클래스 없는 PV**다.

## 2-2) `storageClassName: ""` — 정적 바인딩

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pvc-hostpath1 — 1G / ReadWriteOnce
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-hostpath1
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 1G
  storageClassName: ""                         # 빈 문자열 = 클래스를 쓰지 않겠다
END
```

## 2-4) `storageClassName` 생략

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pvc-default1 — 2G / ReadWriteOnce
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-default1
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 2G
                                               # storageClassName 이 아예 없다
END
```

## 검증: 생략하면 어떻게 되는가

원문은 *"PVC 생성시 storageClassName를 생략하면 Default로 설정된 StorageClass가 추가된다"* 고 적고 있다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # 두 PVC 를 한 번에 생성
# ... pvc-hostpath1(""), pvc-default1(생략) YAML ...
END
kubectl get pvc,pv          # 결과
```

```
NAME            STATUS   VOLUME         CAPACITY   STORAGECLASS
pvc-default1    Bound    pv-hostpath2   2G                        ← 생략했는데 정적 바인딩됐다
pvc-hostpath1   Bound    pv-hostpath1   1G

NAME           STATUS   CLAIM
pv-hostpath1   Bound    default/pvc-hostpath1
pv-hostpath2   Bound    default/pvc-default1
```

**둘 다 정적으로 붙었다.** `pvc-default1` 은 `storageClassName` 을 생략했는데도
동적 프로비저닝이 일어나지 않고 미리 만든 PV에 붙었다.

원인은 단순하다. **이 클러스터에 default StorageClass가 없기 때문**이다.

```
default StorageClass 가 있으면   → 생략 = 그 클래스 사용 (동적 생성)
default StorageClass 가 없으면   → 생략 = "" 와 사실상 같음 (정적 바인딩)
```

원문의 서술은 **Longhorn을 설치해 `longhorn (default)` 가 등록된 상태**를 전제한 것이다.

> 실무에서 이 차이가 사고로 이어진다.
> 개발 클러스터에는 default StorageClass가 있어서 PVC가 알아서 생겼는데,
> 다른 클러스터에는 없어서 **PVC가 영원히 `Pending`** 인 경우가 흔하다.
>
> ```bash
> kubectl get sc        # (default) 표시가 있는지 먼저 확인한다
> ```

## 정리

```bash
clear  # 화면 정리 후 시작
kubectl delete pvc \
  pvc-hostpath1 \
  pvc-default1 \
  --ignore-not-found

kubectl delete pv \
  pv-hostpath1 \
  pv-hostpath2 \
  --ignore-not-found
```

## 배운 것

- `storageClassName: ""` 는 **"클래스를 쓰지 않겠다"** 는 명시적 선언이다. 정적 PV를 찾는다.
- `storageClassName: "fast"` 는 그 클래스의 프로비저너가 **PV를 새로 만든다.**
- **생략은 default StorageClass에 의존한다.** 없으면 `""` 처럼 동작한다.
- `kubectl get sc` 로 **`(default)` 표시가 있는지** 먼저 확인하는 습관이 필요하다.
