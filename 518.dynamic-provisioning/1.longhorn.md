# 1) Longhorn 구축

원문 : https://cafe.naver.com/kubeops/518 (1. Longhorn 구축)

> ## 실습했고, 클러스터가 멈췄다 (2026-09-06)
>
> 처음 작성할 때는 iscsi 미설치를 이유로 절차만 정리해 뒀다.
> 이후 실제로 진행해 **Longhorn v1.5.0 설치까지는 성공**했으나,
> 설치 2분 뒤 master 노드가 리소스 고갈로 멈추면서 apiserver가 먹통이 됐다.
>
> - 원인·조사 과정·조치 : [부록) 마스터 리소스 고갈](../부록%29%20트러블슈팅/마스터-리소스-고갈-apiserver-먹통.md)
> - **2절(StorageClass) 이후로 넘어가기 전에 위 문서의 조치를 먼저 적용할 것.**
>   현재 master 여유 메모리가 약 1.2GiB뿐이라 볼륨을 attach하면 재발한다.

## 왜 필요한가

### 없으면 이렇게 된다

[499 3. PV/PVC](../499.volume-emptydir-hostpath-pv-pvc/3.pv-pvc.md)에서는 **PV를 사람이 미리 만들었다.**
이것을 정적 프로비저닝이라고 한다. 실습에서는 편했지만 운영에서는 세 가지가 걸린다.

| 문제 | 499에서 실제로 확인한 것 |
|---|---|
| **용량이 안 맞는다** | 1G를 요청한 PVC가 **2G PV를 통째로 차지**했다 |
| **미리 만들어야 한다** | 맞는 PV가 없으면 PVC는 `Pending` 으로 남았다 |
| **노드에 묶인다** | `local`·`hostPath` PV는 **그 노드에서만** 쓸 수 있다 |

결국 관리자가 PVC 요청이 올 때마다 손으로 PV를 만드는 상황이 된다.

### 동적 프로비저닝이 바꾸는 순서

**PVC가 생기는 순간 PV를 자동으로 만든다.** 미리 준비할 필요가 없다.

```
정적 :  관리자가 PV 생성  →  PVC 생성  →  둘이 짝지어짐
동적 :  PVC 생성          →  프로비저너가 PV를 즉시 생성
```

그 일을 해주는 주체가 **프로비저너**이고, 어떤 프로비저너를 쓸지 정하는 것이
**StorageClass**다. 쿠버네티스 자체에는 프로비저너가 없으므로
**스토리지 솔루션을 따로 설치해야 한다.** 이 문서가 그 설치를 다룬다.

Longhorn을 고른 이유는 베어메탈에서 쓸 수 있고, 여러 노드에 **복제본을 두어**
위 세 번째 문제(노드 종속)까지 푸는 On-Prem 솔루션이기 때문이다.

### 이 문서에서 확인할 것

- Longhorn이 왜 모든 노드에 iscsi 패키지를 요구하는가 (2절)
- 설치하면 StorageClass가 자동으로 생기는가 (4절)
- `(default)` 표시는 무엇을 뜻하는가 (4절)
- 이 클러스터에서 실제로 무슨 일이 벌어졌는가 (위 경고 참고)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> `longhorn-system` 네임스페이스와 `fast` StorageClass는 건드리지 않는다.

## 1-1) 모든 노드에 iscsi 설치

**master, worker1, worker2 각각에서** 실행한다.

```bash
clear                                                                       # 화면 정리 후 시작
yum --setopt=tsflags=noscripts install -y iscsi-initiator-utils             # 패키지 설치
echo "InitiatorName=$(/sbin/iscsi-iname)" > /etc/iscsi/initiatorname.iscsi  # 고유 이니시에이터 이름 생성
systemctl enable iscsid                                                     # 부팅 시 자동 시작
systemctl start iscsid                                                      # 지금 시작
systemctl is-active iscsid                                                  # active 확인
```

> Longhorn은 블록 스토리지를 iSCSI로 각 노드에 붙인다.
> 그래서 **모든 노드**에 이니시에이터가 있어야 한다. 하나라도 빠지면 그 노드에서 볼륨이 안 붙는다.

## 1-2) Longhorn 설치

```bash
clear                               # 화면 정리 후 시작
kubectl apply -f https://raw.githubusercontent.com/kubetm/kubetm.github.io/master/yamls/longhorn/longhorn-1.5.0.yaml

# 실습 환경이라 replica 를 1로 줄인다 (자원 절약)
kubectl scale deploy -n longhorn-system csi-attacher --replicas=1
kubectl scale deploy -n longhorn-system csi-provisioner --replicas=1
kubectl scale deploy -n longhorn-system csi-resizer --replicas=1
kubectl scale deploy -n longhorn-system csi-snapshotter --replicas=1
kubectl scale deploy -n longhorn-system longhorn-ui --replicas=1

kubectl get all -n longhorn-system  # 전부 Running 이 될 때까지 기다린다
```

## 1-4) fast StorageClass 추가

Longhorn을 설치하면 `longhorn` StorageClass가 **기본(default)** 으로 등록된다.
실습용으로 하나 더 만든다.

```bash
clear           # 화면 정리 후 시작
kubectl apply -f - <<'END'
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: driver.longhorn.io                # 이 프로비저너가 PV 를 만들어준다
parameters:
  dataLocality: disabled
  fromBackup: ""
  fsType: ext4
  numberOfReplicas: "3"                        # 복제본 3벌
  staleReplicaTimeout: "30"
END

kubectl get sc  # 등록 확인
```

```
NAME                 PROVISIONER          RECLAIMPOLICY   VOLUMEBINDINGMODE   ALLOWVOLUMEEXPANSION
fast                 driver.longhorn.io   Delete          Immediate           false
longhorn (default)   driver.longhorn.io   Delete          Immediate           true
```

`longhorn` 옆의 **`(default)`** 표시가 중요하다.
PVC에서 `storageClassName` 을 **생략하면 이것이 자동으로 적용된다** ([2번 문서](2.storageclass.md) 참고).

## 설치하지 않고 넘어가려면

이 저장소의 [게시글 528(StatefulSet)](../528.statefulset/README.md) 에서는
Longhorn 대신 **`fast` StorageClass와 PV를 수동으로 만들어** 정적 바인딩으로 대체했다.
동적 프로비저닝만 빠지고 나머지 동작은 같게 관찰된다.

## 배운 것 (개념)

- 정적 프로비저닝은 **PV를 사람이 미리 만든다.** 용량이 안 맞고 노드에 묶인다.
- 동적 프로비저닝은 **PVC가 생길 때 PV를 자동 생성**한다. 프로비저너가 그 일을 한다.
- Longhorn은 iSCSI 기반이라 **모든 노드에 iscsi 패키지**가 필요하다.
- StorageClass 하나를 **default** 로 지정할 수 있다.
