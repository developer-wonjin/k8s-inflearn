# 3) PV Status와 ReclaimPolicy

원문 : https://cafe.naver.com/kubeops/518 (3. PV Status, ReclaimPolicy)

PV는 생애 동안 상태가 바뀐다. **`Released` 가 함정이다.**

## 왜 필요한가

### 없으면 이렇게 된다

PVC를 지웠다. 그럼 PV는 어떻게 되는가?

**이 질문의 답을 모르면 둘 중 하나를 겪는다.**

| 오해 | 실제로 벌어지는 일 |
|---|---|
| "PV가 다시 비니까 재사용되겠지" | `Released`로 남아 **아무도 못 쓴다.** 조건이 같은 PVC도 거부된다 |
| "PV는 남으니 데이터도 안전하겠지" | `Delete` 정책이면 **PV와 실제 볼륨까지 사라진다** |

[499 3](../499.volume-emptydir-hostpath-pv-pvc/3.pv-pvc.md)에서 `Released` PV가
재사용되지 않는 것은 이미 확인했다. 이 문서는 **왜 그렇게 설계됐는지**와
**정책에 따라 어떻게 달라지는지**를 다룬다.

### 상태와 정책

PV는 생애 동안 상태가 바뀐다.

```
Available  ──PVC가 붙음──▶  Bound  ──PVC 삭제──▶  Released
 (비어 있음)                 (사용 중)              (함정)
```

`Released`가 `Available`로 돌아가지 않는 이유는 **데이터가 남아 있기 때문**이다.
그대로 다음 사람에게 넘기면 **이전 사용자의 데이터가 그대로 보인다.**
그래서 일부러 막아 둔 것이다.

그 다음 처리를 정하는 것이 **ReclaimPolicy**다.

| 정책 | PVC를 지우면 | 기본값인 경우 |
|---|---|---|
| `Retain` | PV가 `Released`로 남는다. 데이터도 남는다 | 수동 생성 PV |
| `Delete` | **PV와 실제 볼륨까지 삭제** | StorageClass로 만든 PV |

동적 프로비저닝의 기본이 `Delete`라는 점이 중요하다.
**PVC 하나 지웠을 뿐인데 데이터가 영구히 사라질 수 있다.**

### 이 문서에서 확인할 것

- `Released` PV에 조건이 같은 PVC를 붙이면 어떻게 되는가 (2절)
- `Retain`에서 그 PV를 다시 쓰려면 무엇을 해야 하는가 (3절)
- `Delete` 정책에서 PVC를 지우면 실제 볼륨까지 사라지는가 (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

# 이 문서는 PVC도 만든다 — 함께 비운다 (PV는 클러스터 범위라 문서 안에서 따로 다룬다)
kubectl delete pvc --all -n default --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> `longhorn-system` 네임스페이스와 `fast` StorageClass는 건드리지 않는다.

## PV Status

| 상태 | 의미 |
|---|---|
| `Available` | 만들어졌고 아직 아무도 안 쓴다 |
| `Bound` | PVC와 연결됨 |
| **`Released`** | **PVC가 삭제됨. 데이터는 남아 있지만 재사용 불가** |
| `Failed` | 실제 볼륨과의 연결이 끊김 |

## ReclaimPolicy

| 정책 | PVC를 지우면 |
|---|---|
| `Retain` (수동 생성 시 기본) | 데이터 보존, **`Released` 로 남음. 수동 정리 필요** |
| `Delete` (StorageClass 사용 시 기본) | PV와 실제 볼륨까지 **함께 삭제** |

## 실습 과정

### 1. Bound 상태에서 파일을 만든다

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pod-hostpath1 — Pod
apiVersion: v1
kind: Pod
metadata:
  name: pod-hostpath1
spec:
  nodeSelector:
    kubernetes.io/hostname: k8s-worker1        # hostPath 라 노드를 고정한다
  terminationGracePeriodSeconds: 0
  containers:
  - name: container
    image: kubetm/init
    volumeMounts:
    - name: hostpath
      mountPath: /mount1
  volumes:
  - name: hostpath
    persistentVolumeClaim:
      claimName: pvc-hostpath1                 # 2번 문서에서 만든 PVC
END
```

```bash
clear                                                                        # 화면 정리 후 시작
kubectl apply -f - <<'END'                                                   # Pod 생성
# ... pod-hostpath1 YAML ...
END

kubectl wait --for=condition=Ready pod/pod-hostpath1 --timeout=180s          # 대기
kubectl exec pod-hostpath1 -- sh -c 'touch /mount1/file.txt; ls -l /mount1'  # 파일 생성
kubectl get pv pv-hostpath1                                                  # 현재 상태
```

```
-rw-r--r--. 1 root root 0 Sep  5 14:30 file.txt

STATUS   CLAIM
Bound    default/pvc-hostpath1
```

### 2. PVC를 지우면 Released가 된다

```bash
clear                                              # 화면 정리 후 시작
kubectl delete pod pod-hostpath1 --grace-period=1  # Pod 먼저
kubectl delete pvc pvc-hostpath1                   # 그다음 PVC
kubectl get pv pv-hostpath1                        # PV 는 어떻게 됐나
```

```
STATUS     CLAIM
Released   default/pvc-hostpath1
```

**`Bound` → `Released`.** 그런데 `CLAIM` 칸에 **지워진 PVC 이름이 그대로 남아 있다.**
이것이 재사용을 막는 원인이다.

### 검증: Released PV를 새 PVC가 쓸 수 있는가

같은 조건(1G, RWO, `storageClassName: ""`)의 PVC를 새로 만들어 본다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # 조건이 동일한 새 PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-retry
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 1G
  storageClassName: ""
END

kubectl get pvc pvc-retry   # 붙었는가
kubectl get pv              # PV 상태
```

```
pvc-retry:  Pending                            ← 붙지 못한다

NAME           CAPACITY   STATUS     CLAIM
pv-hostpath1   1G         Released   default/pvc-hostpath1     ← 여전히 Released
pv-hostpath2   2G         Bound      default/pvc-default1
```

**조건이 완벽히 같은데도 붙지 않는다.**

`Released` 상태의 PV는 이전 PVC의 데이터를 그대로 갖고 있다.
그것을 다른 PVC에 넘기면 **남의 데이터를 보게 되므로** 쿠버네티스가 막는 것이다.

원문의 표현이 정확하다.

> *"Released 된 상태의 PV는 재사용 하지 않습니다 = PVC 삭제는 곧 PV 삭제와 같아요"*

되살리려면 `spec.claimRef` 를 지워야 하지만, **데이터를 직접 정리한 뒤에** 해야 한다.
보통은 그냥 PV를 지우고 새로 만든다.

## 정리

```bash
clear                          # 화면 정리 후 시작
kubectl delete pvc \
  pvc-retry \
  pvc-default1 \
  --ignore-not-found

kubectl delete pv \
  pv-hostpath1 \
  pv-hostpath2 \
  --ignore-not-found

kubectl get pv,pvc -n default  # 아무것도 안 남아야 정상
```

> 노드의 `/mnt/hostpath` 디렉토리와 그 안의 파일은 남는다.
> `Retain` 정책이라 쿠버네티스가 지우지 않는다. 직접 정리해야 한다.

## 배운 것

- PV 상태는 `Available` → `Bound` → `Released` 로 흐른다.
- **`Released` 는 재사용되지 않는다.** 조건이 같은 PVC도 붙지 못한다.
- 데이터가 남아 있어 남에게 넘기면 위험하기 때문이다.
- `Retain` 정책에서는 **PVC 삭제가 사실상 PV 폐기**다.
- `Delete` 정책(StorageClass 사용 시 기본)이면 PV와 실제 볼륨까지 함께 사라진다.
