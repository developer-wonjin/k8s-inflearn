# 2) Headless Service — Pod 하나하나를 이름으로 부르기

원문 : https://cafe.naver.com/kubeops/516 (2. Headless Service)

`clusterIP: None` 을 주면 Service IP를 **아예 만들지 않는다.**

그러면 DNS가 Service IP 대신 **연결된 Pod들의 IP를 그대로** 돌려준다.
게다가 **Pod마다 개별 도메인**이 생긴다.

## 시작 전 확인

> **여기서는 정리하지 않는다.** 이 문서는 1에서 만든 **`request-pod`** 가 남아 있어야 성립한다.
> 표준 정리 블록을 돌리면 전제가 사라져 실습 자체가 되지 않는다.

| 상황 | 할 일 |
|---|---|
| 앞 문서를 막 끝내고 이어서 온 경우 | 그대로 진행한다 |
| 처음부터 다시 하는 경우 | [1.dns-clusterip.md](1.dns-clusterip.md) 를 먼저 실습하고 돌아온다 |

```bash
clear                        # 화면 정리 후 시작
kubectl get pod request-pod  # 전제가 남아 있는지 확인 — 없으면 앞 문서부터
```

## YAML

```yaml
apiVersion: v1
kind: Service
metadata:
  name: headless1
spec:
  selector:
    svc: headless
  ports:
    - port: 80
      targetPort: 8080
  clusterIP: None                              # 이 한 줄이 Headless로 만든다
---
apiVersion: v1
kind: Pod
metadata:
  name: pod4
  labels:
    svc: headless
spec:
  hostname: pod-a                              # 이 값이 도메인 앞부분이 된다 (Pod 이름이 아니다)
  subdomain: headless1                         # Service 이름과 같아야 한다
  containers:
  - name: container
    image: kubetm/app
```

`pod5`는 `hostname: pod-b`로 하나 더 만든다.

**`hostname`과 `subdomain`이 핵심이다.** 이 둘이 있어야 Pod 개별 도메인이 만들어진다.
Pod 이름(`pod4`)이 아니라 `hostname`(`pod-a`)이 도메인에 쓰인다.

## 실습 과정

### 1. Service IP가 없다

```bash
clear                                                                # 화면 정리 후 시작
kubectl apply -f - <<'END'                                           # Headless Service와 Pod 2개 생성
# ... 위 YAML 전체 ...
END

kubectl wait --for=condition=Ready pod/pod4 pod/pod5 --timeout=180s  # 둘 다 뜰 때까지
kubectl get svc clusterip1 headless1                                 # 일반 Service와 비교
```

```
NAME         TYPE        CLUSTER-IP      PORT(S)
clusterip1   ClusterIP   10.105.21.216   80/TCP
headless1    ClusterIP   None            80/TCP      ← IP 자리가 None
```

### 2. DNS가 Pod IP들을 돌려준다

```bash
clear                                           # 화면 정리 후 시작
kubectl exec request-pod -- nslookup headless1  # Service 이름으로 질의
```

```
Name:     headless1.default.svc.cluster.local
Address:  20.110.126.8                         ← pod5 의 IP
Name:     headless1.default.svc.cluster.local
Address:  20.100.194.109                       ← pod4 의 IP
```

**주소가 두 개 나온다.** 일반 Service는 하나(Service IP)만 나왔다.

| | 일반 ClusterIP | Headless |
|---|---|---|
| DNS 응답 | Service IP 하나 | **연결된 Pod IP 전부** |
| 부하 분산 | kube-proxy가 함 | **클라이언트가 알아서** |
| Pod 지정 | 불가 | **가능** |

### 3. Pod마다 개별 도메인

```bash
clear                                                 # 화면 정리 후 시작
kubectl exec request-pod -- nslookup pod-a.headless1  # 특정 Pod 조회
kubectl exec request-pod -- nslookup pod-b.headless1  # 다른 Pod 조회
```

```
Name:     pod-a.headless1.default.svc.cluster.local
Address:  20.100.194.109

Name:     pod-b.headless1.default.svc.cluster.local
Address:  20.110.126.8
```

**Pod 하나를 콕 집어 부를 수 있다.** FQDN 형식은 이렇다.

```
<hostname>.<서비스명>.<네임스페이스>.svc.cluster.local
```

```bash
clear                                                              # 화면 정리 후 시작
kubectl exec request-pod -- curl -s pod-a.headless1:8080/hostname  # pod-a 호출
kubectl exec request-pod -- curl -s pod-b.headless1:8080/hostname  # pod-b 호출
```

```
Hostname : pod-a
Hostname : pod-b
```

**매번 같은 Pod이 응답한다.** 일반 Service였다면 둘 중 아무 데나 갔을 것이다.

응답이 `pod4`가 아니라 `pod-a`인 것에 주목한다.
`spec.hostname`이 컨테이너의 실제 hostname이 되기 때문이다.

## 어디에 쓰나

**상태를 가진 애플리케이션**이다. 각 인스턴스가 서로를 구분해서 알아야 하는 경우.

- DB 클러스터 — primary와 replica가 서로를 정확히 지목해야 한다
- Kafka, ZooKeeper, Elasticsearch — 각 노드가 고유한 신원을 가진다

StatefulSet(게시글 528)이 Headless Service를 필수로 요구하는 이유가 이것이다.
StatefulSet은 `hostname`/`subdomain`을 직접 안 적어도
`<StatefulSet이름>-0`, `-1` 형태로 자동으로 만들어준다.

## 배운 것

- `clusterIP: None` 이면 Service IP가 없고, DNS가 **Pod IP들을 직접** 반환한다.
- `hostname` + `subdomain` 을 주면 **Pod마다 개별 도메인**이 생긴다.
- 도메인은 `<hostname>.<서비스명>.<네임스페이스>.svc.cluster.local` 이다.
- 부하 분산이 없다. 클라이언트가 어느 Pod에 갈지 직접 정한다.
- StatefulSet의 전제 조건이다.
