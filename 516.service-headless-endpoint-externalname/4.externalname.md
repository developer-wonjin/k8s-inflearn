# 4) ExternalName — 외부 도메인에 별명 붙이기

원문 : https://cafe.naver.com/kubeops/516 (6. ExternalName)

[Endpoint 3-3](3.endpoint.md#3-3-클러스터-밖의-ip를-붙이기)에서는 외부 **IP**를 붙였다.
ExternalName은 외부 **도메인**을 붙인다. IP가 아니라 이름을 그대로 넘긴다.

동작 방식이 전혀 다르다. **DNS 단계에서 끝난다.**

```
Pod ──"externalname1 어디야?"──▶ CoreDNS
                                   ↓ CNAME 응답
                              "raw.githubusercontent.com 로 가"
Pod ──직접 연결──▶ 외부 서버        (Service를 거치지 않는다)
```

## 왜 필요한가

### 없으면 이렇게 된다

[3. Endpoint](3.endpoint.md)에서 외부 **IP**를 Service 이름으로 감쌌다.
그런데 외부 서비스는 보통 **도메인**으로 제공된다.

IP를 직접 적으면 그 IP가 바뀌는 순간 끊긴다.
CDN이나 클라우드 서비스는 IP가 수시로 바뀌고 여러 개다.
결국 **바뀔 때마다 Endpoints를 고쳐야 한다.**

### ExternalName이 넘기는 것

ExternalName은 IP가 아니라 **이름을 그대로 넘긴다.**
CoreDNS가 CNAME으로 응답하고, **거기서 끝난다.**

```
Pod ──"externalname1 어디야?"──▶ CoreDNS
                                   ↓ CNAME 응답
                              "raw.githubusercontent.com 로 가"
Pod ──직접 연결──▶ 외부 서버        (Service를 거치지 않는다)
```

**트래픽이 Service를 통과하지 않는다는 점**이 결정적으로 다르다.
앞의 모든 Service는 kube-proxy가 패킷을 중간에서 바꿔치기했지만,
ExternalName은 **DNS 단계에서 일이 끝나고** 실제 통신은 Pod이 직접 한다.

| | Endpoints로 감싸기 | ExternalName |
|---|---|---|
| 적는 것 | **IP** | **도메인** |
| 트래픽 경로 | Service를 거친다 | **직접 간다** |
| IP가 바뀌면 | 고쳐야 한다 | **알아서 따라간다** |

실제로 어디에 쓰는지는 실습 뒤의 [왜 쓰나](#왜-쓰나) 절에서 정리한다.

### 이 문서에서 확인할 것

- DNS 조회 결과가 앞의 Service들과 어떻게 다른가 — CNAME (2절)
- `kubectl get svc`에서 ClusterIP 칸이 어떻게 나오는가 (2절)
- 실제로 외부에 접속되는가 (3절)
- 포트를 바꿔 매핑할 수 있는가 (검증 절)

## 시작 전 확인

> **여기서는 정리하지 않는다.** 이 문서는 1에서 만든 **`request-pod`** 가 남아 있어야 성립한다.
> 표준 정리 블록을 돌리면 전제가 사라져 실습 자체가 되지 않는다.

| 상황 | 할 일 |
|---|---|
| 앞 문서를 막 끝내고 이어서 온 경우 | 그대로 진행한다 |
| 처음부터 다시 하는 경우 | [1.dns-clusterip.md](1.dns-clusterip.md) 를 먼저 실습하고 돌아온다 |

```bash
clear                        # 화면 정리 후 시작
kubectl get pod request-pod  # 전제가 남아 있는지 확인 — 없으면 앞 문서부터
```

## YAML

```yaml
apiVersion: v1
kind: Service
metadata:
  name: externalname1
spec:
  type: ExternalName                           # 특별한 타입
  externalName: raw.githubusercontent.com      # 이 도메인의 별명이 된다
                                               # selector 도 ports 도 필요 없다
```

## 실습 과정

### 1. Service IP가 없다

```bash
clear                          # 화면 정리 후 시작
kubectl apply -f - <<'END'     # ExternalName Service 생성
# ... 위 YAML ...
END

kubectl get svc externalname1  # 어떻게 보이나
```

```
NAME            TYPE           CLUSTER-IP   EXTERNAL-IP                 PORT(S)
externalname1   ExternalName   <none>       raw.githubusercontent.com   <none>
```

`CLUSTER-IP`도 `PORT(S)`도 없다. **Service라기보다 DNS 별명에 가깝다.**

### 2. DNS 응답은 CNAME

```bash
clear                                               # 화면 정리 후 시작
kubectl exec request-pod -- nslookup externalname1  # DNS 질의
```

```
externalname1.default.svc.cluster.local  canonical name = raw.githubusercontent.com.
Name:  raw.githubusercontent.com
```

`canonical name` — **CNAME 레코드**다.
"그건 내 이름이 아니고 저쪽 이름이야"라고 넘겨주는 것이다.

### 검증: 그냥 호출하면 404가 난다

```bash
clear  # 화면 정리 후 시작
P='/k8s-1pro/install/refs/heads/main/container/daeku/app/app.js'
kubectl exec request-pod -- curl -sk -o /dev/null -w 'HTTP %{http_code}' "https://externalname1$P"
```

```
HTTP 404
```

**연결은 됐는데 404다.** DNS는 제대로 동작했다는 뜻이다.

원인은 HTTP `Host` 헤더다. curl은 URL에 적힌 `externalname1`을 그대로 Host 헤더에 넣는다.
GitHub 서버는 `Host: externalname1` 이라는 요청을 받고 "그런 사이트 없다"며 404를 준다.

```bash
clear  # 화면 정리 후 시작
kubectl exec request-pod -- curl -sk -o /dev/null -w 'HTTP %{http_code}' \
  "https://externalname1$P" \
  -H "Host: raw.githubusercontent.com"
```

```
HTTP 200
```

Host 헤더를 정정하니 통과한다.

> 이것은 ExternalName의 결함이 아니라 **이름 기반 가상 호스팅의 성질**이다.
> 한 IP에 여러 사이트가 얹혀 있으면 서버는 Host 헤더로 어느 사이트인지 구분한다.
> 앞의 `endpoint3`(외부 IP를 직접 붙인 방식)에서도 같은 이유로 Host 헤더가 필요했다.
>
> 실제 애플리케이션에서는 대부분 문제가 안 된다.
> DB나 내부 API처럼 **Host 헤더를 안 보는 프로토콜**에 주로 쓰기 때문이다.

## 왜 쓰나

외부 주소를 **애플리케이션 코드나 설정에서 분리**하기 위해서다.

```
[ExternalName 없이]
  Pod 설정에 db.prod.example.com 을 박아둠
  → 주소가 바뀌면 ConfigMap 수정 + Pod 재시작

[ExternalName 사용]
  Pod 설정에는 external-db 라고만 적음
  → 주소가 바뀌면 Service 하나만 수정. Pod은 그대로
```

개발/운영 환경 전환에도 쓴다. 같은 `external-db` 이름을 네임스페이스마다
다른 실제 주소로 매핑해두면 Pod 정의를 환경별로 나눌 필요가 없다.

## 세 가지 외부 연결 방식 비교

| | Endpoint에 외부 IP | ExternalName | 그냥 도메인 직접 호출 |
|---|---|---|---|
| 적는 것 | IP 주소 | 도메인 이름 | (아무것도 안 함) |
| 동작 계층 | 네트워크 (kube-proxy) | **DNS (CNAME)** | - |
| IP가 바뀌면 | **직접 고쳐야 함** | 자동으로 따라감 | 자동 |
| 주소를 한 곳에서 관리 | O | O | X |
| Host 헤더 문제 | 있음 | 있음 | 없음 |

도메인이 있으면 **ExternalName이 낫다.** IP가 바뀌어도 알아서 따라가기 때문이다.
IP밖에 없을 때만 Endpoint 방식을 쓴다.

### 정리 — 516 실습 전체

```bash
clear  # 화면 정리 후 시작
kubectl delete pod \
  pod1 \
  request-pod \
  pod4 \
  pod5 \
  pod7 \
  pod9 \
  --grace-period=1 --ignore-not-found

kubectl delete svc \
  clusterip1 \
  headless1 \
  endpoint1 \
  endpoint2 \
  endpoint3 \
  externalname1 \
  --ignore-not-found
```

## 배운 것

- `ExternalName`은 **CNAME을 돌려주는 DNS 별명**이다. Service IP도 포트도 없다.
- 트래픽이 Service를 거치지 않는다. Pod이 외부 서버에 **직접** 연결한다.
- HTTP로 호출하면 **Host 헤더가 Service 이름으로 나가** 404가 날 수 있다.
- 외부 주소를 한 곳에서 관리하기 위한 장치다. 주소가 바뀌면 Service만 고친다.
