# 네트워크 네임스페이스 공유

- 확인일 : 2026-09-05
- 환경 : Rocky Linux 8.8 / k8s v1.27.2 / containerd 1.6.21
- 관련 실습 : [497. Pod - Container](../497.pod-container-label-nodeschedule/1-1.pod-container.md)

> "같은 Pod 안의 컨테이너는 네트워크 네임스페이스를 공유한다"는 문장이
> 실제로 무엇을 의미하는지 커널 수준에서 확인한 기록.

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> `service/kubernetes`는 API 서버로 가는 기본 서비스라 `--field-selector`로 제외한다.
> 지워도 자동 재생성되지만 그 사이 통신이 끊긴다.

## 확인에 사용한 YAML

```bash
clear                          # 화면 정리 후 시작
kubectl apply -f - <<'END'     # pod-1 — Pod
apiVersion: v1                 # Pod은 core 그룹이라 그룹명 없이 버전만 적는다
kind: Pod                      # 리소스 종류
metadata:
  name: pod-1                  # Pod 이름
spec:
  containers:                  # 컨테이너 2개를 한 Pod에 넣어야 공유를 관찰할 수 있다
  - name: container1           # 첫 번째 컨테이너
    image: kubetm/p8000        # 8000 포트에 bind 하는 node 프로세스
    ports:
    - containerPort: 8000      # 문서용 메타데이터 (실제 개방은 프로세스의 bind가 결정)
  - name: container2           # 두 번째 컨테이너
    image: kubetm/p8080        # 8080 포트에 bind 하는 node 프로세스
    ports:
    - containerPort: 8080
END
```

---

## 1. 네임스페이스란

리눅스 커널이 프로세스에게 **"세상을 보는 창"을 따로 만들어주는 기능**이다.
종류가 여러 개이고 각각 다른 것을 격리한다.

| 종류 | 격리하는 것 |
|---|---|
| `net` | IP 주소, 포트, 라우팅 테이블, 방화벽 규칙 |
| `mnt` | 파일시스템(마운트 지점) |
| `pid` | 프로세스 목록 |
| `uts` | hostname |
| `ipc` | 공유 메모리, 세마포어 |

컨테이너는 마법이 아니라 **이 네임스페이스들로 격리된 그냥 프로세스**다.

## 2. Pod이 하는 일

도커 컨테이너는 보통 위 5가지를 전부 따로 갖는다.
쿠버네티스는 Pod을 만들 때 일부를 **묶는다.**

```
Pod
├── net  ─┐
├── uts  ─┼─ 컨테이너들이 같이 씀
├── ipc  ─┘
├── container1 ── mnt, pid 따로
└── container2 ── mnt, pid 따로
```

**네트워크는 하나로 묶고, 파일시스템과 프로세스는 따로 둔다.**

## 3. 실제 확인

### 3-1) 네임스페이스 식별자 비교 — 가장 직접적인 증거

네임스페이스는 커널이 부여한 고유 번호(inode)로 식별된다.
`/proc/self/ns/*` 심볼릭 링크를 읽으면 그 번호가 나온다.

```bash
clear                                                       # 화면 정리 후 시작
kubectl apply -f - <<'END'                                  # 확인용 Pod 생성 (YAML은 위 절 참고)
apiVersion: v1
kind: Pod
metadata:
  name: pod-1
spec:
  containers:
  - name: container1
    image: kubetm/p8000
    ports:
    - containerPort: 8000
  - name: container2
    image: kubetm/p8080
    ports:
    - containerPort: 8080
END

kubectl wait --for=condition=Ready pod/pod-1 --timeout=90s  # 두 컨테이너가 모두 뜰 때까지 대기

# 컨테이너별로 5가지 네임스페이스의 inode 번호를 출력한다
for c in container1 container2; do
  echo "-- $c --"                                                             # 어느 컨테이너 결과인지 구분
  kubectl exec pod-1 -c $c -- sh -c 'for n in net mnt pid uts ipc; do printf "   %-4s %s\n" "$n" "$(readlink /proc/self/ns/$n)"; done'
done
```

```
-- container1 --
   net  net:[4026532261]
   mnt  mnt:[4026532329]
   pid  pid:[4026532330]
   uts  uts:[4026532326]
   ipc  ipc:[4026532327]
-- container2 --
   net  net:[4026532261]
   mnt  mnt:[4026532331]
   pid  pid:[4026532332]
   uts  uts:[4026532326]
   ipc  ipc:[4026532327]
```

| 네임스페이스 | container1 | container2 | 결과 |
|---|---|---|---|
| **net** | `4026532261` | `4026532261` | **같음** |
| **uts** | `4026532326` | `4026532326` | **같음** |
| **ipc** | `4026532327` | `4026532327` | **같음** |
| mnt | `4026532329` | `4026532331` | 다름 |
| pid | `4026532330` | `4026532332` | 다름 |

번호가 같다는 건 비슷한 게 두 개 있는 게 아니라 **말 그대로 같은 하나**라는 뜻이다.
이 표 하나가 아래 모든 현상의 원인이다.

### 3-2) net이 같으니 → IP도 하나

```bash
clear  # 화면 정리 후 시작
for c in container1 container2; do
  echo -n "  $c: "                                                            # 컨테이너 이름 먼저 출력
  kubectl exec pod-1 -c $c -- hostname -i                                     # 컨테이너가 인식하는 자기 IP
done
```

```
  container1: 20.100.194.97
  container2: 20.100.194.97
```

Pod당 IP가 하나인 이유가 이것이다.
**IP는 컨테이너가 아니라 네트워크 네임스페이스에 붙는다.**

### 3-3) net이 같으니 → 포트 테이블도 하나

커널의 소켓 목록은 `/proc/net/tcp6`에 그대로 노출된다.
두 컨테이너에서 각각 읽어 비교한다.

```bash
clear  # 화면 정리 후 시작
for c in container1 container2; do
  echo "=== $c ==="                                                           # 구분선
  kubectl exec pod-1 -c $c -- cat /proc/net/tcp6 | head -6                    # LISTEN 소켓 목록 원본
done
```

```
=== container1 ===
  sl  local_address                         ... st ... inode
   0: 00000000000000000000000000000000:1F40 ... 0A ... 193600
   1: 00000000000000000000000000000000:1F90 ... 0A ... 193290

=== container2 ===
  sl  local_address                         ... st ... inode
   0: 00000000000000000000000000000000:1F40 ... 0A ... 193600
   1: 00000000000000000000000000000000:1F90 ... 0A ... 193290
```

읽는 법:

| 값 | 의미 |
|---|---|
| `:1F40` | 포트 `0x1F40` = **8000** (container1의 프로세스가 연 것) |
| `:1F90` | 포트 `0x1F90` = **8080** (container2의 프로세스가 연 것) |
| `st 0A` | 상태 `0x0A` = LISTEN |
| `inode 193600` | 소켓의 커널 inode |

**inode 번호까지 같다.** container1이 자기 소켓과 남의 소켓을 구분 없이 보고 있다는 뜻이다.
두 컨테이너가 비슷한 테이블을 각자 가진 게 아니라, 애초에 **테이블이 하나뿐**이다.

여기서 두 가지가 따라 나온다.

**(1) localhost 호출이 된다**

```bash
clear                                                       # 화면 정리 후 시작
kubectl exec pod-1 -c container1 -- curl -s localhost:8080  # container1에서 container2 호출
```

```
containerPort : 8080
```

네트워크를 타고 나갔다 오는 게 아니라 **처음부터 같은 로컬**이다.

**(2) 같은 포트를 쓰면 충돌한다**

포트 테이블이 하나뿐이니 먼저 잡은 쪽이 이기고 나중 쪽은 죽는다.
컨테이너 둘 다 8000을 쓰게 하면 이렇게 된다.

```
container1 ready=true   restarts=0
container2 ready=false  restarts=1   exitCode=1

  code: 'EADDRINUSE',
  port: 8000
```

Pod 생성 자체는 성공하고 **런타임에** `CrashLoopBackOff`가 된다.
자세한 검증은 [497 / 1-1](../497.pod-container-label-nodeschedule/1-1.pod-container.md) 참고.

### 3-4) uts도 같으니 → hostname도 하나

```bash
clear  # 화면 정리 후 시작
for c in container1 container2; do
  echo -n "  $c: "                                                            # 컨테이너 이름 먼저 출력
  kubectl exec pod-1 -c $c -- hostname                                        # uts 네임스페이스가 결정하는 값
done
```

```
  container1: pod-1
  container2: pod-1
```

### 3-5) 하지만 mnt는 다르니 → 파일은 안 보인다

```bash
clear                                                  # 화면 정리 후 시작
kubectl exec pod-1 -c container1 -- sh -c 'echo "container1이 만든 파일" > /tmp/mine.txt; cat /tmp/mine.txt'
kubectl exec pod-1 -c container2 -- cat /tmp/mine.txt  # 같은 경로를 다른 컨테이너에서 조회
```

```
container1: container1이 만든 파일
container2: cat: /tmp/mine.txt: No such file or directory
command terminated with exit code 1
```

파일을 주고받으려면 **볼륨을 양쪽에 마운트**해야 한다 (`emptyDir` 등).

### 3-6) pid도 다르니 → 서로의 프로세스도 안 보인다

```bash
clear  # 화면 정리 후 시작
for c in container1 container2; do
  echo -n "  $c 가 보는 PID 1: "                                              # 각자 1번 프로세스가 누구인지
  kubectl exec pod-1 -c $c -- sh -c 'cat /proc/1/cmdline | tr "\0" " "'       # cmdline은 널 구분이라 공백으로 치환
  echo
done
```

```
  container1 가 보는 PID 1: /bin/sh -c node port8000.js
  container2 가 보는 PID 1: /bin/sh -c node port8080.js
```

각자 자기가 PID 1이라고 생각한다. 서로를 못 본다.

> 필요하면 `spec.shareProcessNamespace: true`로 pid도 공유할 수 있다. 기본값은 `false`.

```bash
clear                                      # 화면 정리 후 시작
kubectl delete pod pod-1 --grace-period=1  # 확인용 Pod 삭제
```

## 4. 어떻게 이게 가능한가 — pause 컨테이너

Pod을 만들면 쿠버네티스는 **`pause`라는 아무것도 안 하는 컨테이너를 먼저** 띄운다.
이것이 네트워크 네임스페이스를 만들어 붙잡고 있고,
나머지 컨테이너는 자기 것을 만드는 대신 **pause의 것에 합류**한다.

도커 명령으로 비유하면 이렇다.

```bash
clear                                      # 화면 정리 후 시작
docker run -d --name pause ...             # 네임스페이스 주인 (실제로는 kubelet이 함)
docker run --network=container:pause app1  # 남의 네임스페이스에 합류
docker run --network=container:pause app2  # 얘도 같은 곳에 합류
```

여기서 중요한 성질이 하나 나온다.

**컨테이너가 죽었다 살아나도 Pod IP는 안 바뀐다.**
네임스페이스 주인은 pause이고, 컨테이너가 재시작해도 pause는 그대로 살아 있기 때문이다.
IP가 바뀌는 건 **Pod 자체를 삭제**해서 pause까지 죽었을 때다.

## 5. 한 줄 정리

| 질문 | 답 |
|---|---|
| 왜 Pod당 IP가 하나인가 | IP는 net 네임스페이스에 붙고, Pod 안에 그게 하나뿐이라서 |
| 왜 localhost로 통신되나 | 서로가 진짜로 같은 로컬이라서 |
| 왜 같은 포트를 못 쓰나 | 포트 테이블을 공유해서 (충돌은 런타임에 드러남) |
| 왜 hostname이 같은가 | uts도 공유해서 |
| 왜 파일은 공유가 안 되나 | mnt는 따로라서 — 볼륨이 필요 |
| 왜 프로세스가 안 보이나 | pid도 따로라서 (`shareProcessNamespace`로 바꿀 수 있음) |
| Pod이 "하나의 배포 단위"인 이유 | 네트워크를 공유할 만큼 밀접한 것들을 묶으라는 뜻 |
