# 3) Blue/Green — 통째로 갈아타기

원문 : https://cafe.naver.com/kubeops/504 (3. Blue/Green)

새 버전을 **미리 다 띄워놓고**, Service의 selector만 바꿔서 트래픽을 한 번에 옮긴다.

- Deployment의 기능이 아니다. **ReplicaSet 2개 + Service 하나**로 직접 구성한다.
- 다운타임 없음, **두 버전이 섞이지도 않음**
- 대신 교체 시점에 **자원이 2배** 필요하다

## 왜 필요한가

### 없으면 이렇게 된다

앞의 두 전략은 각각 하나씩을 포기했다.

| 전략 | 다운타임 | 두 버전 공존 |
|---|---|---|
| [Recreate](1.recreate.md) | **있다** | 없다 |
| [RollingUpdate](2.rollingupdate.md) | 없다 | **있다** |

그런데 **둘 다 피해야 하는** 경우가 있다. 서비스는 끊기면 안 되는데
DB 스키마가 바뀌어 두 버전이 동시에 돌면 데이터가 깨지는 상황이다.

### Blue/Green이 고르는 방법

새 버전을 **미리 전부 띄워 놓고**, 준비가 끝나면 트래픽을 **한 번에** 옮긴다.

```
Service ──selector: v1──▶  [v1 Pod 3개]   ← 지금 트래픽을 받는 쪽
                           [v2 Pod 3개]   ← 미리 다 떠 있음 (트래픽 없음)

        selector를 v2로 바꾸는 순간 전환 완료
```

끊김도 없고 섞이지도 않는다. 대신 **교체 시점에 자원이 2배** 든다.

여기서 중요한 점은 **이것이 쿠버네티스의 기능이 아니라는 것**이다.
`strategy: BlueGreen` 같은 건 없다. ReplicaSet 2개와 Service 하나를 두고
**Service의 selector를 바꾸는 것**이 배포 행위 전부다.
이 게시글에서 유일하게 **직접 조립하는** 방식이다.

덤으로 롤백이 즉시 끝난다. 옛 버전이 아직 살아 있으니 selector만 되돌리면 된다.

### 이 문서에서 확인할 것

- selector를 바꾸는 것만으로 트래픽이 옮겨가는가 (3절)
- 전환 순간에 끊김이나 섞임이 있는가 (3절)
- 롤백은 얼마나 걸리는가 (4절)
- 세 전략을 무엇을 기준으로 고르는가 (마지막 절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## YAML

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # replica1 — ReplicaSet (replicas 2)
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: replica1                               # Blue (현재 운영 중)
spec:
  replicas: 2
  selector:
    matchLabels:
      ver: v1                                  # 버전을 라벨로 구분한다
  template:
    metadata:
      labels:
        ver: v1
    spec:
      containers:
      - name: container
        image: kubetm/app:v1
      terminationGracePeriodSeconds: 0
END
```

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # svc-3 — Service
apiVersion: v1
kind: Service
metadata:
  name: svc-3
spec:
  selector:
    ver: v1                                    # 이 값을 바꾸는 것이 곧 배포다
  ports:
  - port: 8080
    protocol: TCP
    targetPort: 8080
END
```

`replica2`는 `ver: v2`, `image: kubetm/app:v2`로 같은 형태를 하나 더 만든다.

## 실습 과정

### 1. v2를 미리 띄운다 (트래픽은 아직 v1)

```bash
clear                                                            # 화면 정리 후 시작
kubectl apply -f - <<'END'                                       # replica1(v1) 과 svc-3 생성
# ... replica1, svc-3 YAML ...
END
kubectl wait --for=condition=Ready pod -l ver=v1 --timeout=180s  # v1 Pod 대기

kubectl apply -f - <<'END'                                       # replica2(v2) 를 미리 띄운다
# ... replica2 YAML ...
END
kubectl wait --for=condition=Ready pod -l ver=v2 --timeout=180s  # v2 Pod 대기

kubectl get rs                                                   # 두 버전이 모두 떠 있는지
IP=$(kubectl get svc svc-3 -o jsonpath='{.spec.clusterIP}')      # Service IP
curl $IP:8080/version                                            # 아직 어느 쪽이 응답하나
```

```
NAME       DESIRED   CURRENT   READY   AGE
replica1   2         2         2       4s
replica2   2         2         2       1s

Version : v1        ← v2 가 떠 있어도 트래픽은 v1 으로만 간다
```

**Pod 4개가 동시에 떠 있다.** 이것이 Blue/Green의 비용이다.
그 대신 v2를 충분히 검증한 뒤 옮길 수 있다.

### 2. selector를 바꿔 한 번에 전환

```bash
clear                                                            # 화면 정리 후 시작
# 1초 간격으로 20번 호출하며 로그를 남긴다
( for i in $(seq 1 20); do
    r=$(curl -s --max-time 1 $IP:8080/version 2>/dev/null)
    printf "  [%2ds] %s\n" $i "${r:-*** 응답 없음 ***}"
    timeout 1 tail -f /dev/null
  done ) > bg.log 2>&1 &

kubectl patch svc svc-3 -p '{"spec":{"selector":{"ver":"v2"}}}'  # selector 만 바꾼다
wait                                                             # 루프가 끝날 때까지
uniq -c -f1 bg.log                                               # 결과 확인
```

```
      1   [ 1s] Version : v1
      ...
      1   [ 5s] Version : v1
      1   [ 6s] Version : v2      ← 여기서 한 번에 넘어갔다
      ...
     11   [10s] Version : v2
```

**끊김도 없고 섞이지도 않았다.** v1에서 v2로 한 번에 넘어갔다.

```
Recreate      : v1 v1 │ (없음) │ v2 v2      끊김 O, 섞임 X, 추가자원 X
RollingUpdate : v1 v2 v1 v2 ... v2          끊김 X, 섞임 O, 추가자원 일부
Blue/Green    : v1 v1 │ v2 v2               끊김 X, 섞임 X, 추가자원 2배
```

### 3. 롤백도 selector만 되돌리면 된다

```bash
clear                                                            # 화면 정리 후 시작
kubectl patch svc svc-3 -p '{"spec":{"selector":{"ver":"v1"}}}'  # selector 를 v1 으로 되돌린다
curl $IP:8080/version                                            # 잠시 뒤 확인
```

v1 Pod을 지우지 않았으므로 **되돌리는 데 새로 띄울 필요가 없다.**
이것이 Blue/Green의 가장 큰 장점이다 — 롤백이 즉시 끝난다.

> 바꾼 직후 곧바로 호출하면 이전 버전이 한두 번 더 응답할 수 있다.
> 각 노드의 kube-proxy가 규칙을 갱신하는 데 약간의 시간이 걸리기 때문이다.

### 정리

```bash
clear                                        # 화면 정리 후 시작
kubectl delete rs \
  replica1 \
  replica2 \
  --grace-period=1 --ignore-not-found

kubectl delete svc svc-3 --ignore-not-found  # Service 삭제
```

## 배운 것

- Blue/Green은 쿠버네티스 기능이 아니라 **구성 방식**이다. Service selector를 바꾸는 것이 배포다.
- 끊김도 섞임도 없다. 대신 **자원이 2배** 든다.
- 롤백이 즉시 끝난다. 옛 버전이 아직 살아 있기 때문이다.
- 전환 직후 짧은 시간 동안은 이전 버전 응답이 섞일 수 있다 (kube-proxy 갱신 지연).
