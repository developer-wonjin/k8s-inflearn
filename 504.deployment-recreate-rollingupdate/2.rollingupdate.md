# 2) RollingUpdate — 하나씩 갈아끼우기

원문 : https://cafe.naver.com/kubeops/504 (2. RollingUpdate)

옛 Pod을 하나 내리고 새 Pod을 하나 올리는 식으로 **조금씩 교체**한다.
서비스가 끊기지 않는 대신 **두 버전이 잠시 공존**한다.

## 왜 필요한가

### 없으면 이렇게 된다

[1. Recreate](1.recreate.md)는 **전부 내린 뒤 올린다.** 실측에서 약 2초 동안
응답할 Pod이 하나도 없었다. 사용자가 쓰고 있는 서비스라면 그 2초가 그대로 장애다.

배포를 무서워하게 되면 배포 주기가 길어지고, 한 번에 바뀌는 양이 늘어
더 위험해지는 악순환이 생긴다.

### RollingUpdate가 바꾸는 순서

전부 내리는 대신 **하나씩 갈아끼운다.** 항상 누군가는 응답할 수 있는 상태로 둔다.

```
v1 v1 v1  ──▶  v1 v1 v2  ──▶  v1 v2 v2  ──▶  v2 v2 v2
               ↑ 계속 응답 가능
```

| 얻는 것 | 잃는 것 |
|---|---|
| **다운타임이 없다** | **두 버전이 잠시 공존한다** |
| 점진적이라 문제를 중간에 발견할 수 있다 | 교체 중 자원이 조금 더 든다 |

공존이 핵심 대가다. DB 스키마가 바뀌는 배포라면 옛 버전과 새 버전이 같은 DB를
동시에 보게 되므로 문제가 된다. **그럴 때는 오히려 Recreate가 안전하다.**

교체 폭과 속도는 `maxSurge`·`maxUnavailable`·`minReadySeconds`로 조절한다.

### 이 문서에서 확인할 것

- 전환 중 정말 응답 실패가 없는가 (3절)
- 두 버전이 동시에 응답하는 장면을 잡을 수 있는가 (3절)
- `maxSurge`/`maxUnavailable`가 실제 Pod 개수 변화에 어떻게 나타나는가 (4절)
- `strategy`를 생략하면 어떤 전략이 되는가 (YAML 절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## YAML

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: deployment-2
spec:
  selector:
    matchLabels:
      type: app2
  replicas: 2
  strategy:
    type: RollingUpdate                        # 기본값이라 생략해도 된다
  minReadySeconds: 10                          # 새 Pod이 Ready된 뒤 10초를 더 기다린다
  template:
    metadata:
      labels:
        type: app2
    spec:
      containers:
      - name: container
        image: kubetm/app:v1
      terminationGracePeriodSeconds: 0
---
apiVersion: v1
kind: Service
metadata:
  name: svc-2
spec:
  selector:
    type: app2
  ports:
  - port: 8080
    protocol: TCP
    targetPort: 8080
```

`minReadySeconds`는 **성급한 판단을 막는 장치**다.
컨테이너가 떴다고 앱이 준비된 건 아니다. 이 시간 동안 죽지 않아야 다음 Pod으로 넘어간다.

## 실습 과정

### 1. 교체하면서 계속 호출한다

```bash
clear                                                              # 화면 정리 후 시작
kubectl apply -f - <<'END'                                         # Deployment와 Service 생성 (YAML은 위 절 참고)
# ... 위 YAML 전체 ...
END

kubectl rollout status deploy/deployment-2 --timeout=180s          # 롤아웃 완료까지 대기
IP=$(kubectl get svc svc-2 -o jsonpath='{.spec.clusterIP}')        # Service IP를 변수에

# 1초 간격으로 45번 호출하며 로그를 남긴다
( for i in $(seq 1 45); do
    r=$(curl -s --max-time 1 $IP:8080/version 2>/dev/null)
    printf "  [%2ds] %s\n" $i "${r:-*** 응답 없음 ***}"
    timeout 1 tail -f /dev/null
  done ) > rolling.log 2>&1 &

kubectl set image deployment deployment-2 container=kubetm/app:v2  # v2 로 교체 시작
wait                                                               # 루프가 끝날 때까지
uniq -c -f1 rolling.log                                            # 연속된 같은 응답을 묶어서 본다
```

```
      1   [ 1s] Version : v1
      ...
      1   [ 7s] Version : v2      ← 새 Pod이 뜨자마자 섞이기 시작
      1   [ 8s] Version : v2
      1   [ 9s] Version : v1      ← 다시 v1
      2   [10s] Version : v1
      1   [12s] Version : v2
      6   [13s] Version : v1
      ...
      1   [44s] Version : v2
      1   [45s] Version : v1
```

두 가지가 보인다.

- **"응답 없음"이 한 번도 없다.** 다운타임 0.
- **v1과 v2가 번갈아 나온다.** 교체가 끝날 때까지 두 버전이 함께 트래픽을 받는다.

```
Recreate      : v1 v1 │ (없음) (없음) │ v2 v2       ← 끊기지만 섞이지 않음
RollingUpdate : v1 v2 v1 v1 v2 v1 v2 ... v2 v2      ← 안 끊기지만 섞임
```

### 2. 교체 속도를 정하는 값들

```bash
clear                                                                         # 화면 정리 후 시작
kubectl get deploy deployment-2 -o jsonpath='{.spec.strategy.rollingUpdate}'  # 기본값 확인
kubectl get deploy deployment-2 -o jsonpath='{.spec.minReadySeconds}'         # 대기 시간
```

```
{"maxSurge":"25%","maxUnavailable":"25%"}
10
```

| 값 | 뜻 | 기본값 |
|---|---|---|
| `maxSurge` | replicas보다 **더 띄울 수 있는** 최대치 | 25% |
| `maxUnavailable` | 동시에 **없어도 되는** 최대치 | 25% |
| `minReadySeconds` | 새 Pod이 Ready 후 버텨야 하는 시간 | 0 |

`replicas: 2`에 `maxSurge: 25%`면 올림해서 1개를 더 띄울 수 있다(최대 3개).
`maxUnavailable: 25%`면 내림해서 0개 — **항상 2개가 살아 있어야 한다.**
그래서 이 실습에서는 새 Pod을 먼저 띄우고 옛 Pod을 내리는 식으로 진행됐다.

`minReadySeconds: 10` 때문에 교체가 45초 넘게 걸렸다. 안전을 위해 일부러 느리게 만든 값이다.

### 3. 최종 상태

```bash
clear                        # 화면 정리 후 시작
kubectl get rs -l type=app2  # RS 두 개의 상태
curl $IP:8080/version        # 최종 버전
```

```
NAME                      DESIRED   CURRENT   READY   AGE
deployment-2-749f96c56c   2         2         2       2m35s     ← 새 RS (v2)
deployment-2-7cc6f9d6f4   0         0         0       3m11s     ← 옛 RS (v1)

Version : v2
```

Recreate와 마찬가지로 **새 RS로 옮겨 담고 옛 RS는 0으로 남긴다.**
교체 방식만 다를 뿐 구조는 같다.

### 정리

```bash
clear                                                                   # 화면 정리 후 시작
kubectl delete deploy deployment-2 --grace-period=1 --ignore-not-found  # Deployment 삭제
kubectl delete svc svc-2 --ignore-not-found                             # Service 삭제
```

## 배운 것

- `RollingUpdate`는 **다운타임이 없다.** 실측에서 응답 실패가 한 번도 없었다.
- 대신 **두 버전이 동시에 트래픽을 받는다.** 앱이 이를 견딜 수 있어야 한다.
  (DB 스키마가 바뀌는 배포라면 이 지점이 문제가 된다)
- `maxSurge`/`maxUnavailable`가 교체 폭을, `minReadySeconds`가 속도를 정한다.
- 기본 전략이라 `strategy`를 생략하면 RollingUpdate가 적용된다.
