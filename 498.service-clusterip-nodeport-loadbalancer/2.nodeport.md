# 2) NodePort

원문 : https://cafe.naver.com/kubeops/498 (2. NodePort)

- 선행 조건 : [1.clusterip.md](1.clusterip.md)의 `pod-1`이 떠 있어야 한다.

ClusterIP의 기능을 포함하면서, **모든 워커 노드의 같은 포트**를 열어 클러스터 밖에서 접근하게 한다.
할당 범위는 `30000~32767`이고, `nodePort`를 안 적으면 그 범위에서 자동으로 잡힌다.

## 왜 필요한가

### 없으면 이렇게 된다

[1. ClusterIP](1.clusterip.md)로 Pod의 고정 주소는 얻었다. 그런데 그 주소는
**클러스터 안에서만 쓸 수 있다.** `EXTERNAL-IP`가 `<none>`이고, 노드 밖에서
`10.x.x.x`로 접속하면 닿지 않는다.

만든 서비스를 브라우저로 열어보려면 결국 **밖에서 들어올 문**이 필요하다.

### NodePort가 여는 문

NodePort는 **모든 노드의 같은 포트 번호**를 열어 둔다.
어느 노드 IP로 들어와도 서비스에 닿는다.

```
바깥 ──▶ 192.168.56.30:30001 ┐
     ──▶ 192.168.56.31:30001 ├──▶ ClusterIP ──▶ Pod
     ──▶ 192.168.56.32:30001 ┘
```

**Pod이 없는 노드로 들어와도 된다.** 그 노드가 Pod이 있는 노드로 넘겨주기 때문이다.
이 편리함에는 대가가 있는데, 넘겨주는 과정에서 **접속자의 원래 IP가 지워진다.**
그 대가를 피하려면 `externalTrafficPolicy: Local`을 쓰는데, 이번엔 Pod이 없는 노드가
응답하지 않게 된다. 이 맞바꿈이 이 문서의 후반부 주제다.

### 이 문서에서 확인할 것

- Pod이 없는 노드의 포트로도 접속되는가 (2절)
- NodePort가 ClusterIP를 **포함**한다는 것이 출력에 어떻게 드러나는가 (2절)
- `externalTrafficPolicy: Local`로 바꾸면 무엇을 얻고 무엇을 잃는가 (4절)

## 시작 전 확인

> **여기서는 정리하지 않는다.** 이 문서는 1에서 만든 **`pod-1`** 가 남아 있어야 성립한다.
> 표준 정리 블록을 돌리면 전제가 사라져 실습 자체가 되지 않는다.

| 상황 | 할 일 |
|---|---|
| 앞 문서를 막 끝내고 이어서 온 경우 | 그대로 진행한다 |
| 처음부터 다시 하는 경우 | [1.clusterip.md](1.clusterip.md) 를 먼저 실습하고 돌아온다 |

```bash
clear                  # 화면 정리 후 시작

```

## YAML

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # svc-2 — Service (NodePort)
apiVersion: v1
kind: Service
metadata:
  name: svc-2
spec:
  selector:
    app: pod                                   # pod-1, pod-2 둘 다 이 라벨을 가진다
  ports:
  - port: 9000                                 # 클러스터 내부에서 쓰는 포트
    targetPort: 8080                           # Pod의 포트
    nodePort: 30001                            # 모든 노드에 열릴 포트 (30000~32767)
  type: NodePort                               # 이 줄이 있어야 노드 포트가 열린다
END
```

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pod-2 — Pod
apiVersion: v1
kind: Pod
metadata:
  name: pod-2                                  # 분산을 보려고 두 번째 Pod을 만든다
  labels:
    app: pod                                   # svc-2가 이 라벨로 함께 잡는다
spec:
  nodeSelector:
    kubernetes.io/hostname: k8s-worker2        # pod-1과 다른 노드에 둔다
  containers:
  - name: container
    image: kubetm/app
    ports:
    - containerPort: 8080
END
```

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # svc-3 — Service (NodePort)
apiVersion: v1
kind: Service
metadata:
  name: svc-3                                  # externalTrafficPolicy 비교용
spec:
  selector:
    app: pod
  ports:
  - port: 9000
    targetPort: 8080
    nodePort: 30002                            # 30000은 dashboard가 쓰므로 피한다
  type: NodePort
  externalTrafficPolicy: Local                 # 요청 받은 노드의 Pod에만 보낸다
END
```

> 대시보드가 30000 포트를 쓰고 있어 실습은 30001·30002를 쓴다.

## 실습 과정

### 1. svc-2 생성 — Pod이 없는 노드에서도 열린다

이 시점에 Pod은 `pod-1` 하나뿐이고 **worker1에만** 있다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # svc-2 생성 (YAML은 위 절 참고)
# ... svc-2 YAML ...
END

kubectl get svc svc-2       # PORT(S) 표기 확인
```

```
NAME    TYPE       CLUSTER-IP       EXTERNAL-IP   PORT(S)          AGE
svc-2   NodePort   10.109.156.102   <none>        9000:30001/TCP   0s
```

`9000:30001` — 앞이 ClusterIP 포트, 뒤가 노드 포트다.
**NodePort는 ClusterIP를 포함한다.** ClusterIP도 그대로 생겼다.

세 노드 모두에 호출해 본다.

```bash
clear                              # 화면 정리 후 시작
curl 192.168.56.30:30001/hostname  # master (Pod 없음)
curl 192.168.56.31:30001/hostname  # worker1 (pod-1 있음)
curl 192.168.56.32:30001/hostname  # worker2 (Pod 없음)
```

```
192.168.56.30:30001/hostname → Hostname : pod-1
192.168.56.31:30001/hostname → Hostname : pod-1
192.168.56.32:30001/hostname → Hostname : pod-1
```

**Pod이 없는 master와 worker2에서도 응답한다.**
NodePort는 클러스터의 **모든 노드**에 포트를 열고, 요청을 받은 노드가 Pod이 있는 노드로 넘겨준다.

### 2. pod-2 추가 — 트래픽이 분산된다

```bash
clear                                                        # 화면 정리 후 시작
kubectl apply -f - <<'END'                                   # worker2에 pod-2 생성
# ... pod-2 YAML ...
END

kubectl wait --for=condition=Ready pod/pod-2 --timeout=120s  # 뜰 때까지 대기
kubectl get pod -o wide                                      # 두 Pod이 다른 노드에 있는지 확인
kubectl get endpoints svc-2                                  # Endpoints가 2개로 늘었는지
```

```
NAME    READY   STATUS    IP               NODE
pod-1   1/1     Running   20.100.194.125   k8s-worker1
pod-2   1/1     Running   20.110.126.44    k8s-worker2

NAME    ENDPOINTS                                AGE
svc-2   20.100.194.125:8080,20.110.126.44:8080   15s
```

**worker1 한 곳으로만 20번 호출**해서 분산을 확인한다.

```bash
clear  # 화면 정리 후 시작
# worker1 주소로만 20번 호출한 뒤 응답을 집계한다
for i in $(seq 1 20); do curl -s 192.168.56.31:30001/hostname; echo; done | sort | uniq -c
```

```
      7 Hostname : pod-1
     13 Hostname : pod-2
```

worker1에 보냈는데 **13번은 worker2의 pod-2가 응답했다.**
Service는 요청을 받은 노드와 무관하게 Endpoints 중에서 무작위로 고른다.
정확히 반반이 아닌 것은 라운드로빈이 아니라 **확률적 분배**이기 때문이다.

### 3. svc-3 — externalTrafficPolicy: Local

노드를 넘나드는 이 동작이 늘 좋은 건 아니다. 넘길 때 **출발지 IP가 가려지고**, 한 번 더 홉을 탄다.
`externalTrafficPolicy: Local`은 **요청 받은 노드에 있는 Pod에만** 보낸다.

```bash
clear                                                              # 화면 정리 후 시작
kubectl apply -f - <<'END'                                         # svc-3 생성 (nodePort 30002, Local)
# ... svc-3 YAML ...
END

kubectl get svc svc-3 -o jsonpath='{.spec.externalTrafficPolicy}'  # 설정이 들어갔는지 확인
```

**클러스터 밖에서 온 트래픽**으로 시험해야 한다. Pod 안에서 노드 IP를 호출한다.

```bash
clear                                                                           # 화면 정리 후 시작
kubectl run curlbox --image=kubetm/app --restart=Never --command -- sleep 3600  # 테스트용 Pod
kubectl wait --for=condition=Ready pod/curlbox --timeout=120s                   # 뜰 때까지 대기

# curlbox 안에서 각 노드의 30002 포트를 호출한다
kubectl exec curlbox -- curl -s --max-time 5 192.168.56.30:30002/hostname
kubectl exec curlbox -- curl -s --max-time 5 192.168.56.31:30002/hostname
kubectl exec curlbox -- curl -s --max-time 5 192.168.56.32:30002/hostname
```

```
192.168.56.30 (master,  Pod 없음)  → (응답 없음)  http=000  exit 28  ← 타임아웃
192.168.56.31 (worker1, pod-1)     → Hostname : pod-1
192.168.56.32 (worker2, pod-2)     → Hostname : pod-2
```

**Pod이 없는 master는 타임아웃**이다. `Local` 정책이라 넘겨줄 로컬 Pod이 없으면 그냥 버린다.
Pod이 있는 노드는 **자기 노드의 Pod만** 응답한다.

| Service | 정책 | worker1로 보내면 | Pod 없는 노드로 보내면 |
|---|---|---|---|
| `svc-2` (30001) | 기본(`Cluster`) | pod-1 또는 pod-2 | 응답함 (다른 노드로 넘김) |
| `svc-3` (30002) | `Local` | **pod-1만** | **타임아웃** |

> **주의 — 노드 자신에서 호출하면 Local이 적용되지 않는다.**
> master에서 `curl 192.168.56.30:30002` 를 하면 Pod이 없는데도 응답이 온다.
> `externalTrafficPolicy`는 이름 그대로 **외부에서 들어온 트래픽**에만 적용되고,
> 노드 자신이 만든 트래픽은 클러스터 내부 경로를 타서 모든 Endpoints로 갈 수 있다.
> 그래서 위 실습을 Pod 안에서 했다. 이걸 모르면 "Local이 안 먹네" 하고 헷갈리게 된다.

### 정리

```bash
clear                                                           # 화면 정리 후 시작
kubectl delete pod curlbox --grace-period=1 --ignore-not-found  # 테스트용 Pod만 정리
```

## 배운 것

- NodePort는 **모든 노드**에 같은 포트를 연다. Pod이 없는 노드도 포함이다.
- 할당 범위는 `30000~32767`. 생략하면 자동 배정된다.
- NodePort는 ClusterIP를 **포함**한다 (`9000:30001` 표기).
- 기본 정책은 노드를 넘나들며 분산한다. 라운드로빈이 아니라 확률적이다.
- `externalTrafficPolicy: Local`은 자기 노드의 Pod에만 보내고, 없으면 버린다.
- `Local` 검증은 **반드시 클러스터 밖(또는 다른 Pod)에서** 해야 한다.
