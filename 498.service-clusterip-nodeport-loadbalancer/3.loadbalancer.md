# 3) LoadBalancer

원문 : https://cafe.naver.com/kubeops/498 (3. LoadBalancer)

- 선행 조건 : [1.clusterip.md](1.clusterip.md), [2.nodeport.md](2.nodeport.md)의 `pod-1`, `pod-2`

NodePort의 기능을 포함하면서, **클라우드가 만들어준 외부 IP** 하나로 접근하게 한다.
내부 노드 IP를 밖에 노출하지 않아도 된다는 것이 핵심이다.

## 왜 필요한가

### 없으면 이렇게 된다

[2. NodePort](2.nodeport.md)로 밖에서 들어오는 길은 열었다. 하지만 운영에 쓰기엔 불편하다.

| 문제 | 내용 |
|---|---|
| **노드 IP가 노출된다** | 접속자가 `192.168.56.31` 같은 내부 주소를 알아야 한다 |
| **노드가 죽으면** | 그 IP로 접속하던 사람은 끊긴다. 다른 노드 IP를 알려줘야 한다 |
| **포트가 이상하다** | `30001` 같은 번호를 써야 한다. 80·443을 쓸 수 없다 |

### LoadBalancer가 앞에 세우는 것

LoadBalancer는 **노드들 앞에 대표 주소 하나**를 세운다.
접속자는 그 주소만 알면 되고, 뒤에 노드가 몇 대인지 어느 노드가 죽었는지 몰라도 된다.

```
바깥 ──▶ EXTERNAL-IP 하나 ──▶ 노드 여러 대 ──▶ Pod
         (노드 IP를 모른다)     (죽은 노드는 알아서 제외)
```

여기서 중요한 것은 **쿠버네티스가 LB를 직접 만들지 않는다**는 점이다.
`type: LoadBalancer`는 **"만들어 달라"는 요청**일 뿐이고, 그 요청을 받아 실제로
IP를 배정해 주는 주체가 따로 있어야 한다. 클라우드에서는 사업자가 그 일을 하고,
베어메탈에는 그 주체가 없다. 그래서 이 실습 환경에서는 `<pending>`이 뜬다.

**그것이 에러가 아니라는 점**을 확인하는 것이 이 문서의 핵심이다.

### 이 문서에서 확인할 것

- 베어메탈에서 `EXTERNAL-IP`가 어떻게 되는가 (2절)
- `<pending>`인 상태에서도 접속이 되는가 — 된다면 무엇으로 (3절)
- 실제로 외부 IP를 받으려면 무엇이 필요한가 ([부록](../부록%29%20로드밸런서/metallb-설치와-원리.md))
- MetalLB를 설치한 뒤 **서비스 포트·노드 포트·ClusterIP 세 경로가 다 되는가** (3절)
- 그 외부 IP는 실제로 **어느 장비에 붙어 있는가** (3절 검증)

## YAML

```yaml
apiVersion: v1
kind: Service
metadata:
  name: svc-4
spec:
  selector:
    app: pod                                   # pod-1, pod-2 둘 다 대상
  ports:
  - port: 9000                                 # LB가 받는 포트
    targetPort: 8080                           # Pod의 포트
                                               # nodePort를 안 적으면 자동 배정된다
  type: LoadBalancer                           # NodePort + 외부 LB 요청
```

### 2. 왜 pending 인가

```bash
clear                                                                                # 화면 정리 후 시작
kubectl describe svc svc-4 | grep -E 'Type|LoadBalancer Ingress|NodePort|Endpoints'  # 상세 확인
kubectl get pod -A | grep -i 'cloud-controller\|metallb'                             # LB를 만들어줄 컨트롤러가 있는가
```

```
Type:       LoadBalancer
NodePort:   <unset>  30902/TCP
Endpoints:  20.100.194.125:8080,20.110.126.44:8080

(cloud-controller / metallb 검색 결과 없음)
```

- `type: LoadBalancer`는 쿠버네티스가 직접 LB를 만드는 게 아니다.
- **"누가 좀 만들어 줘"라고 요청만 걸어두는 것**이고, 실제로 만드는 건
- 클라우드 컨트롤러(GCP·AWS·Azure)나 MetalLB 같은 별도 구성요소다.   

이 클러스터는 Vagrant 위의 베어메탈이라 그런 게 없어서, 요청이 처리되지 않고 계속 대기한다.
**에러가 아니다.** 원문이 "클라우드 서비스에서 사용 가능"이라고 적은 이유다.

> **2026-09-11 — 이 클러스터에는 MetalLB를 설치했다.**
> 따라서 지금 실습하면 `<pending>`이 아니라 `192.168.56.200` 같은 **실제 IP가 붙는다.**
> 위 출력은 MetalLB 설치 **이전**의 기록이다.
> 배경·원리·설치 방법은 [부록) 로드밸런서 - MetalLB](../부록%29%20로드밸런서/metallb-설치와-원리.md) 참고.
>
> `<pending>` 상태를 그대로 재현하려면 그 문서의 「7-2) MetalLB 제거」를 먼저 실행한다.

### 검증: pending 이어도 접근은 된다

`LoadBalancer`는 `NodePort`를 **포함**하므로, LB가 안 생겨도 아래는 그대로 동작한다.

```bash
clear                                                  # 화면 정리 후 시작
curl 192.168.56.31:30902/hostname                      # 자동 배정된 NodePort로 접근
curl 192.168.56.32:30902/hostname                      # 다른 노드로도 접근
kubectl get svc svc-4 -o jsonpath='{.spec.clusterIP}'  # ClusterIP도 살아있다
```

```
192.168.56.31:30902/hostname → Hostname : pod-2
192.168.56.32:30902/hostname → Hostname : pod-2
10.104.195.72:9000/hostname  → Hostname : pod-2
```

`nodePort`를 지정하지 않았는데 **30902가 자동 배정**됐다.
클라우드에서는 LB가 이 NodePort로 트래픽을 넘긴다. 원문의
*"Load Balancer는 NodePort를 통해 트래픽을 전달"* 이 이 구조를 말한다.

### 3. MetalLB 설치 후 — 서비스 포트·노드 포트 테스트

> **여기부터는 MetalLB가 설치된 현재 클러스터 기준이다** (재실습 2026-09-12).
> 위 1·2절 출력은 설치 **이전** 기록이라 `<pending>`·`30902`가 찍혀 있다. 섞어 보지 않는다.
> 설치 과정은 [부록) 로드밸런서 - MetalLB](../부록%29%20로드밸런서/metallb-설치와-원리.md) 참고.

#### 3-1) EXTERNAL-IP 가 붙었는지 먼저 확인

```bash
clear                  # 화면 정리 후 시작
kubectl get svc svc-4  # EXTERNAL-IP 열이 pending 이 아니어야 한다

# 누가 IP를 배정했고 어느 노드가 광고하는지
kubectl describe svc svc-4 | grep -E 'Annotations|LoadBalancer Ingress|NodePort|Endpoints'

# MetalLB가 남긴 이벤트
kubectl get events --field-selector involvedObject.name=svc-4 \
  --sort-by=.lastTimestamp \
  -o custom-columns=REASON:.reason,MESSAGE:.message
```

```
NAME    TYPE           CLUSTER-IP      EXTERNAL-IP      PORT(S)          AGE
svc-4   LoadBalancer   10.106.176.66   192.168.56.200   9000:30359/TCP   17m

Annotations:           metallb.universe.tf/ip-allocated-from-pool: lab-pool
LoadBalancer Ingress:  192.168.56.200
NodePort:              <unset>  30359/TCP
Endpoints:             20.100.194.93:8080,20.110.126.37:8080

REASON         MESSAGE
IPAllocated    Assigned IP ["192.168.56.200"]
nodeAssigned   announcing from node "k8s-worker2" with protocol "layer2"
```

- `lab-pool`(`192.168.56.200-210`)에서 **첫 주소를 받았다.** 풀은 부록에서 만든 것이다.
- `nodeAssigned` — L2 모드라 **노드 한 대(`k8s-worker2`)가 이 IP를 대표로 물고 있다.**
- `Endpoints`에 Pod 2개가 그대로 잡혀 있다. LB가 붙어도 뒷단은 달라지지 않는다.

#### 3-2) 주소를 변수로 잡아둔다

`nodePort`는 **지정하지 않으면 매번 다른 번호가 배정된다.** 문서의 `30359`를 그대로 치지 말고
아래처럼 뽑아 쓰면 재실습할 때마다 고칠 필요가 없다.

```bash
clear                                                                           # 화면 정리 후 시작
LB=$(kubectl get svc svc-4 -o jsonpath='{.status.loadBalancer.ingress[0].ip}')  # MetalLB가 준 외부 IP
NP=$(kubectl get svc svc-4 -o jsonpath='{.spec.ports[0].nodePort}')             # 자동 배정된 노드 포트
CIP=$(kubectl get svc svc-4 -o jsonpath='{.spec.clusterIP}')                    # 클러스터 내부 IP
echo "LB=$LB  NP=$NP  CIP=$CIP"                                                 # 세 주소를 한 줄로 확인
```

```
LB=192.168.56.200  NP=30359  CIP=10.106.176.66
```

#### 3-3) 서비스 포트 — `EXTERNAL-IP:9000`

LoadBalancer가 실제로 하고 싶었던 접근이다. **노드 IP를 전혀 모르고도** 닿는다.

```bash
clear                      # 화면 정리 후 시작
curl -s $LB:9000/hostname  # 대표 주소 하나로 호출

# 10번 호출해서 어느 Pod으로 갔는지 센다
for i in $(seq 10); do curl -s $LB:9000/hostname; done | sort | uniq -c
```

```
Hostname : pod-2

      7 Hostname : pod-1
      3 Hostname : pod-2
```

**두 Pod에 나뉘어 들어간다.** 다만 7:3이라 균등하지 않다. 이유는 3-6절에서 본다.

#### 3-4) 노드 포트 — `노드IP:30359`

LoadBalancer는 NodePort를 **포함**하므로 이 길도 그대로 살아 있다.
`svc-4`에는 `nodePort`를 적지 않았는데도 `30359`가 자동으로 붙었다.

```bash
clear  # 화면 정리 후 시작

# 세 노드 전부에서 같은 노드 포트로 들어가 본다
for n in 30 31 32; do
  printf '192.168.56.%s:%s → ' $n $NP
  curl -s 192.168.56.$n:$NP/hostname
done
```

```
192.168.56.30:30359 → Hostname : pod-1
192.168.56.31:30359 → Hostname : pod-2
192.168.56.32:30359 → Hostname : pod-1
```

- **Pod이 없는 master(`.30`)로 들어가도 응답한다.** 노드 포트는 모든 노드에 열리고,
  받은 노드가 다른 노드의 Pod으로 넘겨주기 때문이다 (`externalTrafficPolicy: Cluster` 기본값).
- 들어간 노드와 응답한 Pod이 일치하지 않는다. `.32`로 들어갔는데 `pod-1`(worker1)이 받았다.

#### 3-5) ClusterIP — `10.106.176.66:9000`

가장 안쪽 길도 확인해 둔다. LoadBalancer 안에 ClusterIP가 그대로 들어 있다.

```bash
clear                       # 화면 정리 후 시작
curl -s $CIP:9000/hostname  # 클러스터 내부용 주소
```

```
Hostname : pod-2
```

#### 3-6) 세 경로를 한 장으로

| 경로 | 주소 | 어디서 쓰나 | 이번 확인 |
|---|---|---|---|
| 서비스 포트 (LB) | `192.168.56.200:9000` | 클러스터 **바깥**. 노드 IP를 몰라도 된다 | O |
| 노드 포트 | `192.168.56.30~32:30359` | 바깥. 단 노드 IP를 알아야 한다 | O (3대 전부) |
| ClusterIP | `10.106.176.66:9000` | 클러스터 **안**에서만 | O |

```
[바깥] ─▶ 192.168.56.200:9000   (MetalLB VIP — worker2가 물고 있음)
             │
             └▶ 노드의 30359 ─▶ KUBE-SVC 체인 ─▶ pod-1 / pod-2 :8080
```

### 검증: VIP를 어느 노드가 물고 있나

L2 모드는 **VIP를 노드 한 대가 자기 MAC으로 대신 응답**하는 방식이다. 말로만 듣지 말고 확인한다.

```bash
clear                                                      # 화면 정리 후 시작
arping -c 2 -I eth1 192.168.56.200 | grep 'Unicast reply'  # VIP에 응답하는 MAC

# 각 워커의 실제 MAC과 대조
for n in 31 32; do
  printf 'k8s-worker%s(192.168.56.%s) ' $((n-30)) $n
  ssh root@192.168.56.$n "ip -br link show eth1 | awk '{print \$3}'"
done
```

```
Unicast reply from 192.168.56.200 [08:00:27:59:25:3E]  1.142ms
Unicast reply from 192.168.56.200 [08:00:27:59:25:3E]  0.975ms

k8s-worker1(192.168.56.31) 08:00:27:77:9e:1a
k8s-worker2(192.168.56.32) 08:00:27:59:25:3e
```

**VIP의 MAC이 k8s-worker2의 MAC과 같다.** 3-1절 이벤트의
`announcing from node "k8s-worker2"` 와 정확히 맞는다.
VIP는 별도의 장비가 아니라 **worker2가 자기 NIC으로 대신 답해 주는 주소**다.

광고하는 speaker 파드의 로그로도 같은 사실을 볼 수 있다.

```bash
clear  # 화면 정리 후 시작
kubectl get pods -n metallb-system -l component=speaker \
  -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName

# 위에서 확인한 광고 노드의 speaker 로그만 본다
SPK=$(kubectl get pods -n metallb-system -l component=speaker \
  --field-selector spec.nodeName=k8s-worker2 -o jsonpath='{.items[0].metadata.name}')
kubectl logs -n metallb-system $SPK --tail=100 | grep serviceAnnounced | tail -1
```

```
NAME            NODE
speaker-m8gvg   k8s-master
speaker-nmgft   k8s-worker2
speaker-tr5rd   k8s-worker1

{"event":"serviceAnnounced","ips":["192.168.56.200"],"msg":"service has IP, announcing",
 "pool":"lab-pool","protocol":"layer2","ts":"2026-09-12T06:38:30Z"}
```

> speaker는 **세 노드 모두에 뜨지만 광고는 한 대만 한다.** 나머지 둘의 로그에는
> `serviceWithdrawn ... "reason":"notOwner"` 가 찍힌다. `-l component=speaker`로
> 세 파드 로그를 한꺼번에 보면 announce와 withdraw가 뒤섞여 헷갈리니 노드를 지정해서 본다.

### 검증: 왜 7:3으로 나뉘었나 — 라운드로빈이 아니다

3-3절에서 10번 중 7:3으로 갈렸다. 번갈아 가지 않는 이유는 kube-proxy가 만든 규칙에 있다.

```bash
clear  # 화면 정리 후 시작

# kube-proxy가 어떤 모드로 도는지
kubectl logs -n kube-system -l k8s-app=kube-proxy --tail=50 | grep -i 'Proxier' | head -2

# svc-4 의 분산 규칙
iptables -t nat -L KUBE-SVC-SCSBGWXSK7N2YM6T -n
```

```
"Using iptables Proxier"

Chain KUBE-SVC-SCSBGWXSK7N2YM6T (2 references)
target                      prot  ...  destination
KUBE-MARK-MASQ              tcp   ...  10.106.176.66   /* default/svc-4 cluster IP */
KUBE-SEP-E7NW23IFNC6DPQRC   all   ...  /* default/svc-4 -> 20.100.194.93:8080 */ statistic mode random probability 0.50000000000
KUBE-SEP-C5GGJV27PJU5LVVG   all   ...  /* default/svc-4 -> 20.110.126.37:8080 */
```

- 체인 이름(`KUBE-SVC-SCSBGWXSK7N2YM6T`)은 서비스마다 다르다.
  `iptables -t nat -L -n | grep 'svc-4 cluster IP'` 로 먼저 찾는다.
- **`statistic mode random probability 0.5`** — 매 요청마다 **동전을 던진다.**
  순서대로 돌리는 라운드로빈이 아니라서 10번 중 5:5가 아니라 7:3도 정상이다.
- 횟수를 늘릴수록 절반에 가까워진다. 적은 횟수로 균등을 기대하면 안 된다.
  실제로 같은 10회 호출을 한 번 더 돌렸더니 이번엔 **5:5**가 나왔다. 매번 달라지는 것이 정상이다.

### 세 타입의 포함 관계

```
ClusterIP  ─ 클러스터 내부 전용
    ↑ 포함
NodePort   ─ ClusterIP + 모든 노드의 30000~32767 포트
    ↑ 포함
LoadBalancer ─ NodePort + 외부 LB가 만들어준 IP 하나
```

| 타입 | 내부 접근 | 노드 IP로 접근 | 외부 전용 IP |
|---|---|---|---|
| ClusterIP | O | X | X |
| NodePort | O | O | X |
| LoadBalancer | O | O | O (클라우드, 또는 베어메탈 + MetalLB) |

```bash
  svc-4 \
  --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

## 배운 것

- `type: LoadBalancer`는 **LB를 만들어 달라는 요청**일 뿐이다. 만드는 주체가 따로 있어야 한다.
- 베어메탈에서는 `EXTERNAL-IP`가 `<pending>`으로 남는다. 에러가 아니다.
  외부 IP가 필요하면 MetalLB 같은 것을 따로 설치한다.
  → [부록) 로드밸런서 - MetalLB](../부록%29%20로드밸런서/metallb-설치와-원리.md) 에서 실제로 설치하고 원리까지 확인했다.
- pending이어도 **NodePort와 ClusterIP는 동작한다.** LoadBalancer가 그 둘을 포함하기 때문이다.
- `nodePort`를 안 적으면 `30000~32767`에서 자동 배정된다 (설치 전 실습 30902, 재실습 30359).
  **재실습마다 번호가 바뀌므로** 문서의 숫자를 그대로 치지 말고 `jsonpath`로 뽑아 쓴다 (3-2절).
- MetalLB를 설치하면 `EXTERNAL-IP`에 실제 IP가 붙고, **노드 IP를 몰라도 그 주소 하나로 닿는다** (3-3절).
  노드 포트·ClusterIP는 그대로 살아 있다. LoadBalancer가 둘을 포함하기 때문이다 (3-4·3-5절).
- L2 모드의 외부 IP는 장비가 아니라 **노드 한 대가 자기 MAC으로 대신 응답하는 주소**다.
  `arping`의 MAC이 그 노드의 MAC과 같은 것으로 확인했다.
- 분산은 라운드로빈이 아니라 **iptables의 확률 규칙**(`statistic mode random`)이다.
  같은 10회 호출이 7:3이 되기도 5:5가 되기도 한다. 적은 횟수로 균등을 기대하면 안 된다.
