# 1) DaemonSet — 모든 노드에 하나씩

원문 : https://cafe.naver.com/kubeops/507 (1. DaemonSet)

`replicas`를 적지 않는다. **노드마다 Pod 하나**가 규칙이다.
노드별 로그 수집기, 모니터링 에이전트, 네트워크 플러그인이 이 형태다.

> 이 클러스터의 `calico-node`, `csi-node-driver`, `kube-proxy`가 전부 DaemonSet이다.
> `kubectl get ds -A` 로 확인할 수 있다.

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## YAML

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: daemonset-1
spec:
  selector:                                    # replicas 가 없다 — 노드 수가 곧 개수다
    matchLabels:
      type: app
  template:
    metadata:
      labels:
        type: app
    spec:
      containers:
      - name: container
        image: kubetm/app
        ports:
        - containerPort: 8080                  # 컨테이너가 bind 하는 포트
          hostPort: 18080                      # 노드의 이 포트를 컨테이너로 직결한다
```

## 실습 과정

### 1. 노드마다 하나씩 생기는가

```bash
clear                                                        # 화면 정리 후 시작
kubectl apply -f - <<'END'                                   # DaemonSet 생성 (YAML은 위 절 참고)
# ... 위 YAML 전체 ...
END

kubectl rollout status daemonset/daemonset-1 --timeout=180s  # 전 노드에 뜰 때까지 대기
kubectl get ds,pod -o wide                                   # 개수와 배치 확인
```

```
daemonset.apps/daemonset-1   DESIRED 3   CURRENT 3   READY 3

pod/daemonset-1-ljkxs   k8s-master
pod/daemonset-1-wxkhm   k8s-worker1
pod/daemonset-1-hl59q   k8s-worker2
```

**노드가 3대라 Pod도 3개.** master에도 생긴 것은 이 클러스터의 master에
`NoSchedule` taint가 없기 때문이다. 보통은 master를 제외한다.

### 2. hostPort — 자기 노드의 Pod에만 간다

```bash
clear                              # 화면 정리 후 시작
curl 192.168.56.30:18080/hostname  # master
curl 192.168.56.31:18080/hostname  # worker1
curl 192.168.56.32:18080/hostname  # worker2
```

```
192.168.56.30:18080 → Hostname : daemonset-1-ljkxs      (master의 Pod)
192.168.56.31:18080 → Hostname : daemonset-1-wxkhm      (worker1의 Pod)
192.168.56.32:18080 → Hostname : daemonset-1-hl59q      (worker2의 Pod)
```

**각 노드가 자기 위의 Pod에만 연결된다.** 노드를 넘어가지 않는다.

NodePort와 헷갈리기 쉬운데 성격이 다르다.

| | `hostPort` | `nodePort` (Service) |
|---|---|---|
| 정의 위치 | Pod의 `ports` | Service의 `ports` |
| 연결 대상 | **그 노드의 Pod만** | 클러스터 전체의 Endpoints |
| 포트 범위 | 제한 없음 | 30000~32767 |
| 부하 분산 | 없음 | 있음 |

노드별 에이전트처럼 **"그 노드의 것"에 접근해야 할 때** hostPort가 맞다.

> `hostPort`도 노드의 실제 포트를 점유하므로 **한 노드에 같은 hostPort를 쓰는 Pod은 하나뿐**이다.
> DaemonSet은 노드당 하나라 충돌하지 않지만, Deployment로 hostPort를 쓰면
> replicas를 노드 수보다 크게 잡는 순간 나머지는 `Pending`이 된다.

### 3. nodeSelector로 일부 노드에만

```bash
clear                                                  # 화면 정리 후 시작
kubectl label nodes k8s-worker1 os=centos --overwrite  # worker1 에 라벨 부여
kubectl label nodes k8s-worker2 os=ubuntu --overwrite  # worker2 에 다른 라벨
kubectl get nodes -L os                                # 라벨 확인
```

```
NAME          STATUS   ROLES           OS
k8s-master    Ready    control-plane
k8s-worker1   Ready    <none>          centos
k8s-worker2   Ready    <none>          ubuntu
```

`nodeSelector: {os: centos}` 를 넣은 DaemonSet을 만든다.

```bash
clear                                                        # 화면 정리 후 시작
kubectl apply -f - <<'END'                                   # nodeSelector 가 있는 DaemonSet
# ... daemonset-2 YAML (nodeSelector: os: centos) ...
END

kubectl rollout status daemonset/daemonset-2 --timeout=180s  # 대기
kubectl get ds daemonset-2                                   # DESIRED 가 몇인가
```

```
NAME          DESIRED   CURRENT   READY   NODE SELECTOR   AGE
daemonset-2   1         1         1       os=centos       3s
```

**DESIRED가 3이 아니라 1이다.** 라벨이 맞는 노드가 worker1 하나뿐이라서다.

### 검증: 노드 라벨을 바꾸면 즉시 반응하는가

worker2에도 `os=centos`를 붙여본다.

```bash
clear                                                        # 화면 정리 후 시작
kubectl label nodes k8s-worker2 os=centos --overwrite        # 라벨을 centos 로 변경
kubectl rollout status daemonset/daemonset-2 --timeout=180s  # 반영 대기
kubectl get ds daemonset-2                                   # DESIRED 가 바뀌었는가
kubectl get pod -o wide                                      # 어디에 생겼나
```

```
NAME          DESIRED   CURRENT   READY   NODE SELECTOR
daemonset-2   2         2         2       os=centos          ← 1에서 2로

daemonset-2-c9qqp → k8s-worker1
daemonset-2-vrqbc → k8s-worker2          ← 새로 생겼다
```

**yaml을 건드리지 않았는데 Pod이 늘었다.**
DaemonSet은 노드 목록과 라벨을 계속 지켜보다가 조건에 맞는 노드가 생기면 즉시 Pod을 만든다.

노드를 새로 클러스터에 넣어도 마찬가지다. 이것이 DaemonSet을 쓰는 이유다.

### 정리

```bash
clear                                            # 화면 정리 후 시작
kubectl delete ds \
  daemonset-1 \
  daemonset-2 \
  --grace-period=1 --ignore-not-found

kubectl label nodes k8s-worker1 k8s-worker2 os-  # 실습용 라벨 제거 (뒤의 - 가 삭제 의미)
```

## 배운 것

- DaemonSet에는 `replicas`가 없다. **노드 수가 곧 개수**다.
- `hostPort`는 **그 노드의 Pod에만** 연결된다. NodePort와 달리 노드를 넘지 않는다.
- `nodeSelector`로 일부 노드에만 둘 수 있고, `DESIRED`가 그 개수로 잡힌다.
- **노드 라벨이 바뀌거나 노드가 늘면 자동으로 따라간다.** yaml 수정이 필요 없다.
- 노드별 에이전트(로그·모니터링·네트워크)가 전형적인 용도다.
