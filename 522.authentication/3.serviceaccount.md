# 3) ServiceAccount — Pod에게 신원을 주기

원문 : https://cafe.naver.com/kubeops/522 (3. Service Account)

[1번](1.x509-client-certs.md)의 인증서는 **사람**을 위한 것이다.
**Pod 안의 프로그램**이 API를 호출해야 할 때는 인증서를 심어주기 곤란하다.

ServiceAccount는 그 용도의 계정이고, **토큰**으로 인증한다.

| | User (인증서) | ServiceAccount (토큰) |
|---|---|---|
| 오브젝트로 존재하나 | **아니다** | **그렇다** (`kubectl get sa`) |
| 인증 수단 | 클라이언트 인증서 | Bearer 토큰 |
| 대상 | 사람, 외부 시스템 | **Pod 안의 프로그램** |
| 이름 형식 | 인증서의 CN | `system:serviceaccount:<ns>:<이름>` |

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> `nm-01` 등 default 밖의 네임스페이스는 지워지지 않는다.

## 실습 과정

### 1. 네임스페이스를 만들면 ServiceAccount가 따라온다

```bash
clear                    # 화면 정리 후 시작
kubectl create ns nm-01  # 네임스페이스 생성
kubectl get sa -n nm-01  # 자동으로 생긴 것이 있는가
```

```
NAME      SECRETS   AGE
default   0         17s
```

**`default` ServiceAccount가 자동으로 만들어진다.**
Pod에 `serviceAccountName`을 지정하지 않으면 이것이 쓰인다.

`SECRETS` 가 **0**인 것에 주목한다.

### 2. v1.24부터는 토큰이 자동 생성되지 않는다

예전에는 ServiceAccount를 만들면 토큰 Secret이 딸려왔다.
지금은 보안상 그러지 않는다. **직접 만들어야 한다.**

```bash
clear                                                                           # 화면 정리 후 시작
kubectl create -f - <<'EOF'
apiVersion: v1
kind: Secret
metadata:
  name: nm-01
  namespace: nm-01
  annotations:
    kubernetes.io/service-account.name: default   # 이 SA 의 토큰을 만들어라
type: kubernetes.io/service-account-token         # 이 타입이어야 토큰이 채워진다
EOF

kubectl describe secret nm-01 -n nm-01 | grep -E '^Name:|^Type:|^Annotations:'  # 확인
```

```
Name:         nm-01
Annotations:  kubernetes.io/service-account.name: default
Type:  kubernetes.io/service-account-token
```

`annotations`로 어느 ServiceAccount의 것인지 지정하고,
`type`을 `kubernetes.io/service-account-token`으로 두면
**쿠버네티스가 토큰을 채워 넣는다.**

> 원문이 *"Kubernetes v1.24부터 ServiceAccount Token 자동 생성 기능이 비활성화됨"* 이라고
> 적은 부분이다. 무기한 유효한 토큰이 여기저기 남는 것을 막기 위한 변경이다.
>
> 지금 권장 방식은 **Pod에 자동으로 주입되는 임시 토큰**이다.
> Pod을 만들면 `/var/run/secrets/kubernetes.io/serviceaccount/token` 에
> 짧은 수명의 토큰이 자동으로 마운트된다. 이 실습처럼 Secret을 직접 만드는 것은
> **클러스터 밖에서 토큰을 쓰기 위한** 방법이다.

### 3. 토큰으로 API를 호출한다

```bash
clear                                                                               # 화면 정리 후 시작
TOKEN=$(kubectl get secret nm-01 -n nm-01 -o jsonpath='{.data.token}' | base64 -d)  # 토큰 추출
echo "${#TOKEN}"                                                                    # 길이 확인 (JWT 라 길다)

# 인증만 필요한 엔드포인트
curl -sk -o /dev/null -w 'HTTP %{http_code}\n' \
  https://192.168.56.30:6443/api/v1 \
  -H "Authorization: Bearer $TOKEN"
```

```
876
HTTP 200
```

**인증에 성공했다.** 토큰이 유효하다는 뜻이다.

### 검증: 인증은 됐는데 왜 Pod 목록은 못 보는가

```bash
clear  # 화면 정리 후 시작
curl -sk https://192.168.56.30:6443/api/v1/namespaces/nm-01/pods/ \
  -H "Authorization: Bearer $TOKEN"
```

```json
{
  "kind": "Status",
  "status": "Failure",
  "message": "pods is forbidden: User \"system:serviceaccount:nm-01:default\"
              cannot list resource \"pods\" in API group \"\" in the namespace \"nm-01\"",
  "reason": "Forbidden"
}
```

**HTTP 403이다.** 그런데 메시지를 잘 읽어야 한다.

> `User "system:serviceaccount:nm-01:default" cannot list resource "pods"`

**"누구인지 모르겠다"가 아니라 "너는 아는데 권한이 없다"** 는 뜻이다.
이름까지 정확히 지목하고 있다.

여기서 두 단계가 갈린다.

| 단계 | 질문 | 이 게시글 |
|---|---|---|
| **Authentication (인증)** | 너 누구야? | **522 — 통과했다** |
| **Authorization (인가)** | 그걸 해도 돼? | **525 — 아직 안 됐다** |

토큰은 신분증일 뿐이다. **무엇을 할 수 있는지는 별도로 부여해야 한다.**
그것이 RBAC이고 다음 게시글(525)의 주제다.

### 참고 — 토큰 없이 호출하면

```bash
clear  # 화면 정리 후 시작
curl -sk -o /dev/null -w 'HTTP %{http_code}\n' https://192.168.56.30:6443/api/v1/namespaces/nm-01/pods/
```

```
HTTP 403
```

같은 403이지만 이유가 다르다. 이쪽은 `system:anonymous` 라서 막힌 것이다.
**상태 코드만 보지 말고 응답 본문의 `message` 를 봐야** 구분된다.

### 정리하지 않는다

```bash
clear                 # 화면 정리 후 시작
kubectl get ns nm-01  # 다음 실습(525 RBAC)에서 그대로 쓴다
```

> 원문 주석 그대로 — *"생성된 리소스는 다음 실습에서 사용되기 때문에 삭제하지 않습니다."*
> `nm-01` 네임스페이스, `default` ServiceAccount, `nm-01` Secret, `pod-1` 을 남겨둔다.

## 배운 것

- ServiceAccount는 **Pod을 위한 계정**이고 토큰으로 인증한다.
- 네임스페이스를 만들면 `default` ServiceAccount가 자동으로 생긴다.
- **v1.24부터 토큰 Secret이 자동 생성되지 않는다.** 필요하면 직접 만든다.
- 이름은 `system:serviceaccount:<네임스페이스>:<이름>` 형식이다.
- **인증(토큰이 유효한가)과 인가(권한이 있는가)는 별개다.**
  토큰이 통해도 403이 날 수 있고, 그때 메시지에 사용자 이름이 찍힌다.
