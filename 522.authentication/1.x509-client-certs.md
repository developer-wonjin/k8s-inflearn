# 1) X509 Client Certs — 인증서로 API 서버에 접근

원문 : https://cafe.naver.com/kubeops/522 (1. X509 Client Certs)

`kubectl`이 하는 일을 벗겨보면 결국 **API 서버에 HTTPS 요청을 보내는 것**이다.
그 요청이 통하는 이유는 `~/.kube/config` 안에 **클라이언트 인증서**가 들어 있기 때문이다.

## kubeconfig에는 무엇이 들어 있나

```bash
clear                                               # 화면 정리 후 시작
grep -E 'server:|name:' /etc/kubernetes/admin.conf  # 접속 주소와 이름들
```

```
- cluster:
    server: https://192.168.56.30:6443      ← API 서버 주소
  name: kubernetes
    cluster: kubernetes
    user: kubernetes-admin
  name: kubernetes-admin@kubernetes         ← 현재 컨텍스트
```

세 덩어리로 되어 있다.

| 항목 | 뜻 |
|---|---|
| `clusters` | 어느 API 서버에 접속할지 (주소 + CA 인증서) |
| `users` | 누구로 접속할지 (클라이언트 인증서 + 키) |
| `contexts` | 위 둘의 조합. `current-context` 가 현재 사용 중 |

## 실습 과정

### 1. 인증서를 꺼내본다

kubeconfig 안의 인증서는 base64로 인코딩돼 있다. 디코딩하면 실제 파일이 된다.

```bash
clear                        # 화면 정리 후 시작
grep 'client-certificate-data' /etc/kubernetes/admin.conf | head -n 1 | awk '{print $2}' | base64 -d > client.crt
grep 'client-key-data' /etc/kubernetes/admin.conf | head -n 1 | awk '{print $2}' | base64 -d > client.key
ls -l client.crt client.key  # 파일이 생겼는지
```

```
client.crt  1147 bytes
client.key  1679 bytes
```

이 인증서가 **누구를 증명하는지** 확인한다.

```bash
clear                                                       # 화면 정리 후 시작
openssl x509 -in client.crt -noout -subject -issuer -dates  # 인증서 내용
```

```
subject=O = system:masters, CN = kubernetes-admin
issuer=CN = kubernetes
notBefore=Jul 24 16:14:36 2026 GMT
notAfter=Jul 24 16:14:37 2027 GMT
```

여기가 핵심이다.

| 필드 | 값 | 쿠버네티스가 읽는 방식 |
|---|---|---|
| `CN` (Common Name) | `kubernetes-admin` | **사용자 이름** |
| `O` (Organization) | `system:masters` | **그룹 이름** |

`system:masters`는 쿠버네티스에 내장된 **최고 권한 그룹**이다.
RBAC 규칙을 거치지 않고 모든 것을 할 수 있다.
`kubectl`로 뭐든 할 수 있는 이유가 이 한 줄이다.

> **쿠버네티스에는 User 오브젝트가 없다.** `kubectl get users` 같은 명령이 없다.
> 사용자는 **인증서 안의 CN/O로만 존재**한다. 사용자를 추가한다는 것은
> CA로 인증서를 하나 더 발급한다는 뜻이다.
>
> `notAfter` 가 1년 뒤인 것에도 주의한다. **인증서는 만료된다.**
> 만료되면 kubectl이 갑자기 안 되므로 갱신이 필요하다.

### 2. 인증서 유무로 비교한다

```bash
clear  # 화면 정리 후 시작
# 인증서 없이 (-k 는 서버 인증서 검증 생략)
curl -sk -o /dev/null -w 'HTTP %{http_code}\n' https://192.168.56.30:6443/api/v1/nodes

# 인증서를 붙여서
curl -sk --cert client.crt --key client.key \
  -o /dev/null -w 'HTTP %{http_code}\n' \
  https://192.168.56.30:6443/api/v1/nodes
```

```
인증서 없이 → HTTP 403
인증서로   → HTTP 200
```

**kubectl 없이도 API를 쓸 수 있다.** kubectl은 이 요청을 대신 만들어주는 도구일 뿐이다.

> 403은 "누군지 모르겠다"가 아니라 "익명 사용자에게는 권한이 없다"는 뜻이다.
> 인증 자체는 익명(`system:anonymous`)으로 통과하고, **인가에서 막힌 것**이다.
> 이 구분은 [3. ServiceAccount](3.serviceaccount.md)에서 다시 나온다.

### 3. kubectl proxy — 인증을 대신 처리하게 하기

인증서를 나눠주지 않고도 API를 열어주는 방법이다.
master에서 proxy를 띄우면 **proxy가 대신 인증서를 붙여준다.**

```bash
clear  # 화면 정리 후 시작
# 백그라운드로 proxy 실행 (--address 로 외부 접속 허용)
nohup kubectl proxy --port=8001 --address=192.168.56.30 --accept-hosts='^*$' >/dev/null 2>&1 &

# https 도 인증서도 없이 호출된다
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://192.168.56.30:8001/api/v1/nodes
```

```
HTTP 200
```

**http에 인증서도 없는데 200이다.** proxy 뒤에서 kubeconfig의 인증서가 쓰이고 있다.

> **이건 개발·디버깅용이다.** `--accept-hosts='^*$'` 는 아무나 받겠다는 뜻이라
> 그 포트에 닿을 수 있는 사람은 누구나 **클러스터 관리자 권한**을 갖게 된다.
> 실습이 끝나면 반드시 종료한다.

```bash
clear                                                        # 화면 정리 후 시작
PROXY_PID=$(pgrep -f 'kubectl proxy --port=8001' | head -1)  # PID 확인
kill "$PROXY_PID"                                            # 종료
```

> `pkill -f 'kubectl proxy'` 는 쓰지 않는다. `-f` 패턴이 넓어
> 그 문자열을 포함한 **현재 셸까지 죽일 수 있다.** (실제로 겪었다)

### 정리

```bash
clear                        # 화면 정리 후 시작
rm -f client.crt client.key  # 꺼낸 인증서 파일 삭제
```

> **꺼낸 `client.key`는 관리자 권한 그 자체다.** 실습 후 반드시 지운다.
> 이 파일만 있으면 누구나 클러스터를 마음대로 할 수 있다.

## 배운 것

- kubeconfig에는 **접속 주소 + 클라이언트 인증서**가 들어 있다.
- 인증서의 `CN`이 사용자, `O`가 그룹이다. `system:masters`가 최고 권한 그룹이다.
- 쿠버네티스에 **User 오브젝트는 없다.** 사용자는 인증서로만 존재한다.
- `kubectl`은 결국 HTTPS 요청을 만드는 도구다. curl로도 같은 일을 할 수 있다.
- `kubectl proxy`는 인증을 대신 처리해준다. 편하지만 **권한을 그대로 노출**한다.
