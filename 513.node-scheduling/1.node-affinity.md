# 1) Node Affinity — 노드를 고르는 조건

원문 : https://cafe.naver.com/kubeops/513 (1. Node Affinity)

`nodeSelector`는 "이 라벨이 정확히 이 값인 노드"밖에 못 고른다.
Node Affinity는 **조건식**을 쓸 수 있고, 무엇보다 **"되면 좋고 안 되면 말고"** 를 표현할 수 있다.

| 옵션 | 뜻 | 조건에 맞는 노드가 없으면 |
|---|---|---|
| `requiredDuringSchedulingIgnoredDuringExecution` | 반드시 | **`Pending`** |
| `preferredDuringSchedulingIgnoredDuringExecution` | 되도록 | 아무 노드에나 배치 |

> 이름이 긴 이유는 뒷부분(`IgnoredDuringExecution`) 때문이다.
> **스케줄링할 때만 본다**는 뜻이다. 이미 뜬 Pod은 나중에 노드 라벨이 바뀌어도 쫓겨나지 않는다.

## YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-match-expressions1
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - {key: kr, operator: Exists}        # kr 라는 라벨이 있기만 하면 됨
  containers:
  - name: container
    image: kubetm/app
  terminationGracePeriodSeconds: 0
```

`preferred`는 형태가 조금 다르다. **가중치**가 붙는다.

```yaml
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 1                              # 1~100. 여러 개일 때 우선순위가 된다
        preference:
          matchExpressions:
          - {key: ch, operator: Exists}
```

## 실습 과정

### 1. 노드에 라벨을 붙인다

```bash
clear                                                # 화면 정리 후 시작
kubectl label nodes k8s-worker1 kr=az-1 --overwrite  # worker1 에 kr 라벨
kubectl label nodes k8s-worker2 us=az-1 --overwrite  # worker2 에 us 라벨
kubectl get nodes -L kr,us                           # 확인
```

```
NAME          STATUS   ROLES           KR     US
k8s-master    Ready    control-plane
k8s-worker1   Ready    <none>          az-1
k8s-worker2   Ready    <none>          az-1
```

### 2. 세 가지 Pod을 동시에 만들어 비교한다

- `pod-match-expressions1` : `kr` 이 있는 노드 (required) → worker1만 해당
- `pod-required` : `ch` 가 있는 노드 (required) → **그런 노드가 없다**
- `pod-preferred` : `ch` 가 있는 노드 (preferred) → 없지만 preferred다

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # Pod 3개를 한 번에 생성
# ... pod-match-expressions1, pod-required, pod-preferred YAML ...
END

kubectl get pod -o wide     # 어디에 배치됐나
```

```
  pod-match-expressions1     Running    k8s-worker1
  pod-preferred              Running    k8s-worker1
  pod-required               Pending    <none>
```

**`required`만 `Pending`이다.** 나머지 둘은 배치됐다.

```bash
clear                                                   # 화면 정리 후 시작
kubectl describe pod pod-required | grep -A4 '^Events'  # 대기 사유
```

```
Warning  FailedScheduling  default-scheduler
  0/3 nodes are available: 3 node(s) didn't match Pod's node affinity/selector.
```

**3개 노드 모두 조건에 안 맞는다**고 명확히 알려준다.

반면 `preferred`는 조건에 맞는 노드가 없어도 **아무 노드에나 배치했다.**
"있으면 거기로, 없으면 어디든" 이라는 뜻이다.

### operator 종류

| operator | 뜻 | `values` |
|---|---|---|
| `In` | 값이 목록에 있음 | 필요 |
| `NotIn` | 값이 목록에 없음 | 필요 |
| `Exists` | key가 있기만 하면 됨 | 불필요 |
| `DoesNotExist` | key가 없어야 함 | 불필요 |
| `Gt` / `Lt` | 값이 크다 / 작다 (숫자) | 필요 |

`nodeSelector`에는 `In`에 해당하는 것 하나뿐이다. Affinity가 훨씬 넓다.

### 정리

```bash
clear                                # 화면 정리 후 시작
kubectl delete pod \
  pod-match-expressions1 \
  pod-required \
  pod-preferred \
  --grace-period=1 --ignore-not-found

kubectl label nodes k8s-worker1 kr-  # 라벨 제거 (뒤의 - 가 삭제)
kubectl label nodes k8s-worker2 us-  # 라벨 제거
```

## 배운 것

- `nodeSelector`보다 표현력이 넓다. `Exists`, `NotIn`, `Gt` 등을 쓸 수 있다.
- `required`는 조건에 맞는 노드가 없으면 **`Pending`** 으로 무한 대기한다.
- `preferred`는 **조건을 못 맞춰도 배치한다.** 선호일 뿐이다.
- `IgnoredDuringExecution` — **스케줄링 시점에만** 본다. 나중에 라벨이 바뀌어도 쫓아내지 않는다.
