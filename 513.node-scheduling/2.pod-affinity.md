# 2) Pod Affinity / Anti-Affinity — 다른 Pod을 기준으로 배치

원문 : https://cafe.naver.com/kubeops/513 (2. Pod Affinity / Anti-Affinity)

Node Affinity가 **노드의 라벨**을 봤다면, 이쪽은 **다른 Pod의 라벨**을 본다.

- **Pod Affinity** : 그 Pod과 **같은 곳**에 붙인다 (웹-캐시처럼 가까이 둬야 할 때)
- **Pod Anti-Affinity** : 그 Pod과 **다른 곳**에 떨어뜨린다 (master-slave처럼 함께 죽으면 안 될 때)

## 왜 필요한가

### 없으면 이렇게 된다

[1. Node Affinity](1.node-affinity.md)는 **노드의 라벨**을 기준으로 골랐다.
그런데 배치 조건이 노드가 아니라 **다른 Pod**에 달린 경우가 있다.

| 원하는 것 | 노드 라벨로 표현하면 |
|---|---|
| 웹과 캐시를 **같은 노드**에 (네트워크 지연 최소화) | 노드를 못박아야 한다. 캐시가 옮겨가면 깨진다 |
| DB 복제본을 **서로 다른 노드**에 (함께 죽으면 안 됨) | 복제본마다 다른 노드를 손으로 지정해야 한다 |

노드 라벨로 하면 **Pod이 옮겨갈 때마다 사람이 따라 고쳐야 한다.**

### Pod Affinity가 보는 것

기준을 노드에서 **다른 Pod**으로 옮긴다. 그 Pod이 어디에 있든 따라가거나 피한다.

| | 하는 일 | 쓰는 때 |
|---|---|---|
| `podAffinity` | 그 Pod과 **같은 곳**에 붙인다 | 웹-캐시처럼 가까워야 할 때 |
| `podAntiAffinity` | 그 Pod과 **다른 곳**에 떨어뜨린다 | 복제본이 함께 죽으면 안 될 때 |

여기서 **"같은 곳"이 어디까지인지**를 정하는 것이 `topologyKey`다.
같은 노드일 수도 있고, 같은 랙이나 같은 가용 영역일 수도 있다.
이 한 줄로 의미가 완전히 달라지므로 이 문서에서 직접 바꿔가며 확인한다.

### 이 문서에서 확인할 것

- 따라갈 대상 Pod이 **아직 없으면** 어떻게 되는가 (2절)
- 나중에 대상이 생기면 **자동으로 배치되는가** (2절)
- `topologyKey`를 바꾸면 배치가 어떻게 달라지는가 (3절)
- 복제본을 노드마다 흩뿌리려면 어떻게 쓰는가 (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> 노드에 붙인 라벨·taint는 이 정리로 지워지지 않는다. 각 문서 끝 정리에서 되돌린다.

## topologyKey — "같은 곳"의 기준

핵심 개념이다. **어느 범위를 "같은 곳"으로 볼지** 정한다.

| topologyKey | 뜻 |
|---|---|
| `kubernetes.io/hostname` | 같은 **노드** |
| `topology.kubernetes.io/zone` | 같은 **가용 영역** |
| `a-team` (직접 붙인 라벨) | 그 라벨 값이 같은 노드들 |

이 실습에서는 `a-team` 라벨을 노드마다 다른 값으로 붙였다.
그래서 `a-team` 값이 다른 worker1과 worker2가 서로 다른 "곳"이 된다.

## YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web1
  labels:
    type: web1                                 # server1 이 이 라벨을 찾는다
spec:
  nodeSelector:
    a-team: '1'                                # worker1 에 고정
  containers:
  - name: container
    image: kubetm/app
  terminationGracePeriodSeconds: 0
---
apiVersion: v1
kind: Pod
metadata:
  name: server1
spec:
  affinity:
    podAffinity:                               # 같은 곳에 붙인다
      requiredDuringSchedulingIgnoredDuringExecution:
      - topologyKey: a-team                    # "같은 곳" = a-team 값이 같은 노드
        labelSelector:
          matchExpressions:
          - {key: type, operator: In, values: [web1]}   # 이 라벨의 Pod을 따라간다
  containers:
  - name: container
    image: kubetm/app
  terminationGracePeriodSeconds: 0
```

`podAntiAffinity`는 `podAffinity`를 그대로 바꿔 쓰면 된다. 의미만 반대다.

## 실습 과정

### 1. 노드에 라벨을 붙인다

```bash
clear                                                 # 화면 정리 후 시작
kubectl label nodes k8s-worker1 a-team=1 --overwrite  # worker1 = 1번 구역
kubectl label nodes k8s-worker2 a-team=2 --overwrite  # worker2 = 2번 구역
kubectl get nodes -L a-team                           # 확인
```

### 2. Pod Affinity — 따라가기

`web1`(worker1 고정)과 `server1`(web1을 따라감), `server2`(web2를 따라감)를 함께 만든다.
**`web2`는 아직 없다.**

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # web1, server1, server2 생성
# ... web1, server1, server2 YAML ...
END

kubectl get pod -o wide     # 어디에 배치됐나
```

```
  server1    Running    k8s-worker1      ← web1 을 따라갔다
  server2    Pending    <none>           ← web2 가 없어서 대기
  web1       Running    k8s-worker1
```

**`server1`은 `nodeSelector`가 없는데도 worker1로 갔다.** `web1`이 거기 있기 때문이다.
`server2`는 따라갈 대상(`web2`)이 없어 `Pending`이다.

### 3. 대상이 생기면 따라간다

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # worker2 에 web2 생성
# ... web2 YAML (nodeSelector a-team: '2') ...
END

kubectl get pod -o wide     # server2 가 어떻게 됐나
```

```
  server1    Running    k8s-worker1
  server2    Running    k8s-worker2      ← Pending 이 풀리고 web2 를 따라갔다
  web1       Running    k8s-worker1
  web2       Running    k8s-worker2
```

`Pending`이던 `server2`가 **자동으로 배치됐다.**
스케줄러는 포기하지 않고 조건이 갖춰지기를 계속 기다린다.

### 4. Anti-Affinity — 떨어뜨리기

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # master(worker1 고정)와 slave(master 와 반대편)
# ... master, slave YAML ...
END

kubectl get pod -o wide     # 어디에 배치됐나
```

```
  master     Running    k8s-worker1
  slave      Running    k8s-worker2      ← master 를 피해서 반대편으로
```

`slave`에는 `nodeSelector`가 없다. **`master`가 worker1에 있으니 worker2로 간 것**이다.

실무에서는 이런 데 쓴다.

- 같은 앱의 replica를 **여러 노드에 흩뿌려** 한 노드가 죽어도 전멸하지 않게
- DB primary/replica를 **다른 랙·다른 영역**에 두기

### 정리

```bash
clear                                                # 화면 정리 후 시작
kubectl delete pod \
  web1 \
  server1 \
  web2 \
  server2 \
  master \
  slave \
  --grace-period=1 --ignore-not-found

kubectl label nodes k8s-worker1 k8s-worker2 a-team-  # 라벨 제거
```

## 배운 것

- Node Affinity는 **노드 라벨**, Pod Affinity는 **다른 Pod의 라벨**을 본다.
- `topologyKey`가 "같은 곳"의 범위를 정한다. 노드 단위일 수도, 영역 단위일 수도 있다.
- `podAffinity`는 따라가고, `podAntiAffinity`는 피한다.
- 따라갈 대상이 없으면 `Pending`이고, **대상이 생기면 자동으로 배치된다.**
- replica 분산에 쓰려면 `podAntiAffinity` + `topologyKey: kubernetes.io/hostname` 이 정석이다.
