# 3) Pod — Node Schedule (nodeSelector, resources)

원문 : https://cafe.naver.com/kubeops/497 (3. Node Schedule)

Pod을 어느 노드에 올릴지 결정하는 두 가지 축을 확인한다.

1. **직접 지정** — `nodeSelector`로 노드를 못박는다
2. **자원 기반 자동 스케줄링** — `resources.requests`를 보고 스케줄러가 고른다

## 왜 필요한가

### 없으면 이렇게 된다

Pod을 만들면 스케줄러가 알아서 노드를 고른다. 그런데 그 판단에 개입할 수 없으면
문제가 생긴다. **SSD가 달린 노드에서만 돌아야 하는 DB**가 아무 노드에나 뜨고,
자원이 부족한 노드에 Pod이 몰려 **서로 메모리를 뺏다가 같이 죽는다.**

### 두 가지 축

스케줄링에 개입하는 방법은 성격이 다른 두 가지다.

| 방식 | 하는 일 | 누가 고르나 |
|---|---|---|
| `nodeSelector` | **노드를 못박는다.** 라벨이 맞는 노드가 없으면 `Pending` | 사람 |
| `resources.requests` | **필요한 자원을 선언**하면 그만큼 여유 있는 노드가 선택된다 | 스케줄러 |

여기에 `resources.limits`가 더해지면 런타임 상한까지 정해진다.
**`requests`와 `limits`는 이름이 비슷하지만 작동하는 시점이 다르다.**
`requests`는 스케줄링할 때 한 번 쓰이는 **장부상의 예약**이고,
`limits`는 컨테이너가 도는 내내 적용되는 **실제 상한**이다.

이 차이를 모르면 "200Mi를 요청했는데 왜 실사용이 0Mi인가" 같은 데서 막힌다.

### 이 문서에서 확인할 것

- `nodeSelector`로 지정한 노드가 조건을 못 맞추면 어떻게 되는가 (1절)
- `requests`는 실사용량인가 예약인가 (2절)
- `limits`를 넘기면 죽는가 — **메모리와 CPU의 결과가 다른가** (3절)
- QoS 등급은 누가 정하는가 (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> `service/kubernetes`는 API 서버로 가는 기본 서비스라 `--field-selector`로 제외한다.
> 지워도 자동 재생성되지만 그 사이 통신이 끊긴다.

## YAML

### 3-1) pod-3 — 노드 직접 지정 + 노드를 거의 채우기

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pod-3 — Pod
apiVersion: v1                                 # Pod은 core 그룹
kind: Pod
metadata:
  name: pod-3                                  # Pod 이름
spec:
  nodeSelector:                                # 스케줄링될 노드를 직접 지정
    kubernetes.io/hostname: k8s-worker1        # 모든 노드에 기본으로 붙어있는 라벨
  containers:
  - name: container                            # 컨테이너 이름
    image: kubetm/init                         # 계속 떠 있기만 하는 실습용 이미지
    resources:                                 # 자원 사용량 설정
      requests:                                # 스케줄링 판단에 쓰는 값
        memory: 2.7Gi                          # worker1 allocatable(2.79Gi)의 대부분
      limits:                                  # 런타임 상한 — 넘으면 OOMKilled
        memory: 2.7Gi
END
```

### 3-2) pod-4 — 노드 미지정, requests < limits

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pod-4 — Pod
apiVersion: v1
kind: Pod
metadata:
  name: pod-4
spec:                                          # nodeSelector 없음 → 스케줄러가 알아서 고름
  containers:
  - name: container
    image: kubetm/init
    resources:
      requests:
        memory: 2Gi                            # 이만큼 남은 노드에만 스케줄링된다
      limits:
        memory: 3Gi                            # requests보다 커도 된다 (버스트 허용)
END
```

### 3-3) pod-5 — 작은 요청량

```bash
clear                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                     # pod-5 — Pod
apiVersion: v1
kind: Pod
metadata:
  name: pod-5
spec:
  containers:
  - name: container
    image: kubetm/init
    resources:
      requests:
        memory: 0.5Gi                          # 작아서 어느 노드든 들어간다
      limits:
        memory: 0.5Gi                          # requests == limits → Guaranteed QoS
END
```

#### 주의: `2.7Gi` 소수점 표기 경고

원문 yaml의 `2.7Gi`는 동작은 하지만 API 서버가 경고를 낸다.
`2.7Gi`가 내부적으로 `2899102924800m`(밀리 단위)이라는 소수 바이트 값이 되기 때문이다.

경고를 없애려면 정수로 적는다.

```yaml
memory: 2764Mi          # 2.7Gi ≈ 2764.8Mi → 정수로 반올림
```

기능상 차이는 없다. 이 문서는 원문 재현을 위해 `2.7Gi`를 그대로 썼다.

### 2. worker1이 얼마나 찼는지 확인

```bash
clear                                                               # 화면 정리 후 시작
kubectl describe node k8s-worker1 | grep -A6 'Allocated resources'  # 노드에 예약된 자원량만 잘라서 본다
```

```

  --------   --------              ------
  memory     2899102924800m (96%)  2899102924800m (96%)
```

worker1 메모리의 **96%가 예약**됐다. 남은 건 약 0.09Gi.

> `kubetm/init`은 메모리를 거의 쓰지 않지만, 스케줄러 입장에서 worker1은 이미 꽉 찬 노드다.

```
NAME    READY   STATUS    RESTARTS   AGE   IP              NODE
pod-3   1/1     Running   0          29s   20.100.194.96   k8s-worker1

pod-5   1/1     Running   0          2s    20.108.82.206   k8s-master
```

세 노드에 하나씩 분산됐다.

> **pod-5가 master로 간 이유** — 이 클러스터의 master에는 taint가 없다.
> ```bash
> kubectl get node k8s-master -o jsonpath='{.spec.taints}'
> # → (빈 값)
> ```
> 보통 kubeadm 클러스터의 control-plane에는 `node-role.kubernetes.io/control-plane:NoSchedule`
> taint가 붙어 일반 Pod이 스케줄링되지 않는다. 여기선 그 taint가 제거돼 있어
> master도 스케줄링 후보가 된다. 강의 화면과 노드 분포가 달라 보이면 이걸 의심하면 된다.

### 검증 1: requests에 맞는 노드가 없으면 스케줄링 단계에서 Pending

> 아래 [검증 2](#검증-2-limits를-넘으면-실행-단계에서-oomkilled)와 짝이다.
> **`requests`는 스케줄링할 때 한 번 보고, `limits`는 커널이 실행 내내 감시한다.**
> 그래서 하나는 **뜨지도 못하고**(Pending), 다른 하나는 **떴다가 죽는다**(OOMKilled).

#### 시작 전 확인

> **여기서는 정리하면 안 된다.** 이 검증은 앞 실습의 **`pod-3`이 worker1을 차지한 상태**라야
> 성립한다. 지우면 worker1에 자리가 생겨 `pod-pending`이 그냥 스케줄링돼 버린다.

```bash
clear                                                               # 화면 정리 후 시작
kubectl get pod pod-3 -o wide                                       # worker1에 Running 이어야 한다
kubectl describe node k8s-worker1 | grep -A6 'Allocated resources'  # memory가 90%대여야 한다
```

`nodeSelector`는 "부탁"이 아니라 **필터**다. 조건을 만족하는 노드가 없으면 Pod은 뜨지 않는다.

```bash
clear                                                  # 화면 정리 후 시작
kubectl apply -f - <<'END'                             # 스케줄 불가능한 Pod을 일부러 만들어 본다
apiVersion: v1
kind: Pod
metadata:
  name: pod-pending
spec:
  nodeSelector:
    kubernetes.io/hostname: k8s-worker1        # 이미 96% 찬 노드
  containers:
  - name: container
    image: kubetm/init
    resources:
      requests:
        memory: 2Gi                            # 남은 0.09Gi로는 불가능
END

kubectl get pod pod-pending                            # STATUS가 Pending에서 멈춰 있는지 확인
kubectl describe pod pod-pending | grep -A6 '^Events'  # 스케줄러가 남긴 탈락 사유를 읽는다
```

```
NAME          READY   STATUS    RESTARTS   AGE
pod-pending   0/1     Pending   0          0s

Events:
  Type     Reason            From                Message
  ----     ------            ----                -------
  Warning  FailedScheduling  default-scheduler   0/3 nodes are available:
             1 Insufficient memory,
             2 node(s) didn't match Pod's node affinity/selector.
```

메시지가 정확히 나뉘어 나온다.

| 노드 수 | 탈락 사유 |
|---|---|
| 1 (worker1) | `Insufficient memory` — 셀렉터는 맞지만 메모리가 부족 |
| 2 (master, worker2) | `didn't match Pod's node affinity/selector` — 애초에 셀렉터 불일치 |

**Pending은 에러가 아니다.** Pod은 계속 남아서 자원이 생기면 그때 스케줄링된다.
`pod-3`을 지우면 이 Pod이 곧바로 worker1에 뜬다.

```bash
clear                                            # 화면 정리 후 시작
kubectl delete pod pod-pending --grace-period=1  # Pending 상태 Pod 정리 (자원을 점유하진 않는다)
```

### 검증 2: limits를 넘으면 실행 단계에서 OOMKilled

#### 시작 전 정리

앞 실습과 검증 1에서 쓴 `pod-3`·`pod-4`·`pod-5`를 여기서 비운다.
검증 2는 이들에 의존하지 않고, 세 Pod이 `requests`로 잡아둔 5.2Gi를 그대로 두면
뒤쪽 「requests는 실사용량과 무관하다」 절의 노드 장부 값이 문서와 달라진다.

```bash
clear                       # 화면 정리 후 시작
kubectl delete pod \
  pod-3 \
  pod-4 \
  pod-5 \
  --grace-period=1 --ignore-not-found

kubectl get pod             # 아무것도 남지 않아야 한다
```

원문의 *"Memory가 Limit를 넘을 경우 Pod는 OOM을 발생시키며 재시작됨"* 을 확인한다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # 메모리 한계를 일부러 넘기는 Pod 생성
apiVersion: v1
kind: Pod
metadata:
  name: pod-oom
spec:
  containers:
  - name: container
    image: kubetm/init
    command: ["/bin/sh","-c","tail /dev/zero"]   # 익명 메모리를 무한 할당
    resources:
      requests:
        memory: 100Mi
      limits:
        memory: 100Mi
END

kubectl get pod pod-oom -w  # -w = watch, 상태 변화를 실시간으로 흘려본다
```

```
pod-oom   0/1   ContainerCreating   0
pod-oom   0/1   OOMKilled           0            2s
pod-oom   1/1   Running             1 (2s ago)   4s
pod-oom   0/1   OOMKilled           1 (4s ago)   6s
pod-oom   0/1   CrashLoopBackOff    1 (16s ago)  19s
pod-oom   0/1   OOMKilled           2 (18s ago)  21s
pod-oom   0/1   CrashLoopBackOff    2 (14s ago)  34s
```

```bash
clear  # 화면 정리 후 시작
# 마지막으로 죽었을 때의 사유와 종료 코드를 뽑는다 — 줄이 길어 주석을 위로 뺌
kubectl get pod pod-oom -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}{" exitCode="}{.status.containerStatuses[0].lastState.terminated.exitCode}'
```

```
OOMKilled exitCode=137
```

`exitCode 137` = `128 + 9(SIGKILL)`. 커널의 cgroup OOM killer가 프로세스를 죽인 것이다.
Pod 자체는 삭제되지 않고 **컨테이너만 재시작**되며, 반복되면 `CrashLoopBackOff`로 backoff가 늘어난다.

> **첫 시도는 실패했다.** 처음엔 `dd if=/dev/zero of=/dev/shm/fill bs=1M count=200`으로
> 시도했는데 OOM이 나지 않았다. 로그를 보니
> ```
> 65+0 records in
> 64+0 records out
> 67108864 bytes (67 MB) copied
> ```
> 정확히 64MB에서 멈췄다. 쿠버네티스가 컨테이너의 `/dev/shm`을 기본 64Mi로 잡기 때문에
> 메모리 한계(100Mi)에 닿기 전에 **디스크 부족**으로 끝난 것이다.
> `tail /dev/zero`처럼 익명 메모리를 직접 할당해야 cgroup 메모리 제한에 걸린다.

### 검증 3: 메모리와 CPU는 한계를 넘었을 때 다르게 동작한다

#### 시작 전 정리

검증 2의 `pod-oom`은 지울 때까지 `CrashLoopBackOff`로 재시작을 반복한다.
남겨두면 재시작할 때마다 CPU를 써서 아래 `kubectl top` 값이 흔들린다.

```bash
clear                                                       # 화면 정리 후 시작
kubectl delete pod pod-oom --grace-period=1 --ignore-not-found
```

검증 2에서 메모리 한계를 넘긴 컨테이너는 죽었다. CPU도 그럴까?

```bash
clear                                                          # 화면 정리 후 시작
kubectl apply -f - <<'END'                                     # 코어 하나를 다 쓰려는 컨테이너에 100m 제한을 건다
apiVersion: v1
kind: Pod
metadata:
  name: cpu-hog
spec:
  containers:
  - name: c
    image: kubetm/init
    command: ["/bin/sh","-c","while :; do :; done"]   # 무한루프 = 코어 1개(1000m)를 다 쓰려 함
    resources:
      requests:
        cpu: 100m
      limits:
        cpu: 100m
END

kubectl wait --for=condition=Ready pod/cpu-hog --timeout=120s  # 뜰 때까지 대기
kubectl get pod cpu-hog                                        # 죽는지 지켜본다
kubectl top pod cpu-hog                                        # 실제로 CPU를 얼마나 쓰는지
```

```
NAME      READY   STATUS    RESTARTS   AGE
cpu-hog   1/1     Running   0          75s

NAME      CPU(cores)   MEMORY(bytes)
cpu-hog   100m         0Mi
```

1000m를 쓰려는 프로세스가 **정확히 100m에서 잘렸는데, 죽지는 않았다.**
그냥 10배 느리게 돌 뿐이다. 75초 동안 `RESTARTS`는 0이다.

| 자원 | 한계를 넘으면 | 왜 |
|---|---|---|
| **메모리** | `OOMKilled` → 재시작 | 이미 할당된 메모리는 뺏을 방법이 없다 |
| **CPU** | 스로틀링 (느려짐) | 다음 순번에 덜 주면 그만이다 |

CPU는 **압축 가능(compressible)**, 메모리는 **압축 불가능(incompressible)** 자원이라 부른다.
이 성질 하나가 두 동작의 차이를 전부 설명한다.

> 그래서 값을 정하는 기준도 달라진다.
> - **메모리** : `requests == limits` 로 정확히 잡는다. 넘기면 죽으므로 여유를 두는 의미가 없다.
> - **CPU** : `requests`만 두고 `limits`는 넉넉히 잡거나 생략한다.
>   스로틀링은 죽이지 않으니 순간 부하를 흡수하게 두는 편이 낫다.

#### requests와 limits의 조합이 QoS 등급을 정한다

#### 시작 전 정리

`cpu-hog`는 지울 때까지 스로틀링 상한인 100m을 계속 먹는다.
아래 `kubectl top pod` 목록에 섞여 나오면 QoS 등급별 사용량을 읽기 어려우므로 먼저 지운다.

```bash
clear                                                       # 화면 정리 후 시작
kubectl delete pod cpu-hog --grace-period=1 --ignore-not-found
```

세 가지 조합을 만들어 보면 등급이 자동으로 붙는다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # requests/limits 조합이 다른 Pod 3개
apiVersion: v1
kind: Pod
metadata:
  name: qos-guaranteed
spec:
  containers:
  - name: c
    image: kubetm/init
    resources:
      requests:
        memory: 100Mi
        cpu: 100m
      limits:
        memory: 100Mi     # requests 와 같다
        cpu: 100m
---
apiVersion: v1
kind: Pod
metadata:
  name: qos-burstable
spec:
  containers:
  - name: c
    image: kubetm/init
    resources:
      requests:
        memory: 100Mi
      limits:
        memory: 500Mi     # requests 보다 크다
---
apiVersion: v1
kind: Pod
metadata:
  name: qos-besteffort
spec:
  containers:
  - name: c
    image: kubetm/init    # resources 자체가 없다
END

# 부여된 QoS 등급을 확인한다 — 줄이 길어 주석을 위로 뺌
kubectl get pod -o custom-columns='NAME:.metadata.name,QOS:.status.qosClass,REQ_MEM:.spec.containers[0].resources.requests.memory,LIM_MEM:.spec.containers[0].resources.limits.memory'
```

```
NAME             QOS          REQ_MEM   LIM_MEM
qos-besteffort   BestEffort   <none>    <none>
qos-burstable    Burstable    100Mi     500Mi
qos-guaranteed   Guaranteed   100Mi     100Mi
```

| 등급 | 조건 | 노드 메모리가 고갈되면 |
|---|---|---|
| **Guaranteed** | 모든 자원에서 `requests == limits` | 가장 늦게 쫓겨난다 |
| **Burstable** | requests만 있거나 `requests < limits` | 중간 |
| **BestEffort** | `resources`를 아예 안 씀 | **가장 먼저 쫓겨난다** |

등급은 사용자가 지정하는 게 아니라 **requests/limits 조합에서 자동으로 계산**된다.
`kubectl get pod -o yaml`의 `status.qosClass`에 찍힌다.

3-1의 `pod-3`(`2.7Gi` / `2.7Gi`)과 3-3의 `pod-5`(`0.5Gi` / `0.5Gi`)는 `Guaranteed`,
3-2의 `pod-4`(`2Gi` / `3Gi`)는 `Burstable`이다.

#### requests는 실사용량과 무관하다

노드 장부와 실제 사용량을 나란히 보면 분명해진다.

```bash
clear                                                               # 화면 정리 후 시작
kubectl describe node k8s-worker1 | grep -A6 'Allocated resources'  # 스케줄러가 보는 장부
kubectl top pod                                                     # 실제 사용량 (metrics-server 필요)
```

```
-- 장부 (requests 합계) --
  Resource   Requests     Limits
  memory     200Mi (6%)   600Mi (20%)

-- 실제 사용량 --
NAME             CPU(cores)   MEMORY(bytes)
qos-guaranteed   0m           0Mi
qos-burstable    0m           0Mi
```

**장부에는 200Mi가 잡혀 있는데 실제로는 0Mi를 쓴다.**
`kubetm/init`은 아무 일도 하지 않기 때문이다.

그래도 스케줄러에게 그 200Mi는 이미 나간 자리다.
검증 1에서 worker1이 96%로 꽉 차 보였던 것도 실사용량이 아니라 이 장부 때문이었다.

> 호텔 예약과 같다. 방을 잡아두면 손님이 오지 않아도 그 방은 팔 수 없다.

한 가지 더 — `Limits` 합계(600Mi)는 `Requests` 합계(200Mi)보다 크고,
**노드 용량을 넘어도 된다(오버커밋).** 모두가 동시에 한계까지 쓰지는 않는다는 전제다.
반면 **`requests` 합계는 노드 allocatable을 넘을 수 없다.** 넘으면 검증 1처럼 `Pending`이 된다.

## 배운 것

- 모든 Pod은 반드시 어떤 노드 위에 올라가야 한다.
- **`requests`** = 스케줄링 기준 (예약). 실사용량이 아니다.
  장부에 200Mi가 잡혀 있어도 실제 사용은 0Mi일 수 있고, 스케줄러는 장부만 본다.
- **`limits`** = 런타임 상한. 자원에 따라 넘겼을 때 결과가 다르다.
  - **메모리**는 `OOMKilled`(exit 137) 후 재시작 — 압축 불가능 자원
  - **CPU**는 스로틀링만 되고 죽지 않는다 — 압축 가능 자원
- **QoS 등급**은 requests/limits 조합에서 자동으로 계산된다.
  `requests == limits` → `Guaranteed`, `requests < limits` → `Burstable`,
  `resources` 없음 → `BestEffort`. 노드 메모리가 고갈되면 `BestEffort`부터 쫓겨난다.
- **`limits` 합계는 노드 용량을 넘어도 되지만(오버커밋), `requests` 합계는 넘을 수 없다.**
- `nodeSelector`는 필터다. 맞는 노드가 없으면 `Pending`으로 무한 대기한다.
- `Pending`일 때는 `kubectl describe pod`의 **Events**를 보면 탈락 사유가 노드 수와 함께 나온다.
- `2.7Gi` 같은 소수점 표기는 경고가 뜬다. `2764Mi`처럼 정수로 쓰는 게 낫다.
