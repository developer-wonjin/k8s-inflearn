# 1-1) Pod — 컨테이너 2개

원문 : https://cafe.naver.com/kubeops/497 (1. Container)

## 왜 필요한가

### 없으면 이렇게 된다

컨테이너를 그냥 하나씩 띄우면 **함께 떠야 하는 것들을 묶을 방법이 없다.**
웹 서버와 로그 수집기처럼 항상 같은 곳에 붙어 있어야 하는 짝이 서로 다른 노드로
흩어질 수 있고, 파일이나 `localhost`로 주고받을 수도 없다.

### Pod이 묶는 것

Pod은 **함께 배치되어야 하는 컨테이너들의 최소 단위**다.
쿠버네티스가 다루는 모든 것은 컨테이너가 아니라 Pod 단위로 움직인다.

| 공유하는 것 | 결과 |
|---|---|
| 네트워크 | **IP가 하나**다. 컨테이너끼리 `localhost`로 통신한다 |
| 스토리지(볼륨) | 같은 볼륨을 여러 컨테이너가 마운트할 수 있다 |
| 수명·배치 | 같이 뜨고 같이 죽고 **같은 노드**에 올라간다 |

IP를 공유한다는 것은 **포트를 공유한다**는 뜻이기도 하다. 그래서 같은 Pod 안에서는
포트가 겹치면 안 된다. 겹치면 어떻게 되는지가 이 문서의 확인 대상이다.

### 이 문서에서 확인할 것

- 컨테이너를 2개 넣으면 IP가 2개가 되는가 (2절)
- `containerPort`는 실제로 무엇을 하는가 — 포트를 여는가, 막는가 (3절)
- 같은 포트를 두 컨테이너에 쓰면 **언제** 실패하는가 (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> `service/kubernetes`는 API 서버로 가는 기본 서비스라 `--field-selector`로 제외한다.
> 지워도 자동 재생성되지만 그 사이 통신이 끊긴다.

## YAML

```yaml
apiVersion: v1                 # Pod은 core 그룹이라 그룹명 없이 버전만 적는다
kind: Pod                      # 리소스 종류
metadata:
  name: pod-1                  # Pod 이름 (같은 네임스페이스 안에서 고유해야 함)
spec:                          # Pod이 어떤 상태여야 하는지 선언
  containers:                  # Pod 안에서 함께 돌 컨테이너 목록
  - name: container1           # 첫 번째 컨테이너 이름 (Pod 안에서 고유)
    image: kubetm/p8000        # 8000 포트로 응답하는 실습용 이미지
    ports:                     # 노출 포트 목록 — 문서용 메타데이터일 뿐이다
    - containerPort: 8000      # 실제 개방 여부는 컨테이너 내부 프로세스의 bind가 결정
  - name: container2           # 두 번째 컨테이너 이름
    image: kubetm/p8080        # 8080 포트로 응답하는 실습용 이미지
    ports:
    - containerPort: 8080      # container1과 겹치지 않게 8080 사용 (겹치면 아래 검증 참고)
```

## 실습 과정

### 1. 생성

```bash
clear                                                       # 화면 정리 후 시작
kubectl apply -f - <<'END'                                  # 파일 없이 표준입력(heredoc)으로 생성 — YAML 각 줄 설명은 위 YAML 절 참고
apiVersion: v1
kind: Pod
metadata:
  name: pod-1
spec:
  containers:
  - name: container1
    image: kubetm/p8000
    ports:
    - containerPort: 8000
  - name: container2
    image: kubetm/p8080
    ports:
    - containerPort: 8080
END

kubectl wait --for=condition=Ready pod/pod-1 --timeout=90s  # 컨테이너 2개가 모두 Ready 될 때까지 최대 90초 대기
kubectl get pod pod-1 -o wide                               # IP와 스케줄링된 NODE까지 함께 출력
```

```
pod/pod-1 created
pod/pod-1 condition met

NAME    READY   STATUS    RESTARTS   AGE   IP              NODE
pod-1   2/2     Running   0          3s    20.100.194.90   k8s-worker1
```

- `READY 2/2` — 컨테이너 2개가 모두 준비됨
- `IP` 1개 — **컨테이너가 2개여도 Pod당 IP는 하나**

> `kubectl wait --for=condition=Ready`는 Pod이 준비될 때까지 최대 90초 블로킹한다.
> `apply` 직후에는 `ContainerCreating` 상태라 IP가 비어 있어 바로 curl하면 실패한다.
> `sleep 30` 같은 눈대중 대기보다 정확하고, 준비되는 즉시 넘어가서 빠르다.

### 2. Master Node에서 Pod-IP:Port로 각 컨테이너 호출

```bash
clear                                                      # 화면 정리 후 시작
IP=$(kubectl get pod pod-1 -o jsonpath='{.status.podIP}')  # Pod IP만 뽑아 변수에 저장
curl $IP:8000                                              # 같은 IP의 8000 → container1
curl $IP:8080                                              # 같은 IP의 8080 → container2
```

```
curl 20.100.194.90:8000 → containerPort : 8000
curl 20.100.194.90:8080 → containerPort : 8080
```

같은 Pod IP에 **포트만 바꿔서** 서로 다른 컨테이너에 도달한다.

### 3. 컨테이너 내부에서 localhost로 다른 컨테이너 호출

```bash
clear                                                       # 화면 정리 후 시작
kubectl exec pod-1 -c container1 -- curl -s localhost:8000  # container1이 자기 자신을 호출
kubectl exec pod-1 -c container1 -- curl -s localhost:8080  # container1이 container2를 호출
kubectl exec pod-1 -c container2 -- curl -s localhost:8000  # 반대 방향도 되는지 확인
```

```
container1 → localhost:8000 : containerPort : 8000     (자기 자신)
container1 → localhost:8080 : containerPort : 8080     (container2)
container2 → localhost:8000 : containerPort : 8000     (container1)
```

같은 Pod 안의 컨테이너는 **네트워크 네임스페이스를 공유**하므로
서로를 `localhost` + 포트만으로 부를 수 있다. 서비스나 IP가 필요 없다.

### 검증: 같은 Port를 쓰면 정말 "생성 에러"가 나는가

원문은 *"Container 간에 같은 Port를 노출시키면 Pod 생성시 충돌 에러 발생"* 이라고 적고 있다.
확인해보니 **사실과 다르다.**

```bash
clear                                        # 화면 정리 후 시작
# 두 컨테이너 모두 kubetm/p8000 → 둘 다 8000 포트에 bind를 시도하게 된다
kubectl apply --dry-run=server -f - <<'END'  # 서버측 검증만 하고 만들지는 않음 — YAML 각 줄 설명은 위 YAML 절 참고
apiVersion: v1
kind: Pod
metadata:
  name: pod-portconflict
spec:
  containers:
  - name: container1
    image: kubetm/p8000
    ports:
    - containerPort: 8000
  - name: container2
    image: kubetm/p8000
    ports:
    - containerPort: 8000
END
```

```
pod/pod-portconflict created (server dry run)      ← API 서버가 통과시킨다
```

실제로 만들어도 생성 자체는 성공한다.

```bash
clear                                        # 화면 정리 후 시작
kubectl get pod pod-portconflict             # READY가 1/2, STATUS가 Error인지 확인

# 컨테이너별 ready 여부와 재시작 횟수를 한 줄로 뽑는다 (줄이 길어 주석을 위로 뺌)
kubectl get pod pod-portconflict -o jsonpath='{range .status.containerStatuses[*]}{.name}{" ready="}{.ready}{" restarts="}{.restartCount}{"\n"}{end}'

kubectl logs pod-portconflict -c container2  # 죽은 쪽 컨테이너의 로그 → EADDRINUSE 확인
```

```
NAME               READY   STATUS   RESTARTS      AGE
pod-portconflict   1/2     Error    1 (4s ago)    9s

container1 ready=true  restarts=0   state=running
container2 ready=false restarts=1   state=terminated exitCode=1 reason=Error

  code: 'EADDRINUSE',
  errno: -98,
  syscall: 'listen',
  address: '::',
  port: 8000
```

**정리**

| 단계 | 결과 |
|---|---|
| API 서버 검증 (`--dry-run=server`) | 통과 — `containerPort` 중복을 막지 않는다 |
| Pod 생성 | 성공 |
| 런타임 | container2가 `listen(8000)` 실패 → `EADDRINUSE` → exitCode 1 |
| 최종 | `1/2 Error` → 재시작 반복 → `CrashLoopBackOff` |

즉 충돌은 **생성 시점이 아니라 실행 시점**에 드러난다.
근본 원인은 yaml의 `containerPort` 선언이 아니라, 두 프로세스가 **공유된 네트워크
네임스페이스에서 같은 포트에 bind**하려 했기 때문이다.
`containerPort` 필드를 아예 지워도 결과는 똑같다 — 그 필드는 문서용 메타데이터일 뿐이다.

### 정리

```bash
clear  # 화면 정리 후 시작

# 이 문서에서 만든 Pod 2개를 한 번에 삭제
kubectl delete pod \
  pod-1 \
  pod-portconflict \
  --grace-period=1
```

## 배운 것

- Pod당 IP는 하나. 컨테이너를 여러 개 넣어도 IP는 늘지 않는다.
- Pod IP는 재생성할 때마다 바뀐다 → 직접 참조하면 안 되고 Service가 필요하다.
- 같은 Pod 안의 컨테이너는 `localhost`로 통신한다.
- `containerPort`는 **문서용**이다. 포트를 열지도, 막지도, 중복을 검증하지도 않는다.
- 포트 충돌은 생성이 아니라 런타임에 `CrashLoopBackOff`로 나타난다.
