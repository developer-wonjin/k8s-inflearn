# 2-2) Service — 라벨로 Pod 연결

원문 : https://cafe.naver.com/kubeops/497 (2. Label)

[2-1.pod-label.md](2-1.pod-label.md)에서 만든 Pod 6개를 대상으로,
Service가 라벨 셀렉터로 어떤 Pod을 잡아가는지 확인한다.

## 왜 필요한가

### 없으면 이렇게 된다

[1-1](1-1.pod-container.md)에서 확인했듯 **Pod IP는 재생성할 때마다 바뀐다.**
그래서 Pod IP를 직접 적어 두면 Pod이 한 번 죽는 순간 연결이 끊긴다.
Pod이 여러 개면 어느 IP로 보낼지 고르는 일도 직접 해야 한다.

### Service가 라벨로 푸는 방식

Service는 **"이 라벨을 가진 Pod들"** 이라고 조건만 적어 둔다.
Pod 이름도 IP도 적지 않는다.

```
Service  ──selector: type=web──▶  조건에 맞는 Pod 전부
           (이름·IP를 모른다)        (바뀌어도 알아서 따라간다)
```

Pod이 죽고 새로 떠서 IP가 바뀌어도, 라벨만 같으면 **자동으로 다시 잡힌다.**
새 Pod이 추가돼도 마찬가지다. 그래서 Pod의 수명과 무관한 **고정된 접점**이 생긴다.

셀렉터가 실제로 무엇을 잡았는지는 **Endpoints**에 나타난다.
Service가 동작하지 않을 때 가장 먼저 볼 곳이다.

### 이 문서에서 확인할 것

- 셀렉터가 잡은 Pod이 실제로 어디에 나타나는가 — Endpoints (2절)
- 한 Pod이 여러 Service에 동시에 속할 수 있는가 (3절)
- Service의 `selector`가 Deployment와 형식이 다른 이유 (YAML 절)

## 시작 전 확인

> ### 주의 — 이 문서는 앞 문서의 리소스를 그대로 이어받는다
>
> 이 실습은 [2-1.pod-label.md](2-1.pod-label.md)에서 만든 **Pod 6개(`pod-1` ~ `pod-6`)가
> 떠 있는 상태**를 전제한다. Service가 라벨로 그 Pod들을 잡아가는지 보는 것이 목적이기 때문이다.
>
> 그래서 이 문서에는 **정리 블록을 두지 않는다.** 다른 문서처럼 앞에서 리소스를 전부 지우면
> 그 Pod 6개도 함께 사라져 **Endpoints가 비어 있어 실습이 성립하지 않는다.**
>
> | 상황 | 할 일 |
> |---|---|
> | 2-1을 막 끝내고 이어서 온 경우 | 그대로 진행한다 |
> | 처음부터 다시 하는 경우 | **2-1을 먼저 실습**하고 이 문서로 복귀한다 |

지금 전제가 갖춰졌는지는 이걸로 확인한다.

```bash
clear                                 # 화면 정리 후 시작
kubectl get pod --show-labels         # pod-1 ~ pod-6 이 Running 이고 라벨이 붙어 있어야 한다
```

## YAML

```bash
clear                          # 화면 정리 후 시작
kubectl apply -f - <<'END'     # svc-for-web — Service (web)
apiVersion: v1                 # Service도 core 그룹
kind: Service                  # 리소스 종류
metadata:
  name: svc-for-web            # Service 이름
spec:
  selector:                    # 이 라벨을 가진 Pod을 연결 대상으로 삼는다
    type: web                  # type=web 인 Pod 전부 (lo 값은 상관없음)
  ports:
  - port: 8080                 # Service가 받는 포트
                               # targetPort 생략 시 port와 같은 값(8080)으로 전달
---                            # 리소스 구분자
apiVersion: v1
kind: Service
metadata:
  name: svc-for-production     # 두 번째 Service
spec:
  selector:
    lo: production             # lo=production 인 Pod 전부 (type 값은 상관없음)
  ports:
  - port: 8080
END
```

## 실습 과정

### 1. 생성

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # Service 2개를 한 번에 생성 — YAML 각 줄 설명은 위 YAML 절 참고
apiVersion: v1
kind: Service
metadata:
  name: svc-for-web
spec:
  selector:
    type: web
  ports:
  - port: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: svc-for-production
spec:
  selector:
    lo: production
  ports:
  - port: 8080
END

kubectl get svc             # CLUSTER-IP와 PORT가 잡혔는지 확인
```

```
NAME                 TYPE        CLUSTER-IP      PORT(S)    AGE
kubernetes           ClusterIP   10.96.0.1       443/TCP    41d
svc-for-production   ClusterIP   10.110.135.93   8080/TCP   0s
svc-for-web          ClusterIP   10.96.44.58     8080/TCP   0s
```

`type`을 지정하지 않아 기본값 **ClusterIP**로 만들어졌다.

### 2. Endpoints — 셀렉터가 실제로 잡은 Pod 확인

Service가 어떤 Pod에 연결됐는지는 **Endpoints**를 보면 된다.

```bash
clear  # 화면 정리 후 시작

# 셀렉터가 실제로 잡은 Pod의 IP 목록
kubectl get endpoints \
  svc-for-web \
  svc-for-production
```

```
NAME                 ENDPOINTS
svc-for-web          20.110.126.26:8080,20.110.126.27:8080
svc-for-production   20.100.194.95:8080,20.110.126.27:8080,20.110.126.28:8080
```

IP만으로는 알아보기 어려우니 Pod 이름으로 바꿔서 본다.

```bash
clear                                        # 화면 정리 후 시작
for s in svc-for-web svc-for-production; do  # Service 두 개를 차례로 돈다
  echo "-- $s --"                            # 어느 Service의 결과인지 구분선 출력
  # targetRef.name(Pod 이름)과 ip를 함께 뽑는다 — 줄이 길어 주석을 위로 뺌
  kubectl get endpoints $s -o jsonpath='{range .subsets[*].addresses[*]}  {.targetRef.name}{" ("}{.ip}{")"}{"\n"}{end}'
done                                         # 반복 종료
```

```
-- svc-for-web --
  pod-1 (20.110.126.26)
  pod-4 (20.110.126.27)
-- svc-for-production --
  pod-5 (20.100.194.95)
  pod-4 (20.110.126.27)
  pod-6 (20.110.126.28)
```

### 3. 결과 대조

| Service | selector | 잡힌 Pod |
|---|---|---|
| svc-for-web | `type: web` | pod-1(dev), pod-4(production) |
| svc-for-production | `lo: production` | pod-4(web), pod-5(db), pod-6(server) |

- **`pod-4`는 두 Service 모두에 속한다.** `type=web`이면서 `lo=production`이기 때문.
  하나의 Pod이 여러 Service에 동시에 연결될 수 있다.
- Service는 Pod의 *이름*을 모른다. 오직 *라벨*만 본다.
  Pod을 지웠다 새로 만들어 이름과 IP가 바뀌어도, 라벨만 같으면 Endpoint에 자동으로 다시 들어온다.
  이것이 "Pod IP를 직접 쓰지 말고 Service를 쓰라"는 말의 실체다.

> Endpoints가 바로 안 보이면 몇 초 기다렸다 다시 조회한다.
> Service 생성 직후에는 endpoints 컨트롤러가 아직 채우지 않아
> `Error from server (NotFound): endpoints "svc-for-web" not found`가 뜰 수 있다. (실제로 겪음)

### 정리

```bash
clear  # 화면 정리 후 시작

# 2-1에서 만든 Pod 6개 삭제
kubectl delete pod \
  pod-1 \
  pod-2 \
  pod-3 \
  pod-4 \
  pod-5 \
  pod-6 \
  --grace-period=1

# 이 문서에서 만든 Service 2개 삭제
kubectl delete svc \
  svc-for-web \
  svc-for-production
```

## 배운 것

- Service는 **라벨 셀렉터**로 Pod을 찾는다. 이름이 아니다.
- 연결 결과는 **Endpoints**에 나타난다. 셀렉터가 잘못됐는지 확인하려면 여기를 본다.
- 한 Pod이 여러 Service에 동시에 속할 수 있다.
- Service의 `selector`는 Deployment의 `selector.matchLabels`와 달리
  `matchLabels` 없이 라벨을 바로 적는다 (구형 API라 형식이 다르다).
