# 3) Volume Mount (File) — 파일로 붙이기

원문 : https://cafe.naver.com/kubeops/500 (3. Volume Mount (File))

- 선행 조건 : [2.env-file.md](2.env-file.md)에서 만든 `cm-file`

환경변수 대신 **파일로 마운트**한다.
환경변수는 Pod을 다시 만들어야 바뀌지만, 마운트는 **Pod을 그대로 두고도 값이 갱신된다.**

## YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-mount
spec:
  containers:
  - name: container
    image: kubetm/init
    volumeMounts:
    - name: file-volume
      mountPath: /mount                        # 이 경로에 ConfigMap의 key들이 파일로 생긴다
  volumes:
  - name: file-volume
    configMap:
      name: cm-file                            # Secret이면 secret: {secretName: ...}
```

## 실습 과정

### 1. 마운트 확인

```bash
clear                                                            # 화면 정리 후 시작
kubectl apply -f - <<'END'                                       # Pod 생성 (YAML은 위 절 참고)
# ... 위 YAML 전체 ...
END

kubectl wait --for=condition=Ready pod/pod-mount --timeout=120s  # Pod이 뜰 때까지 대기
kubectl exec pod-mount -- ls -l /mount                           # 어떤 형태로 붙었는지
kubectl exec pod-mount -- cat /mount/file-c.txt                  # 내용 확인
```

```
lrwxrwxrwx. 1 root root 17 Sep  5 12:54 file-c.txt -> ..data/file-c.txt
Content
```

**심볼릭 링크**로 붙어 있다. 파일이 아니라 링크인 데는 이유가 있다.

값이 바뀌면 쿠버네티스는 새 디렉토리에 새 내용을 통째로 쓴 뒤 `..data` 링크를 **한 번에** 갈아끼운다.
그래야 읽는 쪽이 반쯤 바뀐 파일을 보지 않는다.

### 검증: 마운트는 정말 "즉시" 반영되는가

원문은 *"마운팅으로 연결하기 때문에 Configmap이나 Secret를 수정시 사용된 Pod의 환경 변수도 즉시 변경됨"* 이라고 적고 있다.

`env`로 받은 Pod([2번](2.env-file.md)의 `pod-file`)과 나란히 두고 비교한다.

```bash
clear                                            # 화면 정리 후 시작
# ConfigMap의 값을 바꾼다
kubectl patch configmap cm-file --type merge -p '{"data":{"file-c.txt":"CHANGED-CONTENT\n"}}'

kubectl exec pod-mount -- cat /mount/file-c.txt  # 마운트로 받은 Pod
kubectl exec pod-file -- printenv file-c         # env로 받은 Pod
```

**수정 직후**

```
마운트(pod-mount): Content            ← 아직 안 바뀜
env(pod-file):     Content
```

**약 75초 뒤**

```
마운트(pod-mount): CHANGED-CONTENT    ← 바뀌었다
env(pod-file):     Content            ← 그대로
```

| 주입 방식 | 값이 바뀌면 | Pod 재생성 필요 |
|---|---|---|
| `env` / `envFrom` | **영원히 안 바뀐다** | 필요 |
| `volumeMounts` | 바뀐다 | 불필요 |

> **"즉시"는 아니다.** 실측 75초가 걸렸다.
> kubelet이 주기적으로 확인해서 갱신하기 때문이다 (기본 sync 주기 1분 + 캐시).
> 설정이 바뀌자마자 반영되기를 기대하면 안 된다.
>
> 그리고 **파일이 바뀌었다고 애플리케이션이 알아채는 것도 아니다.**
> 프로세스가 파일을 다시 읽도록 만들어져 있어야 의미가 있다.
> 그렇지 않다면 결국 Pod을 재시작해야 한다.

### 정리

```bash
clear  # 화면 정리 후 시작
kubectl delete pod \
  pod-1 \
  pod-file \
  pod-mount \
  --grace-period=1 --ignore-not-found

kubectl delete cm \
  cm-dev \
  cm-file \
  --ignore-not-found

kubectl delete secret \
  sec-dev \
  sec-file \
  --ignore-not-found
```

## 배운 것

- ConfigMap을 마운트하면 **key 하나가 파일 하나**가 된다.
- 심볼릭 링크 구조(`..data`)는 값이 바뀔 때 원자적으로 갈아끼우기 위한 것이다.
- `env`는 Pod 생성 시점에 값이 **박제**된다. 나중에 ConfigMap을 고쳐도 안 바뀐다.
- 마운트는 갱신되지만 **즉시는 아니다** (실측 약 75초).
- 갱신된 파일을 앱이 다시 읽어야 의미가 있다.
