# 1) Env (Literal) — 값을 직접 적어 환경변수로 주입

원문 : https://cafe.naver.com/kubeops/500 (1. Env (Literal))

이미지는 그대로 두고 **설정만 바꿔서** 개발/운영을 나누기 위한 리소스.
`ConfigMap`은 평범한 설정값, `Secret`은 비밀번호·키처럼 감춰야 하는 값을 담는다.

## 왜 필요한가

### 없으면 이렇게 된다

설정값을 컨테이너 이미지 안에 넣으면 **환경마다 이미지를 따로 만들어야 한다.**
개발용 DB 주소가 박힌 이미지와 운영용이 박힌 이미지가 따로 생기고,
주소 하나 바꾸려고 이미지를 다시 빌드해 배포하게 된다.

더 나쁜 것은 비밀번호다. 이미지에 넣으면 **이미지를 받을 수 있는 사람 모두가 볼 수 있고**,
레지스트리에도 그대로 남는다.

### ConfigMap과 Secret이 분리하는 것

**이미지는 하나로 두고 설정만 갈아끼운다.** 같은 이미지가 개발에서도 운영에서도 돈다.

| | 담는 것 | 특징 |
|---|---|---|
| **ConfigMap** | 평범한 설정값 (주소, 모드, 개수) | 평문으로 보관 |
| **Secret** | 감춰야 하는 값 (비밀번호, 키, 인증서) | base64로 저장, 취급이 다르다 |

둘은 **쓰는 방법이 거의 같다.** 나눠 놓은 이유는 비밀값을 따로 관리하기 위해서다.
Secret은 노드 디스크에 쓰이지 않고 메모리에만 두며, 권한(RBAC)을 따로 걸 수 있다.

> **base64는 암호화가 아니다.** 누구나 되돌릴 수 있다.
> Secret의 이점은 감춰진다는 데 있지 않고 **취급 방식**에 있다.
> 이 오해를 실제로 확인하는 것이 이 문서의 한 축이다.

주입 방법은 세 가지이고, 이 게시글의 세 문서가 각각을 다룬다.
이 문서는 그중 가장 단순한 **값을 직접 적는 방식**이다.

### 이 문서에서 확인할 것

- `envFrom`은 몇 개의 key를 가져오는가 (2절)
- Secret의 base64가 Pod 안에서 어떻게 보이는가 — 디코딩되는가 (3절)
- ConfigMap에 `false`를 그냥 적으면 왜 실패하는가 (YAML 절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

# ConfigMap·Secret도 비운다 (kube-root-ca.crt는 시스템이 만든 것이라 제외)
kubectl delete cm -n default \
  --field-selector 'metadata.name!=kube-root-ca.crt' --ignore-not-found
kubectl delete secret --all -n default --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## YAML

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cm-dev
data:
  SSH: 'false'                                 # 값은 반드시 문자열. false 를 따옴표 없이 쓰면 에러
  User: dev
---
apiVersion: v1
kind: Secret
metadata:
  name: sec-dev
data:
  Key: MTIzNA==                                # base64로 인코딩한 값 ('1234')
---
apiVersion: v1
kind: Pod
metadata:
  name: pod-1
spec:
  containers:
  - name: container
    image: kubetm/init
    envFrom:                                   # 안에 있는 key 전부를 환경변수로 가져온다
    - configMapRef:
        name: cm-dev                           # cm-dev 의 SSH, User 가 들어간다
    - secretRef:
        name: sec-dev                          # sec-dev 의 Key 가 들어간다
```

> **`'false'`의 따옴표가 필수다.** ConfigMap의 값은 문자열이어야 하는데
> 따옴표 없이 `false`라고 쓰면 YAML이 boolean으로 해석해 생성이 거부된다.
> `true`, `123` 같은 값도 마찬가지다.

## 실습 과정

```bash
clear                                                           # 화면 정리 후 시작
kubectl apply -f - <<'END'                                      # ConfigMap·Secret·Pod을 한 번에 생성
# ... 위 YAML 전체 ...
END

kubectl wait --for=condition=Ready pod/pod-1 --timeout=120s     # Pod이 뜰 때까지 대기
kubectl exec pod-1 -- sh -c 'env | grep -E "^(SSH|User|Key)="'  # 주입된 환경변수 확인
```

```
SSH=false
Key=1234
User=dev
```

### Secret은 넣을 때 base64, 꺼낼 때 평문

```bash
clear                                                 # 화면 정리 후 시작
kubectl get secret sec-dev -o jsonpath='{.data.Key}'  # 저장된 원본 값
kubectl exec pod-1 -- printenv Key                    # Pod 안에서 보이는 값
```

```
MTIzNA==        ← 저장은 base64
1234            ← Pod 안에서는 자동으로 디코딩됨
```

**base64는 암호화가 아니라 인코딩이다.** 누구나 되돌릴 수 있다.

```bash
clear                        # 화면 정리 후 시작
echo 'MTIzNA==' | base64 -d  # 누구나 원래 값을 볼 수 있다
```

그럼 Secret은 왜 쓰나. ConfigMap보다 나은 점은 이렇다.

- 노드에 파일로 떨어지지 않고 **메모리(tmpfs)에** 올라간다
- `kubectl get`이나 로그에 값이 그대로 찍히지 않는다
- RBAC으로 Secret만 따로 권한을 제한할 수 있다 (게시글 525)

**진짜 보안이 필요하면** etcd 암호화나 외부 Vault를 따로 붙여야 한다.

## 배운 것

- `envFrom`은 ConfigMap/Secret 안의 **모든 key**를 환경변수로 가져온다.
- ConfigMap의 값은 문자열이어야 한다. `'false'`처럼 따옴표를 붙인다.
- Secret은 저장할 때 base64, Pod 안에서는 자동 디코딩된다.
- base64는 **암호화가 아니다.** Secret의 이점은 취급 방식(메모리 상주, 권한 분리)에 있다.
- ConfigMap/Secret 하나의 크기는 **1MB를 넘을 수 없다** (etcd 제한).
