# 3) PV / PVC

원문 : https://cafe.naver.com/kubeops/499 (3. PVC/PV)

## 왜 필요한가

### 없으면 이렇게 된다

앞의 두 문서에서 이미 벽에 부딪혔다.

| 방식 | 한계 | 확인한 곳 |
|---|---|---|
| `emptyDir` | **Pod을 지우면 데이터가 사라진다.** 다른 Pod과 공유도 안 된다 | [1. emptyDir](1.emptydir.md) |
| `hostPath` | 노드에는 남지만 **노드가 다르면 완전히 별개**다 | [2. hostPath](2.hostpath.md) |

여기에 세 번째 문제가 더 있다. **Pod YAML에 저장소의 정체가 박힌다.**

```yaml
volumes:
- name: vol
  hostPath:                    # 이 Pod은 이제 "노드에 /node-v 가 있는 환경" 전용이다
    path: /node-v
```

이렇게 쓰면 NFS로 바꿀 때 **Pod YAML을 고쳐야 한다.** 개발자가 스토리지 종류와
경로를 알아야 하고, 같은 YAML을 다른 클러스터에 가져가면 그대로 깨진다.

### PV와 PVC가 나눈 것

**"저장소를 준비하는 사람"과 "저장소를 쓰는 사람"을 분리한 것**이 PV/PVC다.

| | 누가 쓰나 | 무엇을 적나 | 알아야 하는 것 |
|---|---|---|---|
| **PV** (PersistentVolume) | 관리자 | 실제 저장 공간의 **위치와 종류** | 디스크 경로, 스토리지 제품, 용량 |
| **PVC** (PersistentVolumeClaim) | 사용자 | 필요한 **조건만** | "1G가 필요하고 한 노드에서 읽고 쓴다" |

쿠버네티스가 둘을 **capacity와 accessMode 기준으로 짝지어 준다.**

```
Pod  ──claimName──▶  PVC  ──자동 연결──▶  PV  ──▶ 실제 저장소
     "볼륨 주세요"      "1G RWO 필요"      "1G RWO 있음"
```

**Pod은 저장소가 무엇인지 끝내 모른다.** PVC 이름만 안다.
그래서 백엔드가 hostPath든 NFS든 Longhorn이든 **Pod YAML은 그대로**다.
이것이 PV/PVC가 존재하는 진짜 이유다.

### 이 문서에서 확인할 것

- PVC는 **어떤 기준으로** PV와 짝지어지는가 (2절)
- 조건에 맞는 PV가 없으면 PVC는 어떻게 되는가 (2절, `pvc-03`)
- `local` PV가 **Pod의 스케줄링까지** 제약하는가 (3절, 대조군 실험)
- 삭제 순서를 어기면 무슨 일이 생기는가 (4절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

# 이 문서는 PVC도 만든다 — 함께 비운다 (PV는 클러스터 범위라 문서 안에서 따로 다룬다)
kubectl delete pvc --all -n default --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**
>
> 전제인 2의 `/node-v` 디렉토리는 노드 파일시스템이라 지워지지 않는다.

## 시작 전 — 클러스터 디스크 확인

PV는 **노드의 실제 디스크**를 가리킨다. 무엇이 얼마나 남았는지 먼저 본다.

### 조회 방법 1 — 노드에서 직접 (가장 정확하다)

`local`·`hostPath` PV가 쓰는 건 결국 노드의 파일시스템이라, 이게 실측값이다.

```bash
clear                                   # 화면 정리 후 시작
df -h /                                 # master 자신
for n in 31 32; do echo "### 192.168.56.$n"; ssh root@192.168.56.$n "df -h /"; done
ssh root@192.168.56.31 "df -h /node-v"  # 이 실습이 쓰는 경로가 어느 디스크인지
```

```
### k8s-master
/dev/sda4        29G   16G   14G  54% /

### 192.168.56.31
/dev/sda4        29G  9.5G   20G  33% /

### 192.168.56.32
/dev/sda4        29G  9.9G   20G  35% /

/dev/sda4        29G  9.5G   20G  33% /node-v     ← 별도 디스크가 아니라 루트와 같은 sda4다
```

| 노드 | 전체 | 사용 | 여유 | 사용률 |
|---|---|---|---|---|
| k8s-master | 29G | 16G | 14G | 54% |
| **k8s-worker1** | **29G** | **9.5G** | **20G** | **33%** |
| k8s-worker2 | 29G | 9.9G | 20G | 35% |

**이 실습에서 볼 것은 worker1 한 줄뿐이다.** PV 3개가 전부 `/node-v`(worker1)를 가리키기 때문이다.

### 조회 방법 2 — kubectl로 (SSH 없이)

쿠버네티스가 파악하고 있는 값은 `ephemeral-storage`다.
그런데 **그대로 찍으면 사람이 못 읽는다.**

```bash
clear  # 화면 정리 후 시작
kubectl get nodes -o custom-columns='NODE:.metadata.name,전체:.status.capacity.ephemeral-storage,할당가능:.status.allocatable.ephemeral-storage'
```

```
NODE          전체         할당가능
k8s-master    30318572Ki   27941595909
k8s-worker1   30318572Ki   27941595909
k8s-worker2   30318572Ki   27941595909
```

**단위가 섞여 있다.** `capacity`는 `Ki` 접미사가 붙고, `allocatable`은 **접미사 없는 바이트**다.
같은 열처럼 보이지만 1024배 차이가 나므로 눈으로 비교하면 틀린다.

#### GiB로 환산해서 보기

`jq`가 없는 환경이라 `awk`로 접미사를 판별해 환산한다. 복붙해서 바로 쓸 수 있다.

```bash
clear
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.status.capacity.ephemeral-storage}{" "}{.status.allocatable.ephemeral-storage}{"\n"}{end}' \
| awk 'BEGIN{printf "%-14s %10s %12s %10s\n","NODE","CAPACITY","ALLOCATABLE","RESERVED"}
       {c=$2; a=$3;
        if(c~/Ki$/){sub(/Ki$/,"",c); c*=1024} if(a~/Ki$/){sub(/Ki$/,"",a); a*=1024}
        printf "%-14s %9.1fG %11.1fG %9.1fG\n", $1, c/1073741824, a/1073741824, (c-a)/1073741824}'
```

```
NODE             CAPACITY  ALLOCATABLE   RESERVED
k8s-master          28.9G        26.0G       2.9G
k8s-worker1         28.9G        26.0G       2.9G
k8s-worker2         28.9G        26.0G       2.9G
```

- **헤더를 ASCII로 둔 이유** : `printf`의 `%-14s`는 표시 폭이 아니라 **바이트 수**로 세기 때문에
  한글 헤더를 쓰면 열이 틀어진다.
- `RESERVED`(약 2.9GiB)는 kubelet이 떼어 둔 **축출 여유분**이다.
  디스크가 이만큼 남기 전에 `DiskPressure`를 띄워 Pod을 쫓아낸다.
- `df -h`의 29G와 28.9G가 다른 건 **G(10억) 대 GiB(2^30)** 차이다. 같은 디스크가 맞다.

> `ephemeral-storage`는 `emptyDir`·컨테이너 로그 같은 **임시 저장소**용 회계다.
> **PV 용량과는 무관하다.** PV가 이 값을 깎지도 않고, 이 값이 PV 생성을 막지도 않는다.

### 조회 방법 3 — PV가 이미 얼마나 잡고 있나

```bash
clear               # 화면 정리 후 시작
kubectl get pv -o custom-columns='PV:.metadata.name,용량:.spec.capacity.storage,상태:.status.phase,경로:.spec.local.path'
kubectl get pvc -A  # 네임스페이스 전체의 요청 현황
```

```
No resources found
```

실습 시작 시점에는 PV·PVC가 하나도 없다.

### 이 값을 PV 만들기 전에 참고해야 하나 — **아니다**

결론부터 적으면, **`local`·`hostPath` PV에서 `capacity.storage`는 강제되지 않는 메타데이터**다.
쿠버네티스는 그 숫자를 **PVC와 짝지을 때 비교하는 용도로만** 쓰고, 실제 디스크와 대조하지 않는다.

이 환경에서 두 가지로 확인했다.

**(1) 29G 디스크에 500Gi PV를 만들어도 통과한다**

```
NAME               CAPACITY   ACCESS MODES   STATUS   CLAIM
pv-oversize-test   500Gi      RWO            Bound    default/pvc-oversize-test
```

디스크는 29G인데 500Gi PV가 400Gi PVC와 **경고 하나 없이 `Bound`** 됐다.

**(2) 10Mi PV에 50MB를 써도 막히지 않는다**

```
50+0 records out
52428800 bytes (52 MB) copied, 0.0096 s, 5.5 GB/s     ← 10Mi PV에 50MB 기록 성공

Filesystem      Size  Used Avail Use% Mounted on
/dev/sda4        29G  9.6G   20G  33% /mount3        ← 컨테이너가 보는 건 노드 디스크 전체
```

컨테이너 안에서 `df`를 찍으면 **10Mi가 아니라 노드 디스크 29G가 그대로 보인다.**
PV 용량은 쿼터가 아니라 **"이만큼 있다고 치자"는 선언**일 뿐이다.

### 그럼 언제 봐야 하나

| 상황 | 디스크 총량을 봐야 하나 | 이유 |
|---|---|---|
| 이 실습(499)의 PV 생성 | **아니오** | 1G·2G 선언은 숫자놀음이다. 디스크와 무관하게 바인딩된다 |
| 실습 중 실제로 데이터를 쓸 때 | **예** | 진짜로 노드 디스크가 찬다. 85% 넘으면 `DiskPressure`로 Pod이 축출된다 |
| 동적 프로비저닝(518) | **예** | Longhorn 등은 요청 용량만큼 **실제로 확보**하려 하므로 부족하면 실패한다 |

이 실습은 총 4G를 선언하지만 실제로 쓰는 데이터는 몇 바이트짜리 텍스트 파일뿐이라
**20G 여유가 있는 worker1에서는 디스크를 신경 쓸 일이 없다.**

> 정적 프로비저닝에서 `capacity`를 적는 진짜 이유는 **PVC와의 짝짓기 규칙**이다.
> 실습 과정 2절에서 `pvc-03`(3G)이 `Pending`으로 남는 것이 그 규칙이 작동하는 장면이다.
> 디스크가 부족해서가 아니라 **그만한 숫자를 선언한 PV가 없어서**다.

## PV가 가리킬 수 있는 스토리지 — 백엔드 분류

지금까지 "PV는 실제 저장 공간"이라고만 했다. 그 **실제 저장 공간이 무엇이 될 수 있는지**를
정리한다. 이 실습은 그중 가장 단순한 `local`을 쓴다.

### 큰 그림 — 클러스터 안이냐 밖이냐

| 구분 | 분류 | 저장소의 위치 | 쓰는 상황 |
|---|---|---|---|
| **내부망** | Local Storage | **노드의 디스크 그 자체** | 실습, 단일 노드 캐시 |
| **내부망** | On-Prem 솔루션 | 여러 노드에 **복제해서 분산** | 클라우드를 못 쓰는 운영 환경 |
| **내부망** | 공유 스토리지 | 별도 스토리지 장비 (NAS/SAN) | 이미 스토리지 장비가 있는 사내망 |
| **외부망** | Cloud Storage | 클라우드 사업자의 디스크 서비스 | EKS·GKE·AKS 등 관리형 클러스터 |

### 상세 비교

| 분류 | 대표 구현 | 노드에 묶이나 | 노드가 죽으면 | 주 accessMode | 이 저장소 |
|---|---|---|---|---|---|
| Local Storage | `hostPath`, `local` | **묶인다** | **데이터 접근 불가** | RWO | [2. hostPath](2.hostpath.md) · 이 문서 |
| On-Prem 솔루션 | Ceph, GlusterFS, StorageOS, DRBD, vSAN, **Longhorn** | 안 묶인다 | 복제본으로 **계속 동작** | RWO / RWX | [518. Longhorn](../518.dynamic-provisioning/1.longhorn.md) |
| 공유 스토리지 | NFS, iSCSI | 안 묶인다 | 스토리지 장비가 살아 있으면 동작 | NFS는 **RWX** / iSCSI는 RWO | 미사용 |
| Cloud Storage | AWS EBS, GCP PD, Azure Disk | 안 묶이나 **AZ에 묶인다** | 다른 노드에 **재연결됨** | RWO (Azure Files·EFS는 RWX) | 미사용 (베어메탈) |

**가장 중요한 축은 "노드에 묶이는가"다.** 이 실습에서 `pod-volume-5`가 worker1에만 뜨는 이유,
그리고 워커를 지정해 봐도 스케줄링이 실패하는 이유가 전부 Local Storage의 이 성질 때문이다.
실습 과정 3절의 대조군 실험이 그 장면이다.

> **고가용성이 필요하면 Local Storage를 쓰면 안 된다.** 노드가 죽으면 그 위의 데이터에
> 접근할 방법이 없다. 복제를 해 주는 On-Prem 솔루션이나 스토리지 장비를 써야 한다.

### 이 클러스터의 현재 상태

```bash
clear                     # 화면 정리 후 시작
kubectl get storageclass  # 동적 프로비저닝이 걸려 있는지 확인
```

```text
NAME                 PROVISIONER          RECLAIMPOLICY   VOLUMEBINDINGMODE   AGE
longhorn (default)   driver.longhorn.io   Delete          Immediate           6d13h
```

Longhorn(On-Prem 솔루션)이 기본 StorageClass로 잡혀 있다.
**이 실습은 그걸 쓰지 않는다.** PV를 손으로 만들고 PVC에서 `storageClassName: ""`로
비워 두기 때문에 동적 프로비저닝이 끼어들지 않는다. 그 차이는 [518](../518.dynamic-provisioning/README.md)에서 다룬다.

> 원문 정리 노트에는 Cloud Storage 항목에 **`Git`과 `AWS`가 함께 적혀 있다.**
> `gitRepo`는 클라우드 스토리지가 아니라 **Pod 시작 시 git 저장소를 복제해 넣는
> 별도 볼륨 타입**이고, 이미 오래전에 폐기됐다(k8s 1.11 deprecated).
> `AWS`는 바로 위 `AWS EBS`와 중복이다. 위 표에서는 두 항목을 뺐다.

## YAML

### PersistentVolume

```yaml
apiVersion: v1
kind: PersistentVolume                         # 네임스페이스에 속하지 않는 클러스터 자원
metadata:
  name: pv-01
spec:
  capacity:
    storage: 1G                                # 이 PV가 제공한다고 선언하는 용량
  accessModes:
  - ReadWriteOnce                              # 한 노드에서 읽기·쓰기 (아래 표 참고)
  local:
    path: /node-v                              # 노드의 실제 경로 (2번 실습에서 만든 디렉토리)
  nodeAffinity:                                # local 볼륨은 nodeAffinity가 필수다
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - {key: kubernetes.io/hostname, operator: In, values: [k8s-worker1]}
---
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-02
spec:
  capacity:
    storage: 1G                                # pv-01 과 용량은 같다
  accessModes:
  - ReadOnlyMany                               # ★ 모드만 다르다 — 이게 짝짓기를 가른다
  local:
    path: /node-v
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - {key: kubernetes.io/hostname, operator: In, values: [k8s-worker1]}
---
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-03
spec:
  capacity:
    storage: 2G                                # ★ 혼자 용량이 크다 — 1G 요청이 통째로 가져간다
  accessModes:
  - ReadWriteOnce
  local:
    path: /node-v
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - {key: kubernetes.io/hostname, operator: In, values: [k8s-worker1]}
```

> **세 PV가 같은 `/node-v`를 가리킨다.** 실습 편의를 위한 구성이고, 실제로는
> 서로 다른 디스크·디렉토리를 써야 한다. 지금은 셋 중 어느 PV에 붙어도
> 같은 파일이 보이므로, **용량 숫자가 실제 격리와 무관하다**는 점이 오히려 잘 드러난다.

| accessMode | 약어 | 뜻 |
|---|---|---|
| `ReadWriteOnce` | RWO | **한 노드**에서 읽기·쓰기 |
| `ReadOnlyMany` | ROX | 여러 노드에서 읽기만 |
| `ReadWriteMany` | RWX | 여러 노드에서 읽기·쓰기 |

### PersistentVolumeClaim

```yaml
apiVersion: v1
kind: PersistentVolumeClaim                    # PVC는 네임스페이스 자원이다
metadata:
  name: pvc-01
spec:
  accessModes:
  - ReadWriteOnce                              # 이 방식으로 쓸 수 있는 PV를 찾는다
  resources:
    requests:
      storage: 1G                              # 최소 이만큼 필요하다
  storageClassName: ""                         # 빈 문자열 = 동적 프로비저닝을 쓰지 않고
                                               # 미리 만들어둔 PV에 붙겠다는 뜻
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-02
spec:
  accessModes:
  - ReadOnlyMany                               # ★ 용량은 같고 모드만 다르다 → pv-02 로 간다
  resources:
    requests:
      storage: 1G
  storageClassName: ""
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-03
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 3G                              # ★ 이만한 PV가 없다 → Pending 으로 남는다
  storageClassName: ""
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-04
spec:
  accessModes:
  - ReadWriteOnce                              # pvc-01 과 조건이 완전히 같다
  resources:
    requests:
      storage: 1G                              # ★ 남은 pv-03(2G)을 통째로 받게 된다
  storageClassName: ""
```

네 개를 **한꺼번에** 만드는 것이 중요하다. 하나씩 만들면 붙는 순서가 달라져
`pvc-04`가 `pv-03` 대신 다른 PV를 받을 수도 있다.

### Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-volume-5
spec:
  containers:
  - name: container
    image: kubetm/init
    volumeMounts:
    - name: pvc-pv
      mountPath: /mount3                       # 컨테이너에서 보일 경로
  volumes:
  - name: pvc-pv
    persistentVolumeClaim:
      claimName: pvc-01                        # PV가 아니라 PVC 이름을 적는다
```

## 실습 과정

### 1. PV 3개를 만든다

`pv-01`(1G RWO), `pv-02`(1G ROX), `pv-03`(2G RWO) — 용량과 모드를 다르게 둔다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # PV 3개 생성
# ... pv-01, pv-02, pv-03 YAML ...
END

kubectl get pv              # STATUS 확인
```

```
NAME    CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS    CLAIM
pv-01   1G         RWO            Retain           Pending
pv-02   1G         ROX            Retain           Pending
pv-03   2G         RWO            Retain           Pending
```

**`Pending`은 몇 초짜리 과도 상태다.** 바로 다시 조회하면 `Available`로 바뀐다.

```bash
clear           # 화면 정리 후 시작
kubectl get pv  # 몇 초 뒤 다시 조회
```

```
NAME    CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM
pv-01   1G         RWO            Retain           Available
pv-02   1G         ROX            Retain           Available
pv-03   2G         RWO            Retain           Available
```

`Available`이 "아무도 안 가져간, 쓸 준비가 된" 정상 상태다.
생성 직후 `Pending`이 보이더라도 기다리면 된다.

### 2. PVC 4개로 어떻게 짝지어지는지 본다

`pvc-01`(1G RWO), `pvc-02`(1G ROX), `pvc-03`(**3G** RWO), `pvc-04`(1G RWO)를 만든다.

```bash
clear                       # 화면 정리 후 시작
kubectl apply -f - <<'END'  # PVC 4개 생성
# ... pvc-01 ~ pvc-04 YAML ...
END

# PVC별 요청 조건과 실제로 붙은 PV를 한 표로 본다
kubectl get pvc -o custom-columns='PVC:.metadata.name,STATUS:.status.phase,요청용량:.spec.resources.requests.storage,모드:.spec.accessModes[0],연결된PV:.spec.volumeName'
```

```
PVC      STATUS    요청용량   모드              연결된PV
pvc-01   Bound     1G       ReadWriteOnce   pv-01
pvc-02   Bound     1G       ReadOnlyMany    pv-02
pvc-03   Pending   3G       ReadWriteOnce   <none>
pvc-04   Bound     1G       ReadWriteOnce   pv-03
```

세 가지를 읽어낼 수 있다.

**(1) `pvc-02`는 모드가 달라서 `pv-02`로 갔다**
용량은 `pv-01`과 같은 1G지만 `ReadOnlyMany`를 요구했다. **모드가 맞아야 붙는다.**

**(2) `pvc-03`은 붙을 PV가 없어 `Pending`**

```bash
clear                                             # 화면 정리 후 시작
kubectl describe pvc pvc-03 | grep -A5 '^Events'  # 대기 사유 확인
```

```
Normal  FailedBinding  persistentvolume-controller
  no persistent volumes available for this claim and no storage class is set
```

3G를 요구했는데 가장 큰 PV가 2G다. **PV는 요청보다 크거나 같아야 한다.**

**(3) `pvc-04`는 1G를 요청했는데 2G짜리 `pv-03`을 받았다**

남은 RWO PV가 `pv-03`(2G)뿐이라 그리로 붙었다.
여기서 중요한 성질이 나온다 — **PVC는 PV를 통째로 차지한다.**
1G만 요청해도 2G PV를 받으면 그 PV는 다른 PVC가 못 쓴다. 1G가 그냥 놀게 된다.

> 그래서 PV를 미리 만들어 두는 방식(정적 프로비저닝)은 용량을 맞추기 어렵다.
> 이 문제를 푸는 것이 **동적 프로비저닝**이다 (게시글 518).

### 3. Pod에 붙인다

```bash
clear                                                               # 화면 정리 후 시작
kubectl apply -f - <<'END'                                          # pvc-01 을 쓰는 Pod 생성
# ... pod-volume-5 YAML ...
END

kubectl wait --for=condition=Ready pod/pod-volume-5 --timeout=120s  # 뜰 때까지 대기
kubectl get pod pod-volume-5 -o wide                                # 어느 노드에 올라갔는지
kubectl exec pod-volume-5 -- cat /mount3/file.txt                   # 2번 실습에서 만든 파일이 보이는가
```

```
NAME           READY   STATUS    IP              NODE
pod-volume-5   1/1     Running   20.100.194.69   k8s-worker1

file context
```

두 가지를 확인할 수 있다.

- **worker1에 올라갔다.** `nodeSelector`를 안 썼는데도 그렇다.
  `pv-01`이 `local` + `nodeAffinity: k8s-worker1`이라, 그 PV를 쓰는 Pod은 그 노드로 끌려간다.
- **2번 실습(hostPath)에서 만든 `file.txt`가 보인다.** 둘 다 worker1의 `/node-v`를 가리키기 때문이다.

#### 검증: 정말 nodeAffinity 때문인가 — 대조군

"worker1에 올라갔다"만으로는 부족하다. master에 taint가 없어 어디든 갈 수 있는 환경이라
**우연일 수도** 있다. 그래서 worker2로 강제하는 Pod 두 개를 비교했다.

```bash
clear
# ① pvc-02 를 쓰면서 worker2 를 지정 — PV는 worker1 소속이다
kubectl apply -f - <<'END'
# ... pod-affinity-test : nodeSelector worker2 + pvc-02 마운트 ...
END

# ② 볼륨만 뺀 대조군 — 같은 worker2 지정
kubectl apply -f - <<'END'
# ... pod-control-test : nodeSelector worker2, 볼륨 없음 ...
END

kubectl get pod pod-control-test pod-affinity-test -o wide
```

```
pod-control-test    1/1   Running   20.110.126.32   k8s-worker2    ← 볼륨 없으면 뜬다
pod-affinity-test   0/1   Pending   <none>          <none>         ← 볼륨 있으면 못 뜬다
```

같은 `nodeSelector`인데 **볼륨 유무만으로 결과가 갈렸다.** 우연이 아니다.
`local` PV의 `nodeAffinity`는 스케줄러에게 **하드 제약**으로 작용한다.

> 스케줄링 실패 메시지는 `0/3 nodes are available: 1 node(s) didn't match Pod's
> node affinity/selector` 로 뜬다. **`nodeSelector` 때문인지 볼륨 제약 때문인지
> 구분되지 않는다.** 위처럼 대조군을 두는 편이 원인 파악이 빠르다.
### 4. 삭제는 반대 순서로 — Pod → PVC → PV

```bash
clear                                             # 화면 정리 후 시작
kubectl delete pod pod-volume-5 --grace-period=1  # ① Pod 먼저
kubectl delete pvc pvc-01 pvc-02 pvc-03 pvc-04    # ② 그다음 PVC
kubectl get pv                                    # PV 상태가 어떻게 바뀌었나
```

```
NAME    CAPACITY   RECLAIM POLICY   STATUS     CLAIM
pv-01   1G         Retain           Released   default/pvc-01
pv-02   1G         Retain           Released   default/pvc-02
pv-03   2G         Retain           Released   default/pvc-04
```

`Bound` → **`Released`**로 바뀌었다. `CLAIM` 칸에 지워진 PVC 이름이 그대로 남아 있다.

`RECLAIM POLICY: Retain`이라 **데이터를 지우지 않고 붙잡아 둔다.**
`Released` 상태의 PV는 **다른 PVC가 다시 쓸 수 없다.** 관리자가 직접 정리해야 한다.

#### 검증: 정말 재사용이 안 되나

`pv-01`(1G RWO)이 `Released`로 멀쩡히 남아 있는 상태에서, 똑같은 조건의 PVC를 새로 만들어봤다.

```bash
clear
kubectl apply -f - <<'END'
# ... pvc-reuse-test : 1G / ReadWriteOnce / storageClassName: "" ...
END

kubectl get pvc pvc-reuse-test
kubectl describe pvc pvc-reuse-test | grep -A3 '^Events'
```

```
NAME             STATUS    VOLUME   CAPACITY   ACCESS MODES   AGE
pvc-reuse-test   Pending                                      5s

Normal  FailedBinding  persistentvolume-controller
  no persistent volumes available for this claim and no storage class is set
```

조건이 완전히 같은 PV가 눈앞에 있는데도 **"쓸 수 있는 PV가 없다"** 고 한다.
`Released`는 "비었지만 아직 남의 것"인 상태라 후보에서 아예 빠진다.
재사용하려면 PV의 `spec.claimRef`를 지우거나, PV를 지우고 다시 만들어야 한다.


| ReclaimPolicy | PVC 삭제 시 |
|---|---|
| `Retain` (기본) | 데이터 보존, `Released`로 남음. 재사용하려면 수동 처리 |
| `Delete` | PV와 실제 저장소까지 삭제 |
| `Recycle` | (폐기됨) |

```bash
clear                                # 화면 정리 후 시작
kubectl delete pv pv-01 pv-02 pv-03  # ③ 마지막으로 PV
```

> **생성은 PV → PVC → Pod, 삭제는 Pod → PVC → PV.**
> 순서를 어기면 finalizer 때문에 삭제가 멈춘다.

#### 검증: 순서를 어기면 어떻게 되나

Pod이 쓰는 중인 `pvc-01`을 먼저 지워봤다. **`kubectl`의 출력에 속으면 안 된다.**

```bash
clear
timeout 10 kubectl delete pvc pvc-01
echo "종료코드 $?"
kubectl get pvc pvc-01 -o custom-columns='PVC:.metadata.name,STATUS:.status.phase,삭제요청:.metadata.deletionTimestamp,finalizer:.metadata.finalizers[0]'
```

```
persistentvolumeclaim "pvc-01" deleted        ← 지워졌다고 출력하지만
종료코드 124                                   ← 실제로는 타임아웃 (안 끝났다)

PVC      STATUS   삭제요청                   finalizer
pvc-01   Bound    2026-09-11T14:46:11Z   kubernetes.io/pvc-protection
```

- `deleted`라고 찍히지만 **실제로는 블로킹된다.** 종료코드 124는 `timeout`이 끊었다는 뜻이다
- `deletionTimestamp`는 찍혔는데 `kubernetes.io/pvc-protection` finalizer가 붙잡고 있다
- **Pod을 지우는 순간 PVC도 같이 사라진다.** 따로 재실행할 필요가 없다

## 배운 것

- `Pod → PVC → PV` 세 단계다. Pod은 PV 이름을 모르고 **PVC 이름만** 안다.
- PV 뒤의 저장소는 **노드에 묶이는 것(`local`·`hostPath`)과 안 묶이는 것**으로 갈린다.
  묶이는 쪽은 노드가 죽으면 데이터에 접근할 수 없다. **고가용성이 필요하면 쓰면 안 된다.**
- 짝짓기 기준은 **capacity(요청 이상)와 accessMode(일치)** 다.
- **PVC는 PV를 통째로 차지한다.** 1G를 요청해도 2G PV를 받으면 나머지는 놀게 된다.
- **`local`·`hostPath` PV의 `capacity`는 강제되지 않는다.** 짝짓기용 숫자일 뿐이라
  29G 디스크에 500Gi PV도 만들어지고, 10Mi PV에 50MB도 써진다. 디스크 총량은 PV 생성 전 조건이 아니다.
- 조건에 맞는 PV가 없으면 PVC는 `Pending`으로 기다린다.
  **디스크에 20G가 남아 있어도 3G PV를 선언해두지 않았으면 3G PVC는 못 붙는다.**
- PV 생성 직후의 `Pending`은 **몇 초짜리 과도 상태**다. `Available`이 정상이다.
- `local` PV의 `nodeAffinity`는 **그 PV를 쓰는 Pod의 스케줄링까지 결정한다.**
  볼륨만 뺀 대조군은 같은 노드에 뜨는 것으로 확인했다 — 우연이 아니다.
- `Retain` 정책에서는 PVC를 지워도 PV가 `Released`로 남고 **자동 재사용되지 않는다.**
  조건이 같은 PVC를 새로 만들어도 `Pending`이다.
- 생성은 PV→PVC→Pod, 삭제는 그 반대.
  순서를 어기면 **`kubectl`이 `deleted`라고 출력해도 실제로는 finalizer에 막혀 있다.**
