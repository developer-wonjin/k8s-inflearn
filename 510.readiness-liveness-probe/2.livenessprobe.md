# 2) LivenessProbe — 죽은 앱을 되살린다

원문 : https://cafe.naver.com/kubeops/510 (2. LivenessProbe)

프로세스는 살아 있는데 **앱이 응답을 못 하는** 상황이 있다.
데드락, 무한 루프, 커넥션 풀 고갈 같은 것들이다.
컨테이너가 죽지 않았으니 쿠버네티스는 정상으로 본다.

LivenessProbe는 **직접 물어봐서** 대답을 못 하면 컨테이너를 재시작한다.

## YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-liveness-httpget1
  labels:
    app: liveness
spec:
  containers:
  - name: liveness
    image: kubetm/app
    ports:
    - containerPort: 8080
    livenessProbe:
      httpGet:                                 # HTTP로 물어본다
        path: /health                          # 이 경로를 호출해서
        port: 8080
      initialDelaySeconds: 5                   # 5초 뒤부터 검사 시작
      periodSeconds: 10                        # 10초마다
      failureThreshold: 3                      # 3번 연속 실패하면 재시작
  terminationGracePeriodSeconds: 0
```

**HTTP 상태코드 200~399가 성공**이고 그 밖은 실패다.
`kubetm/app` 이미지에는 `/status500`을 호출하면 이후 `/health`가 500을 반환하게 만드는
기능이 있어, 장애 상황을 흉내낼 수 있다.

## 실습 과정

### 1. 정상 상태 확인

```bash
clear                                                                        # 화면 정리 후 시작
kubectl apply -f - <<'END'                                                   # Service와 Pod 생성 (YAML은 위 절 참고)
# ... svc-liveness, pod-liveness-httpget1 YAML ...
END

kubectl wait --for=condition=Ready pod/pod-liveness-httpget1 --timeout=120s  # 뜰 때까지 대기
IP=$(kubectl get pod pod-liveness-httpget1 -o jsonpath='{.status.podIP}')    # Pod IP를 변수에
curl $IP:8080/health                                                         # 정상 응답 확인
```

```
pod-liveness-httpget1 is Running
```

### 2. 앱을 500 상태로 만든다

```bash
clear                                           # 화면 정리 후 시작
curl $IP:8080/status500                         # 이후 /health 가 500을 반환하도록 전환
curl -w ' (HTTP %{http_code})' $IP:8080/health  # 정말 500인지 확인
```

```
Status Code has Changed to 500

pod-liveness-httpget1 : Internal Server Error (HTTP 500)
```

**프로세스는 살아 있다.** 컨테이너도 `Running`이다. 응답만 500일 뿐이다.
LivenessProbe가 없었다면 쿠버네티스는 이 Pod을 정상으로 보고 트래픽을 계속 보냈을 것이다.

### 3. 재시작되는 것을 지켜본다

```bash
clear  # 화면 정리 후 시작
# failureThreshold 3 × periodSeconds 10 → 약 30초 후 재시작된다
for i in $(seq 1 10); do
  printf "  [%2ds] %s\n" $((i*5)) "$(kubectl get pod pod-liveness-httpget1 --no-headers | awk '{print $2, $3, "restarts="$4}')"
  timeout 5 tail -f /dev/null
done
```

```
  [ 5s] 1/1 Running restarts=0
  ...
  [35s] 1/1 Running restarts=0
  [40s] 1/1 Running restarts=1      ← 재시작됐다
```

이벤트를 보면 판단 과정이 그대로 남아 있다.

```bash
clear                                                            # 화면 정리 후 시작
kubectl describe pod pod-liveness-httpget1 | grep -A8 '^Events'  # 무슨 일이 있었나
```

```
Warning  Unhealthy  28s (x3 over 48s)  kubelet  Liveness probe failed: HTTP probe failed with statuscode: 500
Normal   Killing    28s                kubelet  Container liveness failed liveness probe, will be restarted
Normal   Created    25s (x2 over 56s)  kubelet  Created container liveness
```

`x3 over 48s` — **3번 실패한 뒤에야** 죽였다. 일시적인 오류로 성급하게 재시작하지 않기 위해서다.

### 4. 재시작 뒤 상태

```bash
clear                                                                                                                                                                                 # 화면 정리 후 시작
kubectl get pod pod-liveness-httpget1                                                                                                                                                 # 재시작 횟수
kubectl get pod pod-liveness-httpget1 -o jsonpath='{.status.podIP}'                                                                                                                   # Pod IP가 바뀌었나
curl $IP:8080/health                                                                                                                                                                  # 앱 상태가 초기화됐나
kubectl get pod pod-liveness-httpget1 -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason} exitCode={.status.containerStatuses[0].lastState.terminated.exitCode}'  # 어떻게 죽었나
```

```
NAME                    READY   STATUS    RESTARTS      AGE
pod-liveness-httpget1   1/1     Running   1 (26s ago)   66s

Pod IP: 20.100.194.100        ← 그대로다
/health → pod-liveness-httpget1 is Running    ← 500 상태가 풀렸다

Error exitCode=137
```

세 가지를 확인할 수 있다.

- **Pod IP가 그대로다.** Pod은 삭제되지 않고 **컨테이너만** 재시작됐다.
- **앱 상태가 초기화됐다.** 새 프로세스로 시작했으니 500 설정이 사라졌다.
- `exitCode 137` = `128 + 9(SIGKILL)`. kubelet이 강제로 죽였다는 뜻이다.

## Readiness와 Liveness의 차이

같은 형식이지만 하는 일이 정반대다.

| | ReadinessProbe | LivenessProbe |
|---|---|---|
| 실패하면 | **Endpoints에서 뺀다** | **컨테이너를 재시작한다** |
| Pod은 | 살아 있다 | 재시작된다 |
| 목적 | 준비 안 된 곳에 트래픽을 안 보낸다 | 고장난 앱을 되살린다 |
| 회복하면 | 다시 Endpoints에 넣는다 | (재시작으로 회복) |

> **둘을 같은 경로로 설정하면 위험하다.**
> 앱이 잠시 느려졌을 때 Readiness만 실패하면 트래픽만 빠졌다가 회복되면 그만이다.
> 그런데 Liveness까지 같이 실패하면 **재시작이 반복되며 상황이 더 나빠진다.**
> Liveness는 "재시작 말고는 답이 없는 상태"에만 걸어야 한다.

### 정리

```bash
clear                                                                         # 화면 정리 후 시작
kubectl delete pod pod-liveness-httpget1 --grace-period=1 --ignore-not-found  # Pod 삭제
kubectl delete svc svc-liveness --ignore-not-found                            # Service 삭제
```

## 배운 것

- LivenessProbe는 **프로세스가 살아 있어도** 응답을 못 하면 재시작시킨다.
- `failureThreshold`만큼 **연속** 실패해야 죽인다. 일시적 오류에 반응하지 않기 위해서다.
- 재시작되는 것은 **컨테이너**다. Pod과 IP는 그대로다.
- `exitCode 137`(SIGKILL)로 종료된다.
- Readiness는 트래픽을 막고, Liveness는 재시작시킨다. **목적이 다르니 조건도 달라야 한다.**
