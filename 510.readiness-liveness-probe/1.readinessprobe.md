# 1) ReadinessProbe — 준비될 때까지 트래픽을 막는다

원문 : https://cafe.naver.com/kubeops/510 (1. ReadinessProbe)

컨테이너가 **떴다고 앱이 준비된 것은 아니다.**
스프링 부트가 뜨는 데 30초가 걸린다면, 그동안 들어온 요청은 전부 실패한다.

ReadinessProbe는 **"준비됐다"고 확인될 때까지 Service의 Endpoints에서 빼둔다.**

## 왜 필요한가

### 없으면 이렇게 된다

쿠버네티스가 아는 "준비됨"은 **컨테이너 프로세스가 떴다**는 것뿐이다.
하지만 스프링 부트가 뜨는 데 30초가 걸린다면, 프로세스는 떴어도 **앱은 아직 응답을 못 한다.**

Service는 그것을 모르고 곧바로 트래픽을 보낸다. 그 30초 동안 들어온 요청은 전부 실패한다.

롤링 업데이트에서는 더 나쁘다. 새 Pod이 떴다고 판단하고 **옛 Pod을 내려버리기 때문에**,
아무도 응답 못 하는 구간이 생긴다. 다운타임 없다던 RollingUpdate가 무력해진다.

### ReadinessProbe가 끼워 넣는 확인

ReadinessProbe는 **"정말 준비됐냐"고 물어본다.** 대답이 올 때까지 기다린다.

```
컨테이너 뜸  ──▶  [Probe 성공할 때까지]  ──▶  Endpoints 에 추가
                    0/1, 트래픽 안 감            1/1, 트래픽 받음
```

중요한 것은 **Pod을 죽이지 않는다**는 점이다. 살려둔 채 **트래픽만 막는다.**
준비가 끝나면 알아서 합류한다. 이것이 다음 문서의 LivenessProbe와의 결정적 차이다.

### 이 문서에서 확인할 것

- Probe가 실패하면 Pod 상태와 Endpoints가 각각 어떻게 되는가 (2절)
- 실패해도 Pod이 **죽지 않는다**는 것을 확인 (2절)
- 준비가 끝나면 얼마 만에 합류하는가 — `successThreshold`의 효과 (3절)
- 검사 방식 세 가지(`exec`·`httpGet`·`tcpSocket`)는 어떻게 다른가 (YAML 절)

## 실습 시작 전 정리

```bash
clear                       # 화면 정리 후 시작

# default 네임스페이스의 실습 리소스를 전부 삭제 (시스템 네임스페이스는 건드리지 않는다)
kubectl delete pod,deploy,rs,statefulset,daemonset,job,cronjob \
  --all -n default --grace-period=1 --ignore-not-found

# Service는 kubernetes(클러스터 기본 서비스)만 남기고 삭제
kubectl delete svc -n default \
  --field-selector 'metadata.name!=kubernetes' --ignore-not-found

kubectl get all -n default  # service/kubernetes 만 남으면 정상
```

> **`-n default`를 반드시 붙인다.** `-A`(전 네임스페이스)로 실행하면 `kube-system`,
> `calico-system` 등 클러스터 구동에 필요한 리소스까지 지워져 **클러스터가 망가진다.**

## YAML

```bash
clear                                              # 화면 정리 후 시작
kubectl apply -f - <<'END'                         # pod-readiness-exec1 — Pod
apiVersion: v1
kind: Pod
metadata:
  name: pod-readiness-exec1
  labels:
    app: readiness                             # svc-readiness 가 이 라벨로 찾는다
spec:
  containers:
  - name: readiness
    image: kubetm/app
    ports:
    - containerPort: 8080
    readinessProbe:
      exec:                                    # 명령을 실행해 종료코드로 판단한다
        command: ["cat", "/readiness/ready.txt"]   # 파일이 있으면 0, 없으면 1
      initialDelaySeconds: 5                   # Pod 생성 후 5초 뒤부터 검사 시작
      periodSeconds: 10                        # 10초마다 검사
      successThreshold: 3                      # 3번 연속 성공해야 Ready로 인정
    volumeMounts:
    - name: host-path
      mountPath: /readiness                    # 노드의 /tmp/readiness 를 여기에 붙인다
  volumes:
  - name: host-path
    hostPath:
      path: /tmp/readiness
      type: DirectoryOrCreate
  terminationGracePeriodSeconds: 0
END
```

### 검사 방식 세 가지

| 방식 | 성공 기준 | 쓰임 |
|---|---|---|
| `exec` | 명령의 종료코드가 0 | 파일 존재 확인, 커스텀 스크립트 |
| `httpGet` | HTTP 상태코드 200~399 | 웹 애플리케이션 |
| `tcpSocket` | 포트 연결 성공 | DB, 메시지 큐 |

## 실습 과정

### 1. Probe가 실패하면 Endpoints에서 빠진다

먼저 **Probe가 없는** 정상 Pod(`pod1`)을 하나 띄워 비교 대상을 만든다.
그다음 위 yaml의 Pod을 추가한다. `/readiness/ready.txt` 파일이 없으므로 **검사는 계속 실패**한다.

```bash
clear                                                              # 화면 정리 후 시작
kubectl apply -f - <<'END'                                         # Service와 Pod 2개 생성
# ... svc-readiness, pod1, pod-readiness-exec1 YAML ...
END

# 5초 간격으로 상태를 본다
for i in $(seq 1 6); do
  printf "  [%2ds] %s\n" $((i*5)) "$(kubectl get pod pod-readiness-exec1 --no-headers)"
  timeout 5 tail -f /dev/null
done

kubectl get endpoints svc-readiness                                # Endpoints 에 들어갔는가
kubectl describe pod pod-readiness-exec1 | grep -A5 '^Conditions'  # 조건 확인
```

```
  [10s] pod-readiness-exec1   0/1   Running   0     5s
  [30s] pod-readiness-exec1   0/1   Running   0     25s      ← 계속 0/1

NAME            ENDPOINTS            AGE
svc-readiness   20.100.194.99:8080   33s       ← pod1 의 IP 하나뿐

Conditions:
  Type              Status
  Initialized       True
  Ready             False        ← 여기가 False
  ContainersReady   False
  PodScheduled      True
```

**`Running`인데 `0/1`이다.** 컨테이너는 돌고 있지만 준비되지 않았다고 판정된 것이다.
그래서 Service의 Endpoints에 들어가지 못했고 **트래픽을 한 방울도 받지 않는다.**

이것이 핵심이다. 준비 안 된 Pod에 요청이 가서 실패하는 일을 원천적으로 막는다.

### 2. 조건을 만족시키면 합류한다

`/readiness/ready.txt`를 만들어준다.
hostPath가 컨테이너에 마운트돼 있으므로 **Pod 안에서 만들면 노드에도 생긴다.**

```bash
clear                                                                        # 화면 정리 후 시작
kubectl get pod pod-readiness-exec1 -o jsonpath='{.spec.nodeName}'           # 어느 노드에 있는지
kubectl exec pod-readiness-exec1 -c readiness -- touch /readiness/ready.txt  # 조건 파일 생성

# successThreshold 3 × periodSeconds 10 → 최대 30초가 걸린다
for i in $(seq 1 9); do
  printf "  [%2ds] %s\n" $((i*5)) "$(kubectl get pod pod-readiness-exec1 --no-headers | awk '{print $2, $3}')"
  timeout 5 tail -f /dev/null
done

kubectl get endpoints svc-readiness                                          # 합류했는가
```

```
  [30s] 0/1 Running
  [35s] 1/1 Running        ← 3번 연속 성공해서 Ready 가 됐다

NAME            ENDPOINTS                              AGE
svc-readiness   20.100.194.99:8080,20.110.126.2:8080   93s    ← 두 개가 됐다
```

`successThreshold: 3`이라 **한 번 성공한다고 바로 붙지 않는다.**
10초 간격으로 3번을 연속 통과해야 해서 약 35초가 걸렸다.

> 원문은 "Pod가 배치된 노드에 접속해서 파일을 만들라"고 안내한다.
> 워커 노드에 ssh가 안 되는 환경이라면 위처럼 **`kubectl exec`으로 컨테이너 안에서 만들면 된다.**
> hostPath는 노드의 디렉토리를 그대로 붙인 것이라 결과가 같다.

### 정리

```bash
clear  # 화면 정리 후 시작
kubectl delete pod \
  pod1 \
  pod-readiness-exec1 \
  --grace-period=1 --ignore-not-found

kubectl delete svc svc-readiness --ignore-not-found
```

## 배운 것

- ReadinessProbe가 실패하면 `Running`이어도 **`0/1`이고 Endpoints에서 빠진다.**
- Pod을 죽이지 않는다. **트래픽만 막는다.** 이것이 Liveness와의 결정적 차이다.
- `successThreshold`만큼 **연속** 성공해야 하므로 붙는 데 시간이 걸린다.
- 검사 방식은 `exec`, `httpGet`, `tcpSocket` 세 가지.
- 롤링 업데이트에서도 이 조건이 쓰인다. Ready가 되어야 다음 Pod으로 넘어간다.
